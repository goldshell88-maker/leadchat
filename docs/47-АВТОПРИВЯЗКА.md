# Автопривязка адреса без человека (18.09.2026)

Решение владельца 18.09, окончательное: адрес привязывается к карточке
автоматически, оператор ничего не подтверждает — у него остаётся только
«изменить». Приблизительная точка допустима с пометкой; адрес без точки
допустим, но только когда карта знает улицу клиента в месте клиента; поиск по
стране при неизвестном городе — да; участок СНТ — точка массива; когда адреса
в диалоге нет — система задаёт клиенту один вопрос сама. Правки руками
автоматика не трогает никогда. Радиус пригорода 40 км уже в бою.

Пакет собран четырьмя участками: **A** — политика карты (вердикты, степени,
`geocode.card_grade`), **B** — карточка (ворота «в карточку», лестница
уступок, экран), **C** — вопрос клиенту (`address_ask`), **D** — обвязка:
настройки, догон старых строк, недельный замер, аудит точности. Этот документ
— про обвязку и про контракты между участками, на которые она опирается.
19.09 поверх пакета легли пять механизмов «тупиков карты»: Крым в фильтре
шлюза (§4.1, §4.3), «улица не та» не тупик (§2, §4.4), федеральные объявления
без города (§4.1, §6), историческая дверь (§4.5), повторная привязка сама
(§4.6).

---

## 1. Три степени и их признак по данным

Степень строки-кандидата нигде не хранится колонкой — её считает **один
судья** `geocode.card_grade(kind, geo_status, geo_provider, geo_lat, geo_lon,
geo_formatted)`:

| Степень | Признак | Что в карточке |
|---|---|---|
| `exact` — точная точка | `geo_status = exact`, координаты есть, дом (`kind = house`), провайдер без хвоста `~approx` | адрес в формате карт, точка дома |
| `approx` — приблизительная | `geo_status = exact`, координаты есть, и либо место (`kind = place`: улица, массив, центр пункта), либо хвост `~approx` у провайдера (один дом из нескольких в 40 км, поиск по стране, точка DaData `qc_geo 2/3`) | адрес в формате карт с пометкой «точка приблизительная» |
| `text` — без точки | отказ карты по содержанию (`REFUSAL_STATUSES`: `not_found`, `house_missing`, `house_mismatch`, `*_mismatch`, `other_city_in_text`) **и** есть `geo_formatted` — строка улицы, которую воркер пишет только при STREET_KNOWN | улица словами карты, без точки |
| `None` | всё остальное: `pending`, `ambiguous`, `elsewhere`, `no_city`, отказ без строки улицы, `exact` без координат (нарушенный инвариант) | строка в карточку не идёт |

Носитель «приблизительно» — только хвост `~approx` в `geo_provider`
(`POINT_APPROX_SUFFIX`); носитель «текст без точки» — `geo_formatted` у строки
с отказом. Новых колонок и статусов нет. Место всегда `approx` по `kind`, а не
по хвосту — поэтому миграция данных для старых мест не нужна.

В SQL степень не считается: обвязка (догон, аудит, воронка) делает в запросе
только грубый предфильтр (`geo_status`, `geo_lat IS NULL`), а итог судит
`card_grade` в Python. Один судья — одна истина; тест «подменили судью —
счётчики поехали вслед» это закрепляет.

## 2. Что автоматика не трогает никогда

- **Набранное руками** (`clients.address_set_at IS NOT NULL`) — никогда.
- **Карточка без строки-источника** (`address_candidate_id IS NULL`) —
  никогда: адрес пережил каскад или поставлен до 11.09.
- **Подтверждённый кнопкой ДОМ** (`resolved_by_id` у источника) — никогда.
- **Подтверждённое кнопкой МЕСТО уступает подтверждённому картой дому** —
  решение 13.09 (`clients.auto_address_yields_to`, `YIELD_PLACE_TO_HOUSE`).
- **Свой адрес автоматика уточняет только лучшей степенью того же места**:
  лестница `text → approx → exact`; между разными местами карточка
  автоматикой не переезжает.
- **Стёртый оператором адрес не возвращается**: стирание автоадреса — отказ от
  строки-источника (`rejected` + `resolved_by_id`).
- **Спор города об улице автоматика не решает.** С 19.09 «улица не та»
  (`street_mismatch`) у строк уровней A/B — не тупик цепочки
  (`street_mismatch_continues`, сторож уровня — тот же
  `STREET_EVIDENCE_LEVELS`): дом N на другой улице у первой карты значит лишь
  «на улице клиента дома N у этой карты нет» — та же улика, что
  `house_missing`, и дальше идут вторая карта по городу, уступка улице DaData,
  поиск по области и пункту, точка массива, правила `auto_decide` (точка улицы
  `_street_point`) и строка улицы без точки; каждый следующий ответ судит тот
  же вердикт, невод C — никогда. Исключение — `city_disputes_street`: карты по
  городу уже нашли дом с номером клиента на улице той же основы, но чужого
  типа («ул Ленина 5» ↔ «пр-кт Ленина, д 5»). Это спор о типе внутри города,
  и областью его не решают — одноимённая улица нужного типа в пригороде была
  бы подменой: за карты города не выходим
  (`street_mismatch_continues_beyond_city`), а единственный дом области в
  40 км решением не считается (вариант оператору, не точка) — строка остаётся
  `street_mismatch`; спор о типе — очередь механизмов (N6). Другая основа
  («ул Мира, 5» при «ул Ленина 5»), другой номер, другой город, клиент без
  типа — спором не считаются.
- **Названный клиентом пункт автоматика перебивает в одном случае — сосед за
  забором** (правило `neighbour_settlement`, владелец 20.09: «деревня Малиново,
  ягодная 17» → «Сосновка, ул Ягодная, 17» за общим забором), и только
  геометрией, только с `~approx` (степень `approx`, аудит `--degree approx`
  видит каждое). Сторожа — все обязательны: итог `elsewhere` ПОСЛЕ поиска по
  области (в её ответах — и дом-сосед, и эхо DaData «улица в пункте есть»;
  по городу `seen` не собирается, и без области сторож слеп — слаг «Москва и
  МО» правило не трогает); уровень A/B; пункт назван и не массив; названный
  пункт улицы клиента НЕ знает (ни домом, ни улицей без дома, ни переулком-
  тёзкой — иначе это спор о доме на своей улице, путь `street_point`/
  `house_missing`); дом-кандидат ровно один в `NEIGHBOUR_KM` (1,5 км до замера)
  от точки пункта с ТЕМ ЖЕ именем (Жуково ≠ Жуковка), не дальше `SUBURB_KM`
  (40 км) от точки города объявления (якорь: тёзок пункта `search_place`
  отдаёт до десяти по области, а Яндекс по городу — дома всего региона; дом в
  147 км рядом со СВОЕЙ тёзкой — не клиента; нет точки города — молчание;
  дальний дом соперником не считается — ближний решает, как у
  `only_in_radius`), не в самом городе объявления, не в СНТ/ДНТ/КП (массив в
  любом месте ответа: DaData пишет его в `area`, Яндекс — вторым пунктом в
  `settlement`), с типом улицы «улица» при клиенте без типа, с точкой самого
  дома; соперник с точкой пункта считается до подсчёта. Два в круге, ни
  одного, точки пункта нет, пункт-тёзка в 5 км — как прежде: вариант
  оператору.
- **Первое слово улицы без типа автоматика читает пунктом только по уликам
  карты** (правило `settlement_in_street` (10), владелец 20.09: «Кола рыбацкая
  8/47» при объявлении в Мурманске → «ул Рыбацкая, 8/47, Кола», кв 47). Все
  сторожа обязательны: место не названо, улица без типа ровно из двух слов
  буквами, первое — не тип, не фамилия улицы, не речь, не город объявления и
  не город справочника Авито (это `locality`); уровень A/B; итог — отказ
  (`not_found`/`house_missing`/`house_mismatch`/`elsewhere`, «улица не та» A/B
  без спора города); ни одна карта не знает улицы с этим словом (дефис карты
  снимается); DaData знает пункт области с тем же именем ЦЕЛИКОМ («Колла», «им.
  Ленина», улица, СНТ — нет); дом клиента — или дом-голова его дроби — стоит на
  остатке улицы в пункте с тем же именем и не дальше 40 км от точки города
  объявления — и он там РОВНО ОДИН по объединённому пулу всех источников
  (город, голова, область; дубли одного дома у двух карт склеены): два
  одноимённых пункта области с тем же домом — молчание, а не первый источник
  (ревью 20.09, D1). Решение всегда `~approx` (аудит `--degree approx` видит
  каждое), `rule_km` в журнале. Прочтение, установленное картой, закрывает
  остальные правила и строку улицы без точки: без дома в пункте решения нет
  вовсе — иначе дом «Рыбацкая, 8» в самом городе или «8/47» в Североморске за
  18 км побеждал бы слово «Кола» (`_улица_не_шире` прощает клиенту лишнее
  слово). Поэтому и пригород воркера (`suburb_hit`, 18.09) стоит ПОСЛЕ
  прочтения: при `elsewhere` с одним вариантом и первым словом улицы, похожим
  на пункт, место спрашивается до пригорода; прочтение установлено — пригород
  не применяется, судит только правило (10) (ревью 20.09, C1); места нет —
  пригород как прежде.
  Потолок правила: при `exact` в городе объявления слово-пункт не
  рассматривается никогда — той же терпимостью «ул Школьная, 14» в
  Ленинске-Кузнецком закрывает «Полысаево Школьная 14» (Г-1); невод C,
  названное место, спор города — никогда.
- **Голова дроби «N» для «N/M» за картами города** (20.09) — только когда
  хвост похож на квартиру (`flat_from_fraction`: число от 10) и улица без
  угловой нумерации (`corner_numbering`: другой дом с дробью на улице клиента в
  ответах — «12/5» на Луговой — значит «14/88» дом, квартира не пишется;
  считаются только дома в МЕСТЕ клиента — названный пункт/город, иначе сам
  город объявления, сторожами `known_street`: дробь на одноимённой улице в
  другом городе области — Яндекс и область отдают дома всего региона — о
  нумерации улицы клиента не говорит, ревью 20.09, C4);
  вторая карта по городу (Яндекс) — после тех же отказов DaData головой, что у
  второй карты дробью (`_ВТОРАЯ_КАРТА_ПОСЛЕ`), «неоднозначно» она не
  перебивает; область кругом 60 км — только когда голову по городу спрашивали
  и на улице клиента в городе домов нет вовсе (`_ДРОБЬ_ГОЛОВОЙ_ПОСЛЕ` и по
  вердикту головой), уровень A/B, без вариантов области с дробью целиком. Судья
  — то же правило `fraction_head`: подтверждение вердиктом (город, подсказка из
  соседней реплики — «Кола, рыбацкая 8/47», прочтение (10)) пишет квартиру; ветка
  «единственный дом-голова области в 40 км» — только когда город объявления
  улицы клиента НЕ знает (`known_street`), дубли дома у двух карт склеены, и
  квартиру она НЕ пишет: два вывода подряд в карточку не идут.

Все ворота «в карточку» (`workers/geocode.py` — постановка автозаписи и
`autofill_address`; `clients.refresh_auto_address`, `auto_address_yields_to`,
`address_text`) читают только `card_grade`. Владелец ворот — участок B.

## 3. Настройки

Все ключи — в `app_settings.SPECS`, показ — блок «Аккаунты → Адреса в
переписке», журнал — общий `settings.address_detect_changed` (`before`/`after`
по каждому полю), ручка — `PATCH /settings/address-detect`.

| Ключ | Тип, умолчание | Смысл |
|---|---|---|
| `address_geo.auto_decide` | bool, **True** | Политика карты (участок A) довершает вердикт до степени. Выключено — вердикты как до 18.09: степень получают лишь `exact`. **Ворота настройку не читают** — они читают `card_grade`: выключатель гасит новые решения, а не запись уже решённого. Действует только вместе с `address_detect.autofill`; на экране тумблер погашен без автозаписи. Включение догоняет (проверка 24.09): отказы, судимые с последнего выключения с экрана (без строки журнала — за 30 дней), теряют версию судьи, и обход починки пересуживает их сам в своих квотах (`address_catchup.mark_rejudge_after_auto_decide`, журнал `geocode.rejudge_marked`). |
| `address_detect.autofill` | bool, **True** | Писать адрес со степенью в карточку без человека. Выключено — у строки под полем кнопка «Записать в карточку» (`writable` в карточке). Включение с экрана ставит догон (проверка 24.09): задача `address_autofill_catchup` выбирает диалоги тем же `address_catchup.autofill_backlog`, что и `address-autofill-backlog`, и ставит автозапись каждому (журнал `geocode.autofill_catchup`). |
| `address_ask.enabled` | bool, **False** | Один вопрос об адресе клиенту (участок C). Выключено в коде намеренно: это первое исходящее от имени аккаунта, которое не писал никто; включает владелец тумблером после выкатки и сухого прогона (`address-ask-dry-run`) — как автообъединение 12.09. Каналы с лид-ботом отправитель пропускает сам. |
| `address_ask.delay_sec` | count, **600** (ручка: 120…3600) | Сколько секунд после реплики клиента ждать ответа человека. 600, не 180: p50 ответа оператора 205 с, p75 1014 с. Ниже 120 — система перебивала бы оператора, который уже пишет. |
| `address_ask.text` | text, `ADDRESS_ASK_DEFAULT_TEXT` | Текст вопроса. **Обязан** содержать слово из `inbound._ВОПРОС_ОБ_АДРЕСЕ` («адрес», «улиц», «куда подъехать»): ответ клиента «Ленина 5» поднимается адресом только после такого вопроса. Ручка проверяет ДО записи (400, `rule=address_word`), отправитель — ДО отправки и при пустом или чужом тексте выходит с `no_text`. Край: `NULL` в таблице читается как `""`, не как умолчание — отсюда `no_text`. Текст готовится заранее: поле на экране не гаснет от выключенного тумблера. |
| `address_ask.min_chars` | count, **25** (ручка: 0…2000) | Не спрашивать, пока во входящих за сутки меньше N букв и цифр — порог против голого «Здравствуйте», не классификатор смысла. Ноль — после любой реплики. |
| `address_geo.repair_share_yandex` | count, **30** (проценты, 0…100; читатель `repair_share_pct`) | Доля суточного потолка Яндекса и Саджеста, которую получает хвост починки (пакет 5, 20.09; решение владельца «300 из 1 000»). 0 — починке Яндекса не давать (как до 20.09), 100 — починка может выесть потолок. Потолок Яндекса `None` (платный) для доли считается за 1 000. **Только на чтение в ручке**; правится `address-limits --repair-share-yandex N`. |

Ручка отдаёт **хранимые** значения, а не «работает ли» (`ask_enabled AND
enabled`): иначе при выключенном разборе PATCH записывался бы, а тумблер на
экране «не держался». Зависимости экран знает сам.

## 4. Догон старых строк

Догон идёт **единственным существующим путём**: сброс в `pending` → починка
планировщика (`geo_repair`) → воркер → степень → `enqueue_autofill` →
`autofill_address`. Второго пути с расширенным набором статусов нет намеренно
(память `dva-puti-raznyi-schet`).

### 4.1 Команды

- `address-recheck --statuses … --checked-since …` — вернуть окончательные
  вердикты в очередь. С 18.09 сбрасывает и **`geo_formatted = NULL`**: у отказа
  строка карты теперь значит «улица без точки» и даёт степень `text` — старая
  строка у сброшенной проверки врала бы карточке до нового вердикта. `no_city`
  включать явно: у него тратится попытка на каждый проход, после восьми починка
  строку не берёт, сброс обнуляет счётчик. Принятые (`accepted`) строки команда
  не трогает.
  - `--regions "Республика Крым,Севастополь"` (19.09) — только диалоги
    объявлений этих регионов, имена — как в справочнике городов. Регион
    объявления считает `conversation_city` (колонка `item_city_slug`, без
    неё — ссылка) — тем же путём, что воркер; строки со слагом вне
    справочника и без города объявления в срез не входят, команда печатает,
    сколько их, и они идут общим сбросом. Срез шире
    `_ПОТОЛОК_РЕГИОНАЛЬНОГО_СРЕЗА` (30 000) — печать и выход: это общий
    сброс, без опции. Заведено под Крым: шлюз искал Крым и Севастополь «по
    области» по кодам ISO `RU-CR`/`RU-SEV`, которых у DaData нет (у неё
    `UA-43`/`UA-40`), и все места Крыма уходили в `not_found`; с 19.09 фильтр
    — по КЛАДР 91/92 (`docs/46-ШЛЮЗ-API.md`).
  - `no_city` после выкатки миграции 0080 стоит вернуть один раз: строки
    федеральных объявлений (`avito.ru/all/…`, `/rossiya/…`) считались с
    городом «all» — повтор включает город из других диалогов клиента и замер
    `ASK_CITY` (§6). Если шаг 2 из §4.3 ещё не выполнялся — ничего сверх
    него: он и так включает `no_city`.
  - `--levels A,B` (19.09) — только строки этих уровней разбора (колонка
    `level`, буквы через запятую, регистр не важен; чужое имя — печать и
    выход без записи). Уровень — тот же признак, по которому улика «карта
    знает улицу, дома нет» пускается в карточку (`STREET_EVIDENCE_LEVELS`,
    §2): догон `street_mismatch` без опции вернул бы и невод C — сторожа его
    не пропустят, но запросы карт он потратит (§4.4).
- `address-autofill-backlog` — поставить автозапись тем диалогам, которым есть
  что взять по степени. Два случая живого пути: (а) карточка пуста — любая
  строка со степенью (дом, место, отказ со строкой улицы); (б) карточку держит
  строка автоматики (не руками, не кнопкой), а в диалоге ждёт строка **лучшей**
  степени по лестнице. Руками и кнопкой — не ставится никогда. Источник без
  степени (вердикт сброшен) ждёт своего вердикта, а не догона. Печатает «поставлено
  (без подтверждения от очереди): N» — `enqueue_autofill` молчит при сбое Redis
  (`geocode.autofill_enqueue_failed` в логе).
- `address-audit-sample --days 7 --limit 50 --degree all|exact|approx|text` —
  случайные карточки, записанные автоматикой, TSV «текст клиента ↔ адрес
  карточки» **масками**: телефон → `[телефон]`, номер квартиры/подъезда/этажа/
  домофона → слово и `**`; улица, дом и пункт остаются — иначе сверять нечего. В
  журнал уходит только число строк.
- `address-funnel [--week YYYY-MM-DD] [--store] [--history N]` — воронка за
  неделю руками (§5).

### 4.2 Объём и цена (по замеру 18.09)

30 дней: сухой `address-recheck` по девяти статусам без `elsewhere` — 2 543
строки; с `elsewhere` и `no_city` ≈ 2,7 тыс. 60 дней — печатает сухой прогон,
оценка 4,5–5,5 тыс. До трёх запросов DaData на строку по замеру 18.09; с
20.09 полный путь строки с пунктом — город (2 текста) + круг 60 км (2) +
область (2) + точка пункта (1, только при кандидате-соседе) = до 7 HTTP без
кэша; с 20.09 у дроби «N/M» с хвостом-квартирой ещё +1–2 DaData головой по
области (только после пустой головы по городу; ≤ 29 строк/мес по корпусу) и
+1 Яндекс головой по городу у живых строк; у двухсловной улицы без типа с
отказом — +1 `op=place` (≈ 60–70/мес по корпусу 30 дней, кэш неделю; с C1 он идёт и у

не входили, прибавка — единицы в месяц); доля починки `9000 − 1500 = 7500`/сутки → 2–3 московских суток на
хвост 30 дней (§4.8); темп починки 300/10 мин → 2,7 тыс. ≈ 1,5 ч чистого
времени. На время починки оператор видит «проверяем
по карте» вместо старого отказа; реплики старше 7 дней идут без Яндекса —
точки DaData `qc_geo 2/3` останутся `~approx`, что владелец разрешил с пометкой.

### 4.5 Историческая дверь (N29, 19.09)

Реплики, пришедшие догрузкой истории (`_backfill_chat`: подключение канала,
«Загрузить историю», история чата после первого вебхука), раньше в разбор не
попадали — корзина H_no_rows, 47 диалогов/мес без единой строки при названном
адресе (по гипотезе разбора; проверка — §4.5.1). Теперь после вставки чата
ставится задача `catchup_conversation_cards` (`cardcatch:{conversation_id}`,
постановка — `cards_catchup.enqueue_cards_catchup` после commit'а): весь хвост
диалога от самой ранней вставленной реплики клиента (окно `ОКНО_ДОГОНА`,
30 дней) перечитывается тем же путём, что живой приём — обёрткой
`inbound.replay_card_extraction` (телефон, затем адрес), `now` = время
реплики. Хвост целиком, а не только вставленное: правила контекстны («кв 7»
ищет строку из истории, строчная «садовая 12» — вопрос оператора за сутки).
Ничего не вставлено (повторный заход по разобранному чату) — задачи нет; все
вставленные реплики старше окна — тоже. Карту догон не зовёт — строки
`pending` берёт `geo_repair` (новые вперёд); автозапись — после вердикта,
поверх непустой карточки только суточные строки. Исключение — геоточка Авито
с координатами: её строка сразу `exact`, карта к ней не придёт, и догон
ставит одну автозапись на диалог сам (`enqueue_autofill`, годность решает
`autofill_address`). Одна реплика — одна транзакция: сбой одной
(`cards_catchup.message_failed`) не уносит остальные; повторов ARQ нет
(`max_tries=1`). После каждого commit'а карточка и диалог перечитываются
(`db.refresh`; сессия `expire_on_commit=False`): между двумя репликами
оператор мог вписать адрес руками, автозапись — положить строку в поле —
решения по следующей реплике идут по свежей карточке, а не по снимку на старте
(ревью 19.09). Пункт/город из повторного адреса дописываются в пустое поле
строки всегда, а вердикт карты сбрасывается только у строки, **не решённой
человеком**, и только от реплики **не старше** строки (`упоминание_не_старше`):
реплика из догона старше строки и любая реплика к строке с `resolved_by_id`
координаты и варианты не трогают и перепроверку не ставят
(`record_address_candidate`). Номер из реплики старше суток (`clients.ИСТОРИЯ_СТАРШЕ`)
ложится в карточку как обычно, но аудит `client.phone_captured` несёт
`details.history=true` — отчёт «собрано телефонов» (`stats._PHONES_SQL`) такие
строки не считает: иначе день подключения канала показывал бы месяц чужих
номеров. Кадр `client:updated` — один на диалог и только живому
(`status != closed`). Вопрос клиенту ждёт догон замком `history_loading`
(`_история_едет` видит `cardcatch:{id}` в полёте). Журнал:
`cards_catchup.enqueued / already_queued / enqueue_failed (с error=класс
ошибки) / done / message_failed / gone`. Новых настроек нет:
`address_detect.enabled` и `phone_detect.enabled` действуют внутри той же
обёртки.

Разовый догон прошлого — `backfill-cards --days 30` (сухой, потом
`--no-dry-run`): с 19.09 команда идёт **той же обёрткой**
`inbound.replay_card_extraction`, что задача догона, — один путь, а не своя
копия разбора (до 19.09 номера она клала прямым `absorb_phones`, мимо
межканальной проверки и выключателя `phone_detect.enabled`); `now` = время
сообщения. Геоточки Авито с координатами — одна автозапись на диалог
(`enqueue_autofill`), только в боевом прогоне и после commit'а порции; сухой
прогон Redis не получает вовсе (откат порции — ставить не по чему). Печать:
`сообщений`, `с_номером`, `телефон_записан` (сообщений, из которых номер лёг
в карточку основным или дополнительным), `адресов`, `геоточек`. Он же
закрывает потери окна выкатки (старый воркер новой задачи не знает) и отказ
Redis при постановке. Ничего сбрасывать (`address-recheck`) не нужно: новые
строки рождаются `pending`.

Проверка в бою (память `verify-shipped-code`) — в контейнере воркера
`grep -c catchup_conversation_cards app/workers/main.py`,
`grep -c "def replay_card_extraction" app/services/inbound.py`,
`grep -c "db.get(Message, (mid, at))" app/workers/cards_catchup.py` — ≥ 1
у каждого (в `main.py` строка два раза: импорт и регистрация; у `messages`
составной ключ, `get` одним id падал в бою 18.08); через час
`cards_catchup.enqueued` > 0 и `cards_catchup.message_failed` = 0. Замер через
неделю — как проверка гипотезы, а не «47 → 0»: корзина должна упасть на долю
диалогов с репликами из истории, а не целиком.

#### 4.5.1 Что не закрывает

Строка того же адреса у клиента в **другом** диалоге (ключ `(client_id,
value)`, отклонённая строка не переезжает) — диалог без строки, но это не
потеря. Замер по `conversation_id` такие диалоги считает пустыми; замер по
`client_id` — нет. Долю самой двери в корзине даёт запрос к бою до выкатки:
живая реплика оставляет запись в `webhook_raw_log` (30 дней), историческая —
нет; ожидаемое падение корзины — эта доля, не 100 %.

### 4.6 Повторная привязка сама (N13, 19.09)

Три повода пересмотреть вердикт без человека и без новой команды — поздняя
реплика-место, возврат DaData, смена версии судьи — сведены к **одному
действию** (условный `UPDATE … SET geo_status = 'pending'` одним набором
полей `clients.сброс_вердикта`) и **одному исполнителю** — той же починке
`geo_repair` → `geocode_candidate(origin="repair")`. Нового origin, очереди и
команды владельца нет; дедуп «уже повторяли по этому поводу» — на строке,
двумя колонками миграции `0081_geo_requeue.py`: `geo_verdict_version`
(версия судьи `geocode.VERDICT_VERSION`, воркер пишет её всегда) и
`geo_without_dadata` (вердикт вынесен без ответа DaData; ставит
`_пометить(without_dadata=…)`, флаг ложится и на отложенный отказ).

- **Поздний пункт с типом после дома** (ветка 1b `_maybe_extract_address`):
  «Лесной 4» → карта нашла три по области → «деревня Заречье». Сторож
  смысла один на оба режима — `address_parse.place_stated_as_address`
  (именительный падеж типа, без «из/до/у…» перед и без «не» в двух ближайших
  словах: «еду из деревни Заречье» не адрес ни в каком режиме). Ответ на
  вопрос оператора — пункт в последнюю строку дома любого статуса, и `exact`
  тоже (клиент поправил адрес); речь без вопроса — только в строку без
  вердикта или с неспокойным (`geocode.LATE_PLACE_STATUSES` =
  `REQUEUE_STATUSES` ∪ `CHECKING_STATUSES`): у точного дома в городе место
  живёт своей строкой. Город словами («г. Шадринск») — `locality`. Дом с новым
  пунктом идёт **живой** задачей вместе со строкой места (`_maybe_extract_
  address` отдаёт кортеж строк на проверку): вопрос клиенту ждёт `pending`
  лишь `RETRY_MAX × RETRY_DEFER_SEC`, починки он не дождался бы.
- **Обход починки** (`geo_repair.перепривязать`): строки с пересматриваемым
  вердиктом (`geocode.RECHECK_STATUSES` = `REQUEUE_STATUSES` ∪
  `REFUSAL_STATUSES`; `exact` — никогда, он в карточке; `no_city` — не здесь,
  его и так берёт починка), судимые без DaData (`dadata_back`, только когда
  DaData в деле прямо сейчас) или прежней версией судьи (`verdict_version`,
  всегда, `NULL` до колонки — тоже), возвращаются в `pending` **в свободный
  остаток порции** и встают в очередь в том же заходе — не лежат без
  вариантов до полуночи. Не моложе `REQUEUE_MIN_AGE` (27 ч: `ОКНО` вопроса
  24 ч + `ADDRESS_ASK_DELAY_MAX_SEC` + `MAX_AGE` + `RETRY_MAX ×
  RETRY_DEFER_SEC`; тест считает границу из констант) — ни одно окно вопроса
  клиенту обход не видит; не старше `REQUEUE_MAX_AGE` (30 дней); попытки
  сохраняются; принятые, решённые человеком и упёршиеся в потолок попыток не
  трогаются. Одним `UPDATE … WHERE id IN (SELECT … LIMIT) … RETURNING id`:
  под READ COMMITTED решение оператора между выбором и записью не затирается.
- **Один набор полей сброса на все пути**: `clients.сброс_вердикта(*,
  с_попытками)` — обход, `address-recheck`, смена провайдера карты в ручке
  настроек (`reason=provider_changed`), `address-reparse`, `address-dedup`;
  `clients.сбросить_вердикт(row, reason=…)` — живые пути (`settlement_named`,
  `locality_named`, `street_type_named`, `late_place`). Второго набора полей
  нет намеренно (память `dva-puti-raznyi-schet`).

Замер и журнал. Событие `geocode.requeue` с `reason` / `rows` /
`candidate_id` / `was` — единая точка grep по всем путям сброса; `geo.repair`
получает `requeued=` рядом с `found`/`enqueued`. По базе: `SELECT geo_status,
geo_verdict_version, geo_without_dadata, count(*) FROM
client_address_candidates WHERE detected_at >= now() - interval '30 days' AND
geo_status <> 'exact' GROUP BY 1, 2, 3`. Через сутки после выкатки:
`geo.repair found/enqueued/requeued` и `geocode.auto_decided` по строкам,
возвращённым с `reason=verdict_version`, — это замер шага A1 (§4.3 п. 2) как
постоянного механизма. Сухой прогон сторожа 1b (до и после выкатки, без ПД в проект): по
входящим за 30 дней, где `parse_place` даёт `settlement` без улицы, — доля

### 4.7 Голос → карточка (19.09)

**Разрыв.** Владелец 19.09: «не распознал номер из аудио». У голосового
`body = None`, а весь разбор карточки читал только тело; расшифровка
(`workers/transcribe`) приезжала минуты спустя в `messages.voice_transcript`,
и после `_записать_исход(ГОТОВО)` её не читал никто. Замер за 30 дней до
выкатки: 708 расшифровок `done`, тело пусто у всех, строк адреса от них — 0,
расшифровок с телефоном 5 (в карточке 2, не в карточке 3), с адресом по
парсеру 52.

**Источник речи — один.** `voice.speech_of(body, transcript, status)` —
тело побеждает, расшифровка берётся ТОЛЬКО при `done` (у `running`/`failed`/
`too_long` текста в колонке нет по контракту), текст отдаётся без обрезки
(смещения `find_all` и подсказка `hint_word` — по одной строке);
`voice.speech_sql()` — то же условием SQL для выборок соседних реплик
(`trim` только в условии `case`). В `inbound` — обёртка `client_speech(msg)`:
единственная точка, где разбор узнаёт текст реплики. Читают речь:
`_maybe_extract_phone` (и та же строка — в `absorb_phones`),
`_maybe_extract_address`, `_дом_к_месту`, сторож `replay_card_extraction`,
`разбор_реплики_сейчас`/`реплика_без_адреса` (сторож автозаписи и
`address-reparse` судят строку от голоса по той же расшифровке), выборки
`_пункт_из_соседних_реплик`, `workers/geocode._соседние_реплики` (подсказка
пункта карте — «своя реплика» и соседи), контекст и сама реплика в
`workers/address_llm`, `address_ask.client_declined` (отказ голосом глушит
вопрос; `InboundRow.voice_transcript_status`), счётчик `с_номером` в
`backfill-cards`. Не читают намеренно: дедуп эха исходящих, служебная подпись
Авито (`AVITO_SYSTEM_PREFIX` бывает только в теле), `address_funnel`, `leads`
(хвосты — замер и заявка, отдельный шаг).

**Контур.** `transcribe_voice`, фаза 3: `_записать_исход(ГОТОВО)` вернула
True (строка есть, commit прошёл, кадр `message:transcript` ушёл) → строго
после этого `voice.enqueue_voice_card` ставит задачу `voice_card_extract`
под именем `voicecard:{message_id}` (дата едет ради одной партиции). Фаза 1
при повторе задачи на `done` перепоставляет разбор (самопочинка окна «воркер
умер между commit'ом и постановкой»); `too_long` — нет. Отдельная задача, а не
хвост расшифровки: упади разбор внутри, ARQ повторил бы расшифровку, а фаза 1
вышла бы на `done` — номер не попал бы в карточку никогда. Регистрация
`workers/main.py`: `keep_result=0` (постоянное имя; замок `transcribing` не
залипает), `max_tries=3` (на `OperationalError`/`InterfaceError` —
`Retry(defer=30)`). Имена задач голоса рождаются в одном месте
(`voice.transcribe_job_ids`, `voice.VOICE_CARD_JOB_ID`).

**Задача `workers/voice_card.py`.** Не своя копия разбора, а обёртка догона
`cards_catchup.replay_conversation(since=время голосового, before=None)` —
хвост до конца переписки, а не одна реплика: «кв 7», дописанное текстом,
пока считалась запись, ложится в строку от голоса; а часть, дописанная позже
голосового, не перебивается ранним «квартира 3» (итог верный только
благодаря хвосту). Без потолка суток намеренно (ревью 19.09, C1): у
голосового, расшифрованного с опозданием (досчёт `voice_repair`), потолок
`+24 ч` возвращал бы «кв 7» из окна, но не «кв 9» через двое суток — поздняя
часть откатывалась бы к старой в строке и в автоадресе карточки; у свежего
позже него реплик нет, хвосты совпадают. Простые значения
(`conversation_id`, время, речь) снимаются ДО хвоста — после rollback +
expunge_all при сбое одной реплики `msg` протухает. Сбой соединения
(`OperationalError`/`InterfaceError`) догон НЕ изолирует как сбой одной
реплики, а отдаёт наверх (ревью 19.09, C2): задача голоса просит
`Retry(defer=30)`, иначе номер из расшифровки терялся бы под «done» до
ручного `backfill-cards`; задача истории (`max_tries=1`) падает со следом.
Что живой путь ставил бы задачами, догон отдаёт полной формой
`inbound.replay_card_extraction_full` → `CardReplayFull(card, geocode_ids,
llm_read_wanted)` и копит в `CatchupResult.geocode_ids/llm_reads` — только
по просьбе вызывающего (`со_следствиями=True`, у задачи голоса; у истории
копилка закрыта: ворота модели — запрос к ленте, а читать их некому); ставит
их задача голоса и только у СВЕЖЕГО голосового (`СВЕЖЕЕ` = 24 ч от
отправки): карта сразу (`enqueue_geocode`) и модель-читатель
(`enqueue_llm_read`, ворота ОДНИ с живым путём — `inbound.llm_read_wanted`);
старому (досчёт `voice_repair`) — семантика догона, карту делает `geo_repair`.
Автозапись по геоточке и один кадр `client:updated` живому — как у догона.
Объединение двойников из задачи не ставится: пару найдёт ночной
`merge_backlog` под своими сторожами. Трёхполевой контракт
`replay_card_extraction`/`CardReplay` не меняется; полная форма идёт ЧЕРЕЗ
него (копилка `_СЛЕДСТВИЯ`): один шов «реплика догона» на историю,
`backfill-cards` и голос. Исходы задачи: `nothing`/`no_speech`/`gone`/
`done`/`empty`; журнал `voice_card.done` с `tail_messages/tail_phones/
tail_addresses/reason/fresh/geocode/llm` (поля хвоста, не «в голосовом был
номер»: критерий боя — строка `client_phone_candidates.message_id = <id
голосового>`), `voice_card.db_unavailable`, `voice.card_enqueue_failed`.

**Доверие.** Правила те же, что у текста (12.09: пустой основной заполняется
при `PHONE_DETECT_AUTOFILL`, заполненный не меняется никогда; 18.09:
автопривязка без человека). Строка получает `source='voice'`
(`CANDIDATE_SOURCE_VOICE`; CHECK'а на колонке нет, миграции нет), и подпись
«из голосового» стоит и под ОСНОВНЫМ номером карточки (`_phone_source`,
`запись()` — после ручного ввода, перед «из диалога»), не только у
предложений (`identity_view.phone_source == "voice"`, элементы `phones` с
`source: "voice"`; экран — `PhoneSource += "voice"`, цитата предложения из
`voice_transcript`). Аудит `client.phone_captured` оставляет
`details.source="regex"` (колонка отчёта). Через две недели — замер доверия:

```sql
SELECT source, status, count(*) FROM client_phone_candidates
WHERE detected_at >= now() - interval '14 days' AND source IN ('inbound','voice')
GROUP BY 1,2 ORDER BY 1,2;
```

Доля `voice` отклонённых/заменённых выше `inbound` — откат одной строкой в
`_maybe_extract_phone`: `autofill = autofill and not речь.spoken` (голос →
всегда предложение). Новой настройки нет, пока нет числа.

**Замок `transcribing` (`workers/address_ask.py`).** На 600-й секунде
`client_described` считает голосовое описанием — без замка вопрос ушёл бы
тому, кто только что наговорил адрес. Замок — по задачам ARQ В ПОЛЁТЕ
(`_голос_считается`: `voice:{id}`, `voice:{id}:repair`, `voicecard:{id}` —
среди последних `LLM_CHECK_LIMIT` входящих любого вида, у тех из них, где есть
голосовое; голосовое, за которым клиент прислал пять текстов, из окна уже
вышло — расширять ли окно до последнего голосового за сутки, отдельное
решение), не по колонке: NULL в базе
— и «в очереди за досчётом», и «Whisper выключен», и «не дождалась замка»;
`running` — и «считает», и «воркер умер». Исход после `RETRY_MAX` — честный
`skip("transcribing")`, вопрос не уходит (как `history_loading`). Сухой
прогон `cli` переходные замки Redis не моделирует и раньше (`llm_reading`).

**Догон.** `backfill-cards --days 30` той же обёрткой добирает расшифровки,
лежавшие `done` до выкатки: сухой — только числа (`с_номером` теперь считает
речь); боевой `--no-dry-run` — ТОЛЬКО по решению владельца: при
`PHONE_DETECT_AUTOFILL=True` он заполнит до 3 пустых основных номерами из
месячных расшифровок и заведёт ~52 строки адреса (карту им сделает
`geo_repair`; автозапись адреса не случится — сутки по `detected_at`).

**Что помнить при выкатке.** Порядок: пакет 2 в бою, затем этот, `ship.sh` не
прерывать. Миграций нет. Окно выкатки: задачи `voicecard:*`, поставленные
новым api до перезапуска воркера, старый воркер отвергнет как неизвестные —
след в журнале, добирает `backfill-cards`. Проверка «код в бою» (грепом по
контейнеру, помнить про `.pyc`):

```bash

"${DC[@]}" exec -T worker grep -c "voice_card_extract" /app/app/workers/main.py      # 2
```

Живая проверка без настоящих данных: с проверочного аккаунта (учётки 23.08)
голосовое на проверочный канал с вымышленным номером «900 111 22 44» и
адресом → за ~2 мин `voice.transcribed` → `voice_card.done … reason=phone_*`,
в карточке номер с подписью «из голосового» (или предложение с той же
подписью), строка `client_phone_candidates` с `source='voice'` и

### 4.8 Сосед за забором (20.09)

**Случай.** «мой адрес ягодная д 17 деревня малиново», объявление Одинцово.
DaData по городу — один дом «Сосновка, ул Ягодная, 17» (`precise`), вердикт
`settlement_mismatch`; по трассе HEAD 32a9717 строка кончалась `elsewhere` с
одним вариантом и пустой карточкой (`variants` пункт не сверяет, `suburb_hit`
требует названный пункт, `_пункт_уступает_городу` при типе не уступает,
`auto_decide` знал `elsewhere` только как `only_in_radius`). Владелец: дом
юридически в Сосновке, на местности — за общим забором с Малиново.

**Механизм.** Правило (9) `neighbour_settlement` в `auto_decide` под
`elsewhere` после `only_in_radius`; улика воркера — `settlement_place_hits`
(один `dadata.search_place(«деревня Малиново», region=…)`, кэш `op=place`
неделю, пустой — сутки), спрашивается только когда без него правило заведомо
не сработает: итог `elsewhere` после области, уровень A/B, пункт не массив,
кандидат уже лежит в ответах города/области (`neighbour_candidates`), DaData в
деле и в потолке. Сторожа — §2. Решение — `exact` с `~approx`, строка карты
соседа («ул Ягодная, 17, Сосновка, Одинцово»), точка дома, слово клиента о
пункте в строке не переписывается; журнал `geocode.auto_decided
rule=neighbour_settlement was=elsewhere rule_km=…` — `rule_km` и есть замер
для радиуса. 403 на запросе места — DaData недоступна: решений нет, строка
остаётся вариантом с флагом `geo_without_dadata`, обход `dadata_back` вернётся.
Радиус `NEIGHBOUR_KM = 1.5` — до замера (по OSM этот дом в 0,6 км от
центра Малиново; в круге 3 км — восемь пунктов и две разные «Новая улица»):
поднимать только с распределением `rule_km` по живым срабатываниям.

**Версия судьи** `VERDICT_VERSION = 2`: обход починки (§4.6) вернёт в очередь
все строки `RECHECK_STATUSES` 27 ч–30 дней (≈2,5–2,7 тыс.), каждой +1 попытка
и до 7 запросов DaData без кэша (§4.2) — 2–3 московских суток доли. Перед
выкаткой убедиться, что обход версии 1 завершён (`geo.repair requeued=0`
несколько заходов подряд), иначе части строк достанется +2 попытки.

**Догон 30–60 дней (рука, после сухого прогона):** `address-recheck --statuses
elsewhere --levels A,B --checked-since <60 дней>` — `elsewhere` с названным
пунктом и есть урожай правила; ожидание по стенду 19.09 — единицы срабатываний
в месяц (правило качества, не объёма: главный эффект — Малиново-подобные
строки перестают быть тупиком).

**Проверка «код в бою» грепом по контейнеру, не по git:**
`docker compose exec worker grep -c "RULE_NEIGHBOUR_SETTLEMENT" app/services/geocode.py` ≥ 1;
`docker compose exec worker grep -c "settlement_place_failed" app/workers/geocode.py` ≥ 1;
`docker compose exec worker grep -n "^VERDICT_VERSION" app/services/geocode.py` → `= 2`.
Строку Малиново (`pending` после reparse 20.09) возьмёт починка сама; через
10–15 мин — `SELECT geo_status, geo_provider, geo_formatted, geo_lat, geo_lon,
geo_verdict_version, geo_variants FROM client_address_candidates WHERE
settlement ILIKE 'малиново' AND street ILIKE 'ягодная%' ORDER BY detected_at
DESC LIMIT 3` — ожидание `exact / dadata~approx / «ул Ягодная, 17, Сосновка,
Одинцово» / 55.7000, 37.3000 / 2 / NULL`; в журнале воркера `rule_km` — первое
настоящее расстояние Малиново → Ягодная 17 (в живом прогоне 20.09 точка
пункта не бралась). `rule_km` > 1,5 — правило смолчало честно, и это повод
обсуждать радиус с числом в руках. Через неделю: `address-audit-sample --days 7
--degree approx` — глазами каждое срабатывание правила; ложное = сузить радиус;
ноль при живых `elsewhere` с пунктом = смотреть, где молчит сторож (в) или
`precise`. Тесты — `tests/unit/test_paket4_neighbour_1909.py` (§7).

городу у живых строк; судья — правило `fraction_head` (город → подсказки из
соседних реплик → область; радиусная ветка без квартиры). (Б) Правило (10)
`settlement_in_street`: `search_place(«Кола», область)` → «г Кола» → уже
собранные ответы судятся с прочтением `settlement=Кола, street=рыбацкая`,
суженные до домов в пункте с тем же именем целиком в 40 км от города: дом
целиком — (i) `rule=settlement_in_street`; дом-голова дроби — (ii) правило
дроби с прочтением (`rule=fraction_head`, кв 47); соперники в обеих ветках —
по объединённому пулу источников (D1). Сторожа — §2.

**Трасса после сборки** (реплика старше 7 дней, DaData + OSM): город «8/47» и
«8 к 47» → 0; OSM → улица в Коле; голова по городу «Кола рыбацкая 8» → 0;
область кругом и без круга → 0 (или сама «г Кола, ул Рыбацкая, д 8» — тогда
голова по области не тратится); голова по области кругом → «г Кола, ул
Рыбацкая, д 8»; место «Кола» → «г Кола»; `auto_decide` → прочтение → (ii).
Ожидание в базе: `exact / dadata~approx / «ул Рыбацкая, 8/47, Кола» / office 47
/ geo_variants NULL / geo_verdict_version 2`; в журнале `geocode.auto_decided
rule=fraction_head was=house_missing settlement_read=Кола rule_km=9.0`; походы
DaData на строку: место 1, голова по области ≤ 1 (в стенде — пять походов
ровно в этом порядке). Печать «8/47» + кв 47 — контракт правила дроби (номер
клиента печатается, квартира — в `office`); «г» перед пунктом не печатается
(тип — только от клиента). Что DaData отдаёт по области на «Кола рыбацкая 8/47»
и «Кола рыбацкая 8» — единственное, от чего зависит срабатывание на этой строке;
живой прогон 20.09 записал только город/Яндекс/OSM — снять раз перед выкаткой
(ключ и бой у владельца). Если у ФИАС дома 8 на Рыбацкой в Коле нет — правило
молчит честно (`geocode.street_head_unresolved`), строка остаётся
`house_missing` без карточки; следующий шаг — «прочтение по улице без дома»,
не в этом пакете.

**Где искать прочтение.** Только в `geo_formatted`, `office` и журнале
(`settlement_read`): `street`/`settlement` строки не переписываются (условный
UPDATE по снимку), `address-reparse`, N13 `late_correction_wins` и отчёты по
`street` видят сырой разбор «Кола рыбацкая». Регистр первого слова не улика:
у `_ПУНКТ_ИМЯ_ВПЛОТНУЮ` заглавная — единственная опора (карты ещё не
спрашивали), у правила (10) улика — место у карты, и «кола рыбацкая» строчными
проходит так же.

**Границы, записанные намеренно.** «Апатиты рыбацкая 8» при объявлении в
Мурманске — Апатиты в справочнике Авито, слово идёт в `locality`, правило (10)
молчит (край Б0 — очередь механизмов); «Мурманск рыбацкая 8» (город объявления
первым словом) — то же; «рыбацкая Кола 8/47» (пункт вторым словом) — после
замера; невод C — после сухого подсчёта доли; собственный поход правила по
области (пункт дальше 60 км, которого плоский запрос области не вернул) —
после замера по `settlement_read`/`street_head_unresolved`; посылка «хвост от
10 — квартира» в городской ветке дроби — контракт 18.09, корпусом 20.09
подтверждается слабо (среди отказов с M ≥ 10 дома-дроби и квартиры поровну) —
менять по всему правилу решением владельца, здесь она сведена в одно место
`flat_from_fraction` и выключается угловой нумерацией.

**Версия судьи** остаётся `2`: А и Б идут тем же коммитом, что сосед за

### 4.10 Пакет 5: доля Яндекса и монотонность пересуда (20.09)

Решение владельца 20.09 — «всё автоматически и точно, точность должна только
расти». Правил разбора и судьи нет, `VERDICT_VERSION = 2` не поднимался.
Проект и разбор возражений — `scratchpad/newcode/paket5/{design,skeptic,decisions}_paket5.md`.

**Q1 — Яндекс и Саджест починке долей.** До 20.09 ветка возраста
(`workers/geocode.py`: реплика старше недели → потолок 0) стояла раньше ветки
origin, и `доля_починки(0) == 0`: хвост починки Яндекса не получал никогда.
Теперь порядок — сначала `origin == repair` (Яндекс и Саджест —
`потолок × repair_share_yandex // 100`, DaData — как была), возраст — только
у живой задачи. `ЗАПАС_ЖИВЫМ` остался у одной DaData; `доля_починки` — один
источник истины «что получает починка».

**Q2 — монотонность пересуда.** Колонка `geo_prev JSONB` (миграция 0082,
форма `clients.СНИМОК_УЛИК`): сброс по триггеру обхода и `address-recheck`
кладут туда улики прежнего вердикта (построчно, оптимистическое условие
`geo_checked_at IS NOT DISTINCT FROM`), живые изменения и решение человека
стирают. Воркер в фазе 1 сверяет ключ содержания снимка
(`value, settlement, settlement_type, locality, area`) с текущей строкой —
чужой снимок стирается (`rejudge_prev_stale`). Перед записью:
`verdict_rank` (5 точка дома · 4 приблизительная · 3 строка улицы · 2 варианты
при любом статусе · 1 именованный отказ · 0 остальное; считается через
`card_grade`) и `keeps_previous(rank_new, rank_prev, maps_incomplete)` —
удержать, если новый слабее И часть карт **этой строке** отказала по факту
(`_Отказы`: Яндекс, Саджест — любой отказ, не только потолок и доля: сеть,
5xx, не тот JSON, в каждом обработчике похода; DaData — `dadata_недоступна`).
Полный набор и
слабее — записывается (`rejudge_weaker`): карта поправила справочник. Флаг
`geo_without_dadata` — по этому суду, не из снимка (иначе петля с
`dadata_back`). Слепой суд любого исхода в `RECHECK_STATUSES` оставляет в
`geo_prev` снимок записанного с `missing=[…]`; полный суд и `exact` — `NULL`.

**Обход (`geo_repair`).** Строка со снимком ставится в очередь только в
квоту Яндекса `квота_яндекса = (доля − расход) // 3` (по 3 похода на строку);
без снимка — как раньше. Квоты нет (`None`), когда Яндексу в починке делать
нечего: ключа нет или доля 0 (`repair_share_yandex=0`, потолок 0) — ждать
нечего, строки со снимком судятся DaData и OSM с удержанием улик, триггеры
сброса не ограничены. Третий триггер `kept_blind`: `geo_prev IS NOT NULL
AND geo_checked_at < now − 20 ч`, только при свободной квоте; ключ есть, а
доля 0 — пауза `yandex_share_zero` (Яндекс к строкам не вернётся, пока
владелец не даст долю). Границы — `ПОТОЛОК_ПОПЫТОК = 8` и пауза 20 ч. Раз в
московские сутки — `geocode.daily_counters` **за вчера** (первый заход после
полуночи сегодняшних ключей ещё не видит; вчерашние живут ещё сутки) — есть
по чему настраивать долю. `address-recheck` получил `--older-than-hours`
(умолчание 27 — окно вопроса клиенту). Ручка смены провайдера снимает бан
с `blocked`, **не трогая** `geo_prev` (`сброс_вердикта(улики=СНИМОК_НЕ_ТРОГАТЬ)`):
строка со снимком от обхода, упёршаяся в бан, снимок несёт.

**Q7 — города справочника.** `city_by_name` нормализует дефис/тире/ё и по
`declined=True` знает **только предложный падеж** («Салавате», «Твери»,
«Грозном», «Ярославле», «Раменском», «Новом Уренгое», «Великих Луках»,
«Набережных Челнах», «Ростове на Дону»); творительный «-ом» у
существительных не принимается — «в Подольском районе» иначе давало бы
Подольск. Все читатели `_имена_городов()` сравнивают через `_норм_города`
(одна нормализация с справочником): «Санкт-Петербург ул Ленина 5» —
`locality`, не пункт; геоточка «Санкт-Петербург, 5» — не дом. Включают только вызывающие с известным падежом: `inbound._пункт_в_реплике`
(«в …», со сторожем следующего слова `район|р-н|округ|край|область|мкр|шоссе|
проспект|тракт`; город-прилагательное — как написано), `address_parse` после
«г/город» (`locality` каноном, `value`/`raw` как написал клиент), воркер по
`row.locality` старых строк. Инъективность держится тестом по всему `CITIES`
и 100 прилагательным районов.

**Что осталось руками (и почему):** `address-recheck` по строкам, судимым до
пакета вслепую (признака «без Яндекса» у них нет; после пакета такие не
рождаются), и `address-reparse --days 30` — оба безопасны в любое время: залп
идёт в квоту. Замер выигрыша Q2 — стенд `stage1.py` (поля `fmt`, `nvar`,
`ver`, `wo_dd`, `prev`) через сутки после выкатки.

**Проверка «код в бою»:** `docker compose exec worker grep -c "rejudge_kept" app/workers/geocode.py` ≥ 1;
`docker compose exec scheduler grep -c "kept_blind" app/scheduler/jobs/geo_repair.py` ≥ 1;
`docker compose exec api alembic current` → `0082`;
`docker compose exec api python -m app.cli address-limits` → `repair_share_yandex=30%`.
Тесты — `tests/unit/test_paket5_2009.py` (§7).

## 5. Еженедельный замер воронки

Одно определение на всех — `services/address_funnel.py`; задача планировщика,
команда и строка монитора зовут `measure`/`compare` оттуда и ничего не считают
сами. Снимки — таблица `address_funnel_weekly` (миграция 0079: `week_start`
понедельник МСК, `computed_at`, `counts` jsonb). Таблица, а не Redis: сравнение
с прошлой неделей и история обязаны пережить перезапуск.

**База неизменяемая, карточки — снимок.** Реплики (`created_at`) и строки
(`detected_at`) за неделю не меняются; карточку могут заполнить и через месяц,
поэтому повторный пересчёт недели меняет `card_*` и делается только руками
(`address-funnel --store`).

### 5.1 Поля

| Поле | Что считает |
|---|---|
| `dialogs` | диалоги, где клиент в окне написал что-то похожее на адрес: грубый невод `ADDRESS_LIKE_PATTERN` (слово типа улицы/пункта) + цифра, без служебной подписи Авито «Вот подробности». Невод независим от разбора — его смысл увидеть «адрес есть, строки нет» |
| `with_row` | из них — со строкой-кандидатом (`detected_at` в окне ± сутки) |
| `card` | из них — адрес в карточке (снимок) |
| `card_auto_exact` / `card_auto_approx` / `card_auto_text` | автоматика (не руками, источник без `resolved_by_id`), степень источника по `card_grade` |
| `card_person` | руками (`address_set_at`) или кнопкой (`resolved_by_id` у источника) |
| `card_unknown` | источника нет (каскад, адрес до 11.09) или у источника нет степени |
| `edited_after_auto` | ручная правка (`client.address_edited`, `source=manual`) поверх адреса, который до неё записала автоматика — строка журнала о том же тексте без человека (`user_id IS NULL`) |
| `asked` | строк журнала `conversation.address_asked` в окне (пишет участок C) |

Партиция карточки сходится по построению: `card = card_auto_exact +
card_auto_approx + card_auto_text + card_person + card_unknown`.
Присоединённая карточка (`merged_into_id`) считается по своей строке — адрес
при объединении переезжает, диалог остаётся у прежней.

### 5.2 Тревога

`compare(prev, cur)` — список причин, пусто — всё ровно:

- `card_share` — обе недели ≥ 100 диалогов, доля `card/dialogs` упала на
  ≥ 10 п.п.;
- `row_share` — то же для `with_row/dialogs` (регресс разбора);
- `edits` — автокарточек ≥ 50 и правок руками поверх них ≥ 10 %.

Прошлая неделя — **одно правило**: строка с `week_start − 7 дней`, иначе
`None` (при пропущенной неделе соседняя строка — позапрошлая, и падение
считалось бы по разрыву в две недели). Меньше ста диалогов — шум: неделя
отпуска даёт ±20 п.п.

Задача `scheduler/jobs/address_funnel.py` — понедельник **04:40 МСК**
(01:40 UTC, планировщик в UTC), `misfire_grace_time` 6 ч, `statement_timeout`
180 с. Считает последнюю полную неделю, пишет снимок, **коммитит явно**
(`session_scope` на выходе откатывает — без этой строки ровная неделя терялась
бы, `prev` был бы вечно `None`, и тревога стала бы невозможной по построению),
затем при причинах шлёт `address.funnel_dropped` (важно, администраторам) и
логирует `address_funnel.measured`. Ошибка замера — исключение до commit,
строки недели нет, в лог планировщика; центр уведомлений упал — строка недели
уже есть, исключение наружу.

### 5.3 Где смотреть

«Настройки → Внешние сервисы»: последняя строка монитора «Адреса в карточку
(воронка за неделю)» — состояние «Нет замера» / «Ровно» / «Падение» с долями
за неделю и прошлую и разбивкой по степеням в заметке. Пробы у строки нет,
«Проверить все» её обходит. И `address-funnel --history 8` в консоли.

  `CANDIDATE_SOURCE_VOICE` → `phone_source`/`phones[].source == "voice"`.
- Дом — одним определением на проект: `address_parse.is_house_number`
  (объединение головы `_ДОМ` и `_НОМЕР_ДОМА`; латинская техника «4G» и четыре
  цифры не дом) — его читают `geocode._похож_на_дом` (номер клиента у точки
  улицы/массива) и модель-читатель (`address_llm.parse_reading`); своих
  регэкспов дома у них больше нет.
- «Реплика без адреса по нынешнему разбору» — один предикат
  `inbound.реплика_без_адреса` (через `разбор_реплики_сейчас`, порядок как у
  живого пути); его читают `address-reparse` (в том числе `--auto` для
  автопринятых строк), сторож автозаписи `workers/geocode._отсеять_речь`.
  Отклонение и снятие автозаписи — с кадром `client:updated`
  (`address_candidate_rejected` у воркера, `address_reparsed` у CLI) строго
  после commit'а; фронт перечитывает карточку по любой причине.
- Источник строки едет за ссылкой: при переносе `message_id` на повтор адреса
  из другого диалога `source` строки — источник повтора (`llm`/`voice`), пара
  (`message_id`, `source`) — одно утверждение о реплике, по нему судят сторожа
  речи.
- Сосед за забором (9): `geocode.NEIGHBOUR_KM` — единственный радиус;
  `settlement_place`/`neighbour_candidates` — ворота воркера и правило читают
  одно и то же; уровень — `STREET_EVIDENCE_LEVELS`; «улица в пункте есть» —
  `street_in_settlement(..., с_типом=False)`; дома клиента — общий фильтр
  `_дома_клиента` (он же под `_дома_области`); «тот же дом у двух карт» —
  `_одно_пятно` (он же под `_one_spot`); имя пункта — `_то_же_имя_пункта`
  (равенство, не `_пункт_назван`); `Evidence.settlement_place_hits`,
  `Decision.km` — поля с умолчаниями в хвосте.
- Фильтр региона DaData (`_РЕГИОН_ФИЛЬТР`, `locations_for`) — шлюз; Крым и
  Севастополь только по КЛАДР 91/92, `UA-43` в код не кладём; договор слоёв
  «все крымские слаги `CITIES` ведут в фильтр КЛАДР» держит тест
  `tests/unit/test_paket2_crimea_1909.py`.
