## 1. Один раз: ключи, секреты, сервер

### 1.1. Пара ключей minisign

Подпись обновлений — единственное, что защищает клиента от подмены
инсталлятора: приложение проверяет `.sig` **зашитым в бинарник публичным
ключом**, поэтому даже компрометация VPS не даёт подсунуть обновление
(04 §6.2). Ключ генерирует ответственный за релизы **у себя локально**:

```bash
cd desktop
npm run tauri signer generate -- -w ~/.tauri/leadchat.key
# спросит парольную фразу — придумайте длинную и сразу положите в менеджер паролей
```

Получилось два файла:

| Файл | Что это | Куда |
|---|---|---|
| `~/.tauri/leadchat.key` | **приватный** ключ | GitHub Secrets, менеджер паролей. Больше **нигде** |
| `~/.tauri/leadchat.key.pub` | публичный ключ | коммитится в `desktop/src-tauri/tauri.conf.json` |

```bash
# публичный ключ -> в конфиг (plugins.updater.pubkey), коммитится в git
cat ~/.tauri/leadchat.key.pub
```

> **Приватный ключ и парольная фраза не попадают ни в репозиторий, ни на VPS.**
> Сервер только раздаёт файлы — подписывать ему нечем и не нужно.
> Потеря приватного ключа = невозможность выпускать обновления для уже
> установленных клиентов: они проверяют подпись старым pubkey и новый
> инсталлятор отвергнут. Лечится только ротацией (§7) — то есть заранее,
> пока старый ключ ещё есть. **Сделайте резервную копию ключа офлайн.**

### 1.2. Секреты и переменные GitHub

`Settings → Environments → New environment → desktop-release`, в него:

| Секрет | Значение |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | **содержимое** файла `~/.tauri/leadchat.key` целиком |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | парольная фраза от него |
| `DEPLOY_SSH_KEY` | приватный ssh-ключ пользователя `deploy` на VPS |
| `DEPLOY_SSH_KNOWN_HOSTS` | (желательно) вывод `ssh-keyscan -H <домен>` |
| `VPS_HOST` | (опц.) хост, если он не `chat.partner-lead-centre.ru` |
| `VPS_USER` | (опц.) пользователь, если он не `deploy` |

`Settings → Secrets and variables → Actions → Variables`:

| Переменная | Значение |
|---|---|
| `DESKTOP_PUBLIC_BASE_URL` | (опц.) публичный origin, если он не `https://chat.partner-lead-centre.ru` |

`DEPLOY_SSH_KNOWN_HOSTS` не обязателен, но без него workflow доверяет
`ssh-keyscan` при каждом запуске (TOFU) и пишет об этом warning — окно для
MITM в момент выкладки. Заполните:

```bash
ssh-keyscan -H chat.partner-lead-centre.ru
# весь вывод целиком -> в секрет
```

### 1.3. Каталог на сервере

Создаётся при первичной подготовке VPS (05 §1), проверить:

```bash
ssh deploy@chat.partner-lead-centre.ru \
  'ls -ld /var/leadchat/download && touch /var/leadchat/download/.w && rm /var/leadchat/download/.w && echo WRITABLE'
```

Каталог монтируется в контейнер nginx **только на чтение** — писать в него
может лишь пользователь `deploy` по ssh. Права на файлы `644`, их выставляет
`deploy/publish-desktop.sh`.

## 2. Поднять версию

Версия десктопа живёт в **трёх** файлах, и CI не даст собрать релиз, если они
разошлись между собой или с тегом. Источник истины — `tauri.conf.json`,
остальные обязаны совпадать с ним **точь-в-точь**.

| # | Файл | Поле |
|---|---|---|
| 1 | `desktop/src-tauri/tauri.conf.json` | `"version": "1.4.2"` ← источник истины |
| 2 | `desktop/package.json` | `"version": "1.4.2"` |
| 3 | `desktop/src-tauri/Cargo.toml` | `[package]` → `version = "1.4.2"` |
| 4 | `desktop/src-tauri/Cargo.lock` | обновляется сам — **но его нужно закоммитить** |

```bash
# 1–3 руками, затем:
cd desktop/src-tauri && cargo check   # перепишет version в Cargo.lock
cd ../.. && git add desktop && git commit -m "desktop: 1.4.2"
```

Чего **не** трогаем:

- `frontend/package.json` — это версия веб-приложения, у неё свой цикл
  релизов (тег `v*`). Десктоп — обёртка над тем же бандлом, своей версии
  фронта у него нет.
- имена файлов инсталляторов — их формирует Tauri из `productName` и
  `version`, руками ничего переименовывать не нужно.

Версионирование — semver: патч для исправлений, минор для новых
возможностей. Тег всегда `desktop-v<version>`.

## 3. Выпуск тегом

```bash
git switch main && git pull
# версия поднята и смержена (см. §2)
git tag -a desktop-v1.4.2 -m "Быстрый ответ из уведомления; починен бейдж непрочитанных"
git push origin desktop-v1.4.2
```

Текст аннотации тега попадает в `notes` манифеста — это ровно то, что
оператор увидит в баннере «Доступна версия 1.4.2». Пишите его для оператора,
а не для разработчика.

Дальше `.github/workflows/desktop-release.yml` делает сам:

| Job | Где | Что |
|---|---|---|
| `build` | windows-latest | проверка версий → `npm ci` → `tauri build` (NSIS + MSI, подпись minisign) → `latest.json` → артефакт |
| `publish-vps` | ubuntu-latest | `deploy/publish-desktop.sh` → выкладка в `/var/leadchat/download` |
| `publish-github` | ubuntu-latest | GitHub Release с теми же файлами (архив для отката) |

Порядок внутри выкладки жёсткий и важный: **бинарники → симлинк → манифест**.
Манифест публикуется последним и атомарным `mv`, поэтому клиент никогда не
увидит `latest.json`, ссылающийся на ещё не выложенный файл.

Ручной запуск (`Actions → desktop-release → Run workflow`) собирает и
подписывает, но **не публикует** — это способ проверить, что сборка жива, не
выпуская релиз.

Время: ~15 минут от пуша тега до баннера у клиентов.

## 4. Проверка, что клиенты увидели обновление

### 4.1. Сервер (сразу после выкладки)

```bash
DOMAIN=chat.partner-lead-centre.ru

# 1. манифест отдаётся и в нём новая версия
curl -s https://$DOMAIN/download/latest.json | jq '.version, .notes, .platforms."windows-x86_64".url'

# 2. файл из манифеста реально скачивается (200, а не 404)
curl -sI "$(curl -s https://$DOMAIN/download/latest.json | jq -r '.platforms."windows-x86_64".url')" | head -1

# 3. кнопка «Скачать» на /login ведёт на свежий инсталлятор
curl -sI https://$DOMAIN/download | head -1              # 302
curl -sI https://$DOMAIN/download/LeadChat-Setup.exe | head -1   # 200

# 4. манифест не закэширован
curl -sI https://$DOMAIN/download/latest.json | grep -i cache-control   # no-cache
```

`publish-desktop.sh` делает эти проверки сам и краснеет, если что-то не так, —
руками они нужны только при разборе инцидента.

### 4.2. Клиент

- Приложение проверяет обновление **через 30 секунд после старта** и дальше
  **каждые 4 часа** (04 §6.3). Чтобы не ждать — перезапустите приложение.
- Появляется баннер «Доступна версия 1.4.2 — Перезапустить». Обновление
  **никогда не ставится без клика**: у оператора может быть открыт недописанный
  ответ.
- После установки: `/settings/profile` → «О приложении» → новая версия.
- Приёмочная проверка подписи (04 §10): подменить `signature` в `latest.json`
  на мусор → клиент обязан **отвергнуть** обновление. Делать это только с
  копией под рукой, `latest.json.prev` для возврата не годится — там манифест
  ПРЕДЫДУЩЕГО релиза:

  ```bash
  ssh deploy@$DOMAIN 'cd /var/leadchat/download && cp -p latest.json latest.json.bak'
  # …подменить signature, проверить на клиенте, затем вернуть:
  ssh deploy@$DOMAIN 'cd /var/leadchat/download && mv latest.json.bak latest.json'
  ```

### 4.3. Чек-лист релиза

- [ ] `latest.json` отдаёт новую версию, `notes` читаемы для оператора
- [ ] URL из манифеста отвечает 200
- [ ] `/download` → 302 → `LeadChat-Setup.exe` → 200
- [ ] На тестовой машине баннер появился, обновление встало, версия новая
- [ ] Старые версии в `/var/leadchat/download` не удалены (нужны для отката)
- [ ] GitHub Release создан, в нём `.exe`, `.msi`, `.sig`, `latest.json`

## 5. Откат релиза

**Главное, что нужно понимать:** апдейтер Tauri предлагает только **более
новые** версии. Откат манифеста на предыдущую версию **останавливает
раскатку**, но не откатывает тех, кто уже обновился. Их лечит только релиз
вперёд (fix-forward) или ручная переустановка.

### 5.1. Остановить раскатку (30 секунд)

`publish-desktop.sh` перед подстановкой сохраняет предыдущий манифест
в `latest.json.prev`, поэтому откат — одна команда:

```bash
ssh deploy@chat.partner-lead-centre.ru \
  'cd /var/leadchat/download && mv latest.json.prev latest.json'

# проверить
curl -s https://chat.partner-lead-centre.ru/download/latest.json | jq .version
```

`latest.json` отдаётся с `Cache-Control: no-cache`, поэтому клиенты видят
откат сразу — ждать истечения кэша не нужно.

### 5.2. Вернуть кнопку «Скачать» на старый инсталлятор

Старые версии с сервера **не удаляются** — именно ради этого:

```bash
ssh deploy@chat.partner-lead-centre.ru '
  cd /var/leadchat/download
  ls -t *-setup.exe                       # выбрать предыдущую версию
  ln -sfn LeadChat_1.4.1_x64-setup.exe .LeadChat-Setup.exe.new
  mv -T .LeadChat-Setup.exe.new LeadChat-Setup.exe
  ls -l LeadChat-Setup.exe'
```

### 5.3. Дальше

- Тем, кто уже обновился, — переустановка с
  `https://<домен>/download/LeadChat_1.4.1_x64-setup.exe` (NSIS ставится
  поверх, кэш и outbox в `%LOCALAPPDATA%` не трогаются).
- GitHub Release битой версии — пометить `pre-release` (не удалять: артефакты
  ещё нужны для разбора).
- Починить, поднять версию (§2), выпустить `desktop-v1.4.3`. Версию сломанного
  релиза **не переиспользуем**: клиенты, успевшие обновиться, сравнивают
  версии по номеру и «то же самое» не поставят.
- Битый бинарник с сервера **не удаляем**: манифест на него больше не
  ссылается, а вот у кого-то он может быть в процессе скачивания.

### 5.4. Полный откат к «как было» вручную

Если `latest.json.prev` не сохранился (первый релиз, чужая выкладка) —
опубликуйте предыдущий релиз ещё раз тем же скриптом из его артефактов
(GitHub Release или локальная копия):

```bash
bash deploy/publish-desktop.sh ~/releases/leadchat-1.4.1/
```

Пересобирать и переподписывать при этом **не нужно** — артефакты и подписи
уже готовы, скрипт просто выложит их заново.

## 6. Релиз без GitHub-репозитория

Если репозитория на GitHub нет (или CI недоступен), релиз собирается на
**локальной Windows-машине** и выкладывается тем же `publish-desktop.sh` —
это ровно тот же код, который вызывает CI, поэтому результат идентичен.

### 6.1. Что нужно на машине сборки (один раз)

- [ ] Windows 10/11 x64
- [ ] [Node.js 20 LTS](https://nodejs.org)
- [ ] [Rust](https://rustup.rs) — toolchain `stable-x86_64-pc-windows-msvc`
- [ ] **Visual Studio Build Tools 2022** с рабочей нагрузкой «Разработка
      классических приложений на C++» (без неё Rust не слинкует бинарник)
- [ ] Git for Windows — из него нужен **git-bash**, в нём запускается
      `publish-desktop.sh`
- [ ] Приватный ключ minisign в `~/.tauri/leadchat.key` и парольная фраза
- [ ] ssh-ключ пользователя `deploy`, проверенный `ssh deploy@<домен> true`

WebView2 на Windows 10/11 уже есть; на голой машине его дотянет бутстраппер
из инсталлятора.

### 6.2. Сборка (PowerShell)

```powershell
git pull
npm ci --prefix frontend
npm ci --prefix desktop

$env:VITE_API_BASE  = "https://chat.partner-lead-centre.ru"
$env:VITE_IS_DESKTOP = "1"
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content $HOME\.tauri\leadchat.key -Raw
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = Read-Host "парольная фраза"

cd desktop
npm run tauri -- build
cd ..
```

Готовые файлы — в `desktop/src-tauri/target/release/bundle/{nsis,msi}/`.
Рядом с `*-setup.exe` **обязан** появиться `*-setup.exe.sig`. Если его нет —
сборка прошла без ключа подписи, публиковать такое нельзя: клиенты обновление
не примут.

### 6.3. Собрать каталог артефактов и выложить (git-bash)

```bash
BUNDLE=desktop/src-tauri/target/release/bundle
rm -rf dist-release && mkdir -p dist-release
cp "$BUNDLE"/nsis/*-setup.exe "$BUNDLE"/nsis/*-setup.exe.sig dist-release/
cp "$BUNDLE"/msi/*.msi "$BUNDLE"/msi/*.msi.sig dist-release/ 2>/dev/null || true

# манифест (запускать из корня репозитория)
RELEASE_NOTES="Быстрый ответ из уведомления" node desktop/scripts/make-latest-json.mjs
# если домен не боевой — добавьте базу ссылок (обязательно https и со слэшем):
#   DOWNLOAD_BASE_URL="https://stend.example/download/" node desktop/scripts/make-latest-json.mjs

# выкладка: спросит подтверждение, потом сама проверит результат снаружи
bash deploy/publish-desktop.sh dist-release
```

Скрипт откажется публиковать, если: нет `.sig`, в каталоге больше одного
`*-setup.exe`, `latest.json` не совпадает с артефактами (версия, имя файла,
подпись) или файл долетел до сервера не целиком.

Полезные опции:

```bash
bash deploy/publish-desktop.sh --dry-run dist-release          # показать план
bash deploy/publish-desktop.sh --host 1.2.3.4 dist-release     # другой сервер
bash deploy/publish-desktop.sh --yes --skip-verify dist-release # без вопросов и проверки
bash deploy/publish-desktop.sh --help
```

### 6.4. Что при этом теряется и чем компенсировать

| Даёт CI | Без CI |
|---|---|
| проверка версий в 3 файлах | сверить руками по §2 |
| воспроизводимая среда сборки | одна выделенная машина сборки, не «чей-то ноут» |
| GitHub Release как архив артефактов | **складывать `dist-release` каждого релиза** в отдельную папку/облако — без них не откатиться (§5.4) |
| история релизов | всё равно ставить git-тег: `git tag -a desktop-v1.4.2 -m "…"` |

## 7. Ротация ключа подписи

Клиент проверяет подпись **зашитым в него** публичным ключом, поэтому нельзя
просто поменять ключ: уже установленные приложения перестанут принимать
обновления. Порядок — в два релиза:

1. Сгенерировать новую пару (§1.1), **старую не удалять**.
2. **Релиз N**: в `tauri.conf.json` прописать **новый** pubkey, а подписать
   релиз **старым** приватным ключом (секреты пока старые). Клиенты проверяют
   его старым ключом, ставят — и с этого момента у них внутри новый pubkey.
3. Дождаться, пока обновятся все. Версию каждый видит у себя в
   `/settings/profile` → «О приложении»; централизованного списка версий
   по машинам нет, поэтому — пройтись по сотрудникам и убедиться, что
   отставших не осталось. Это самый долгий шаг ротации, закладывайте неделю.
4. Заменить секреты `TAURI_SIGNING_PRIVATE_KEY` / `…_PASSWORD` на новые.
5. **Релиз N+1** подписывается уже новым ключом. Старый — в архив.

Тот же порядок при компрометации приватного ключа, только быстрее и с
обязательным обходом всех машин: до шага 5 подменённое обновление технически
возможно.

## 8. Что и как раздаёт nginx

Конфиг — `docker/nginx/templates/leadchat.conf.template`, блок `/download`.
Каталог `/var/leadchat/download` смонтирован в контейнер **только на чтение**.

| Запрос | Ответ | Cache-Control | Content-Type |
|---|---|---|---|
| `/download` и `/download/` | 302 → `LeadChat-Setup.exe` | — | — |
| `LeadChat-Setup.exe` (симлинк) | 200 | `no-cache` | `application/octet-stream` + `Content-Disposition: attachment` |
| `LeadChat_1.4.2_*.exe` / `*.msi` | 200 | `public, max-age=3600` | `application/octet-stream` + `attachment` |
| `*.sig` | 200 | `public, max-age=3600` | `text/plain; charset=utf-8` |
| `latest.json` | 200 | `no-cache` | `application/json` |
| что-либо ещё в каталоге | **404** | — | — |

Почему так:

- **`LeadChat-Setup.exe` — `no-cache`**, хотя это и бинарник: это симлинк,
  его цель меняется каждым релизом. Кэшируйся он на час — сотрудник скачал бы
  «свежий» инсталлятор прошлой версии. Тело при этом не перекачивается:
  не изменился — 304 по ETag.
- **Версионированные файлы — час.** Имя содержит версию, содержимое по нему не
  меняется; час — намеренный потолок, чтобы в первые минуты после релиза можно
  было перезалить артефакт.
- **`latest.json` — `no-cache`**, иначе откат (§5.1) не подействовал бы
  мгновенно.
- **Всё остальное — 404.** Список расширений — это allowlist: случайно
  оказавшийся в каталоге файл (черновик, ключ, лог) не станет публичным
  из-за того, что мы не догадались его запретить. Листинга каталога нет
  (`autoindex off`), подкаталоги не раздаются.

Диапазонные запросы (`Range`) работают — апдейтер умеет докачивать.

## 9. Траблшутинг

| Симптом | Причина | Что делать |
|---|---|---|
| CI: `tauri.conf.json version=X != tag Y` | подняли версию не везде | §2, все 4 пункта, включая `Cargo.lock` |
| CI: `секрет TAURI_SIGNING_PRIVATE_KEY пуст` | секрет не заведён в environment `desktop-release` | §1.2 |
| CI: `нет …-setup.exe.sig` | `bundle.createUpdaterArtifacts` не `true` либо ключ не доехал | проверить `tauri.conf.json` и секреты |
| CI: `npm ci` падает на `desktop` | нет `desktop/package-lock.json` в git | закоммитить лок-файл |
| Скрипт: `нет подписи …sig` | сборка без ключа | пересобрать с `TAURI_SIGNING_PRIVATE_KEY` |
| Скрипт: `signature в манифесте не совпадает с .sig` | `latest.json` от другой сборки | перегенерировать `make-latest-json.mjs` |
| Скрипт: `размер на сервере != локального` | оборвалась заливка | запустить скрипт заново, он идемпотентен |
| Клиент: «обновление не удалось», подпись | pubkey в конфиге не от того ключа | §7 |
| Клиент: баннера нет | версия в манифесте не больше установленной; либо ещё не прошёл интервал | сверить версии, перезапустить приложение |
| Клиент: 404 при скачивании обновления | манифест выложили раньше бинарника | перезапустить выкладку — правильный порядок в ней зашит |
| SmartScreen ругается на инсталлятор | нет EV-сертификата Authenticode (осознанно, 04 §6.2) | «Подробнее → Выполнить в любом случае»; вариант — раздать сертификат через GPO |
| `/download` отдаёт 404 | нет симлинка `LeadChat-Setup.exe` | §5.2 — переставить симлинк |
