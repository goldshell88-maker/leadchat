# Как слить две параллельные сессии 12 августа

Записка для второй сессии. Не про код — про то, где мы уже дважды столкнулись
и как не столкнуться в третий раз.

## Номера миграций заняты по 0037

    0034  индексы журнала аудита и имена CHECK
    0035  bots.ai_provider — чей мозг отвечает (claude | leadbot)
    0036  bots.mode — куда уходит ответ (suggest | auto)   ← вторая сессия
    0037  client_phone_candidates — телефон из текста сообщения
    0038  bots.is_system + leadbot_calls — лид-бот как отдельный раздел

**Следующий свободный — 0039.**

Мы уже дважды взяли один номер вдвоём. Цена не в переименовании: две ревизии с
одним номером дают ДВЕ ГОЛОВЫ, и `alembic upgrade head` отказывается работать
целиком — выкатка встаёт, а выглядит это как «миграции сломались».

Проверять так, ДО коммита:

    .venv/bin/python -m alembic heads     # обязана быть одна строка

Правило, если столкнулись: уступает тот, кто пришёл вторым. Переписывать
ревизию, уже лежащую в истории `main`, нельзя — она могла примениться.

## База разработки могла разъехаться со схемой

Один раз уже разъехалась: версия `0035` записалась от файла, который потом
переименовали, и колонка `ai_provider` не добавилась вовсе — при том что
`alembic` считал миграцию применённой. Такое не чинится накатом.

Пересобрать начисто (только для стенда разработки, боевую так не трогать):

    docker exec leadchat-dev-postgres-1 psql -U leadchat -d postgres \
        -tAc "DROP DATABASE IF EXISTS leadchat WITH (FORCE)"
    docker exec leadchat-dev-postgres-1 psql -U leadchat -d postgres \
        -tAc "CREATE DATABASE leadchat OWNER leadchat"
    .venv/bin/python -m alembic upgrade head

## Порядок слияния

Слить обе стороны в `main`, затем ОДИН раз прогнать целиком:

    .venv/bin/python -m alembic heads          # одна голова
    .venv/bin/python -m alembic upgrade head   # на пересобранной базе
    .venv/bin/python -m pytest tests/unit tests/integration -q
    .venv/bin/python -m ruff check app tests && .venv/bin/python -m mypy app
    cd frontend && npx tsc --noEmit && npx vitest run && npm run lint

Прогон каждой стороны у себя ничего не доказывает: оба падения, которые мы
поймали сегодня, появились ИМЕННО на стыке — поля `leadbot_url` и
`leadbot_token` приехали в `config.py` одной стороной, а в `.env.example` их
описала другая.

## Две ловушки стенда разработки на этой машине

Обе стоили сегодня по часу и обе выглядят как дефект продукта, которым не
являются. Проверяйте их ПЕРВЫМИ, если на стенде «не работает то, что работает
в тестах».

**1. Uvicorn на 8000 не перезапускается сам.** Он поднят без `--reload`.
Процесс, запущенный утром, отдаёт утренний код: ручка `/clients/{id}/identity`
молча приезжала без `phone_source` и `phone_candidates`, и это читалось как
«сервер не отдаёт кандидатов» — при том что код был написан и покрыт. Сверять
так:

    ps -o lstart= -p $(lsof -ti tcp:8000)     # когда поднят процесс
    git log -1 --format=%ad -S "искомое" -- путь/к/файлу.py

**2. На `localhost:6379` отвечает НЕ контейнерный Redis.** На хосте свой,
и `localhost` уходит к нему, а `docker exec leadchat-dev-redis-1 redis-cli`
пишет в другую базу. Видно по числу ключей: у приложения их больше тысячи, в
контейнере — полсотни. Отметки о подписке на вебхук, записанные через
`docker exec`, приложение не увидит вовсе. Писать надо клиентом приложения:

    .venv/bin/python -c "
    import asyncio, uuid
    from app.core.redis import init_client
    from app.services import avito_accounts
    asyncio.run(avito_accounts.set_webhook_state(
        init_client(), uuid.UUID('<id канала>'), 'ok', '<адрес>'))"

Мелочь оттуда же: у канала на стенде статус должен быть `active`. При
`connected` (значения такого нет) карточка молча прячет обе строки состояния —
условие показа в `AccountsPage.tsx` смотрит именно на `active`.


## ⚠ Редактор ботов изменился — это задевает вторую сессию

Решение владельца от 12 августа: «сам LeadBot это не совсем бот, я хочу чтобы у
него была своя собственная вкладка и настройки». Что из этого вышло:

* из `BotEditor.tsx` убран переключатель «Кто придумывает ответ» — выбора между
  нашим ИИ и лид-ботом у обычного бота больше нет;
* из `BotsPage.tsx` убран значок «Лид-бот» в строке списка;
* в `draftStore.ts` не стало `setAiProvider` (поле `aiProvider` осталось: оно
  едет в теле запроса и у обычного бота всегда `claude`);
* появился раздел `/settings/leadbot` и пункт меню после «Ботов».

Вторая сессия держит `BotEditor.tsx` и `BotsPage.tsx` — при слиянии эти четыре
места конфликтуют предсказуемо. Правильное разрешение: НАШУ сторону в части
поставщика (его там больше нет), ВАШУ — во всём остальном.

Сервер: все шесть ручек `/bots/{bot_id}` теперь отвечают 404 на системную
запись. Если ваш код ходит в них по идентификатору лид-бота — он получит «не
найден», и это намеренно: настраивается лид-бот своим разделом.
