# Каталог API Авито — сверка с нашим кодом

Разобрано 8 августа по просьбе «изучи https://www.avito.ru/developers/api-catalog».
Сам сайт закрыт для машинного чтения, поэтому взята официальная спецификация
OpenAPI (2 МБ, 238 путей) из открытого зеркала и разобрана локально.

## Что сверка ПОЙМАЛА

**1. Чтение сообщений чата шло по несуществующему пути.** У нас стояло
`/messenger/v2/accounts/{uid}/chats/{chat_id}/messages/`. В каталоге эндпоинта
v2 для сообщений НЕТ вовсе: есть `v1` на отправку и `v3` на чтение. На боевом
Авито это 404.

Сломалось бы на сверке пропущенных — то есть на механизме, который чинит
потерянные сообщения, — и молча: сверка ловит ошибки и идёт дальше.

Почему не всплыло раньше: встроенный имитатор отвечал по тому пути, который мы
у него же и спросили. **Имитатор, написанный по нашим догадкам, подтверждает
наши догадки.** Путь в имитаторе тоже исправлен.

**2. Истёкший токен Авито даёт 403, а не 401.** Наше авто-обновление висело
на 401, и 403 попадал в общую ветку ошибок: обновление не запускалось, и каждый
следующий запрос падал до планового обновления за два часа до истечения.
Отправка сообщений могла молча встать на часы.

Подтверждено двумя независимыми источниками, включая чужую рабочую интеграцию,
где ради этого заведена отдельная настройка `tokenExpiredStatusCode: 403`.

**3. `flow_id` — не вложение.** Поле объявлено в `MessageContent` наравне с
`image` и `voice`, но это строка: пометка «сообщение написал чат-бот Авито».
Наша нормализация превращала её во «Вложение (flow_id)» под каждым системным
сообщением.

## Что сверка ПОДТВЕРДИЛА

* права `messenger:read`, `messenger:write`, `user:read` — совпадают;
* `/core/v1/accounts/self`, `/token`, `/messenger/v3/webhook`,
  `/messenger/v1/webhook/unsubscribe`, `/messenger/v2/accounts/{uid}/chats` — верны;
* формы вложений угаданы точно: `image.sizes` — словарь «ШxВ → адрес»,
  `voice.voice_id`, `call.status`, `location.lat/lon/kind`, `link.preview`,
  `item.item_url`. Закреплено тестом по каталогу.

## Чего мы не используем, а стоило бы

| Метод | Зачем нам |
|---|---|
| `POST /messenger/v1/accounts/{uid}/chats/{chat_id}/read` | Отметка «прочитано» обратно в Авито. В самой спецификации сказано прямо: чтение сообщений НЕ помечает чат прочитанным, для этого есть отдельный метод. Без него у владельца в мобильном Авито растёт счётчик, который никогда не гаснет |
| `GET /messenger/v1/accounts/{uid}/getVoiceFiles` | Ссылки на голосовые. Сейчас голосовое показывается строкой без возможности послушать |
| `POST /messenger/v1/accounts/{uid}/uploadImages` + `.../messages/image` | Отправка фотографии оператором (#30). Ограничение платформы: отправлять можно ИЗОБРАЖЕНИЯ, отдельного метода для произвольного файла в каталоге нет |
| `GET/POST /messenger/v2/accounts/{uid}/blacklist` | У нас чёрный список свой, локальный. Авито умеет блокировать на своей стороне — тогда клиент не сможет написать вовсе |
| `DELETE /messenger/v1/accounts/{uid}/chats/{chat_id}/messages/{message_id}` | Удаление отправленного сообщения |
| ~~`GET /messenger/v1/subscriptions`~~ | **СДЕЛАНО (#39).** Проверить, какие подписки на вебхук стоят у аккаунта СЕЙЧАС — прямой ответ на вопрос «перебили ли мы подписку Jivo». Ручка `GET /api/v1/avito-accounts/{id}/subscriptions`, право `accounts:manage`. **Глагол в этой строке и в таблице ниже расходился: здесь GET, в таблице из спецификации POST — и имитатор реализовал наш GET, то есть подтвердил нашу же догадку.** Клиент пробует POST (спецификация) и на 404/405 переходит к GET; имитатор отвечает на оба. **9 августа проверено на боевом Авито: POST отвечает 200, спецификация права.** Ответ на сам вопрос — в `docs/24 §2`: Авито держит на аккаунт ОДНУ подписку, наша заменяет чужую |

## Приложение: какие формы содержимого приходят на самом деле (замер 07.09)

Таблица собрана по `webhook_raw_log` за 30 дней и по ответам
`GET /messenger/v3/.../messages/`. Она нужна, чтобы следующий раз не начинался с
вопроса «а можно ли дотянуть файл» — ответ уже получен, и получен трижды.

| Вид сообщения (`value.type`) | Что лежит в `content` | Можно ли получить файл |
|---|---|---|
| `text` | `text` | — |
| `image` | `sizes` — словарь «ШxВ → адрес», 4 ссылки | да, ссылка прямо в сообщении |
| `voice` | `voice_id` | да, отдельным методом `GET /messenger/v1/accounts/{uid}/getVoiceFiles` |
| `video` | пустой объект `{}` — **130 из 130** | **нет** |
| `file` | пустой объект `{}` — **22 из 22** | **нет** |
| `appCall` | пустой объект `{}` | файла и не бывает: это событие звонка |

**Почему «нет» — это вывод, а не усталость.** Проверено три раза разными
способами:

1. сырцы вебхуков за 30 дней: у всех 152 сообщений видов `video` и `file` поле
   `content` — пустой объект. Ни ссылки, ни идентификатора, ни имени, ни размера;
2. чтение переписки той же парой сообщений отдаёт тот же пустой `content` —
   значит вебхук ничего не «недосказал»;
3. шесть угаданных путей (`getFiles`, `getVideoFiles`, `getFile`, `files`,
   `getVideos`, тот же `getVoiceFiles` в версии `v2`) отвечают 404 «page not
   found». Контрольный `getVoiceFiles` на том же токене отвечает 400 — то есть
   путь существует и токен рабочий, а 404 у остальных означает «такого метода
   нет», а не «нет прав».

**Что из этого следует для кода.** Показать видео и файл нельзя ничем, кроме
приложения Авито, и система обязана говорить это прямо. Подписи лежат в
`_CONTENT_FREE_KINDS` (`app/integrations/avito/adapter.py`) и с 07.09 едут не в
теле сообщения, а вложением без ссылки: в теле они выглядели словами клиента.
