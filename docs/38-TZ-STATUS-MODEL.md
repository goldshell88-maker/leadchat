## Как устроено сейчас

### 9.1 Серверная модель: три значения и ни одного ограничения в базе

`app/models/conversation.py:40-42`:

```python
status: Mapped[str] = mapped_column(
    Text, nullable=False, default="new"
)  # new | in_progress | closed
```

Комментарий — единственное место, где записан состав словаря на уровне модели. **В базе ограничения нет:** в `app/db/migrations/versions/0001_init.py:132` колонка объявлена как `sa.Column("status", sa.Text(), server_default=sa.text("'new'"), nullable=False)`, никакого `CheckConstraint`. Грep по всем миграциям и моделям даёт `CHECK` только у `notifications` (`app/models/notification.py:55-60`) и у `users.role` (`app/models/user.py:16`). То есть в колонку `conversations.status` физически можно записать что угодно; от мусора её охраняет только Python.

Проверок в Python три, и они независимы друг от друга:

| Где | Что | Строка |
|---|---|---|
| Сервис | `STATUSES: tuple[str, ...] = ("new", "in_progress", "closed")` | `app/services/conversations.py:42` |
| Схема запроса | `status: Literal["new", "in_progress", "closed"]` | `app/api/routes/conversations.py:69` |
| Фильтр списка | `Query(None, pattern="^(new\|in_progress\|closed)$")` | `app/api/routes/conversations.py:188` |

Ни одна из трёх не выведена из двух других. Добавление значения требует правки всех трёх — и ещё девяти мест, перечисленных ниже.

**Индексы по статусу есть и их два:** `ix_conversations_status_last_message` и `ix_conversations_assignee_status` (`app/db/migrations/versions/0002_inbound.py:73,77`). Новые значения их не ломают — это b-tree по значению, а не по перечислению.

**Цвета — три места, и все три ведут в одни токены (это единственное, что сейчас согласовано):**

* `frontend/src/features/chats/components/thread/chat-thread.css:141-153` — `.thread-status[data-status=…]`, три ветки, **мёртвый код**: грeп по `frontend/src` даёт `thread-status` только в CSS, ни одного TSX (это остаток убранного из шапки селекта, зафиксированный в описи `docs/28-AUDIT-STEP0-INVENTORY.md:1432`);
* токены `--lc-status-new-bg/-text`, `--lc-status-inprogress-*`, `--lc-status-closed-*` — `frontend/src/app/lc-vars.css:469-474` (тёмная) и `:647-652` (светлая). Синий / зелёный / серый.

**Бейджа статуса в списке чатов нет.** Атрибут `data-status={row.status}` на карточке строки стоит (`frontend/src/features/chats/components/list/ConversationListItem.tsx:127`), но грeп `data-status` по `chat-list.css` не даёт **ни одного** правила — атрибут не используется ничем.

**Четвёртое и пятое значения того же слова — в статистике.** Это уже разобрано в `docs/29-AUDIT-STEP1-SCREENS.md`, пункты STATS-01 (critical) и STATS-09 (major), повторять не буду; для полноты таблицы соответствия:

* карточка «**Ждут ответа**» = `count(*) FILTER (WHERE c.status = 'new')` (`app/services/stats.py:412` → `:642` `"waiting_now": card(snapshot["new_now"])`), а её собственная подсказка гласит «Диалоги в работе, где последнее сообщение — от клиента» (`frontend/src/features/stats/components/SummaryCards.tsx:78`) — это другое множество;
* «**Ждут моего ответа**» в виджете оператора = `c.status='in_progress'` И последнее сообщение от клиента (`app/services/stats.py:1119-1131`);
* карточка «**В работе**» = `count(*) FILTER (WHERE c.status='in_progress')` (`app/services/stats.py:413`).

**Итог по подзадаче.** Слово «статус» в продукте означает четыре разные вещи: значение колонки, срез вкладки списка, метрику снимка и колонку отчёта; слово «ждёт» — три разные вещи; словарей подписей девять, и один из них (`stats.py`) вообще не переводит.

| 7 | `in_progress` | назначение ответственного | `app/services/conversations.py:1014` |

| 13 | любой из трёх | руками — `change_status` | `app/services/conversations.py:874` |

**Единственный запрещённый переход** — `closed → new` руками (`app/services/conversations.py:821-830`, ошибка 422 `manual_reopen_forbidden`). Всё остальное разрешено: `new → closed`, `closed → in_progress`, `in_progress → new` — любой в любой, кроме одного.

Второе ограничение — не переход, а тавтология: `previous == new_status` даёт 422 `same_status` (`app/services/conversations.py:815-820`).

Третье — `outcome` разрешён только при закрытии (`:849-856`), а сумма — только у исхода `visit` (`:857-865`).

Матрицы переходов как объекта в коде **нет**: проверки написаны двумя `if`-ами подряд.

### 9.4 Как связаны `status`, `assignee_id`, очередь, `awaiting_since` и `unread_count`

**`status` и `assignee_id` связаны, но не жёстко.** Назначение всегда ставит `in_progress`, снятие — `new` (`app/services/conversations.py:1014`). Но обратное неверно: `change_status(in_progress)` ставит ответственного **только если** его не было и актор умеет отвечать клиентам (`app/services/conversations.py:879-882`, `can_answer_clients`). Руководитель, переведя диалог в «В работе», оставляет его без ответственного — это закреплено тестом `tests/unit/test_rbac.py:498-521` и описано в `docs/28-AUDIT-STEP0-INVENTORY.md:913`. То есть **состояние «в работе, ответственного нет» законно и встречается.**

**Очередь ортогональна статусу — и это записано прямым текстом** в шапке модели, `app/models/conversation.py:64-71`: «Состояние „ждёт принятия“ выражено ПОЛЯМИ ОЧЕРЕДИ, а не пятым статусом… новое значение в нём означало бы правку каждого из них». Предикат очереди (`app/services/inbox.py:80-94`):

```python
Conversation.claimed_by_id.is_(None),
Conversation.assignee_id.is_(None),
Conversation.offered_at.is_not(None),
Conversation.status != CLOSED,
```

Статус тут участвует одним отрицанием. **Это прямо относится к настоящей задаче:** решение «не заводить пятый статус под очередь» было принято осознанно и обосновано; заказчик просит завести два новых значения по другому поводу, и в §1 ниже показано, почему в этот раз довод не работает против.

**`awaiting_since` — «клиент ждёт ответа с этого момента»** (`app/models/conversation.py:106-126`). Ставится на входящем, если поле пусто (`app/services/inbound.py:283-284`); снимается `clear_awaiting` (`app/services/inbox.py:188-193`) при ответе оператора, при закрытии и при возврате в очередь. **Наружу через API не отдаётся** — в `conversation_out` его нет (`app/services/conversations.py:165-262`). Фронт считает ожидание сам, двумя разными способами:

* шапка ленты — по направлению последнего видимого сообщения, `frontend/src/features/chats/components/thread/ChatThreadPane.tsx:159-170`;
* строка списка — по `unread_count > 0`, `frontend/src/shared/lib/waiting.ts:67-72` через `ConversationListItem.tsx:94`.

Ни один из двух не смотрит на статус — это подтверждённый дефект №3 из `docs/33-AUDIT-STEP2-DEFECTS.md:122-131`.

**`unread_count`** — счётчик на диалоге (`app/models/conversation.py:52-54`), растёт на входящем, обнуляется `POST /conversations/{id}/read`. **Закрытие его не трогает:** `change_status` вызывает `clear_auto_assignment` и, при закрытии, `clear_awaiting` — и всё (`app/services/conversations.py:875-880`). Поэтому закрытый диалог с непрочитанным продолжает показывать чип ожидания (тот же дефект №3).

**Осторожно с названием.** Заказчик просит значение «**Ждёт клиента**» — то есть ход за клиентом. Поле `awaiting_since` означает **ровно обратное**: клиент ждёт нас. А карточка статистики «Ждут ответа» означает третье — диалоги в очереди. Три «ожидания» в одном продукте уже есть; четвёртое обязано быть названо так, чтобы не слиться с ними (см. §1).

### 9.5 Что сломается в статистике при добавлении значений

**Витрину `mv_conversation_stats` перестраивать НЕ надо, и это проверено.** Колонка `status` в неё входит (`app/db/migrations/versions/0004_stats_indexes_and_mv.py:112,121` — `b.status`), но ни один фильтр витрины по значениям статуса не идёт: `_F_MV` (`app/services/stats.py:304-308`) и `_F_CONV` (`:309-313`) сужают только по аккаунту и по менеджерам. `closed_at` берётся из журнала по `details->>'to' = 'closed'` (`0004_stats_indexes_and_mv.py:176`), а не по колонке, — новые значения его не задевают. Витрина обновляется раз в час в HH:05 (`app/scheduler/jobs/stats.py:98-102`).

**Сломается вот что** (каждый пункт — конкретный запрос):

1. **`app/services/stats.py:411-414`, `_SNAPSHOT_SQL`.** Считает ровно два значения:
   ```sql
   count(*) FILTER (WHERE c.status = 'new')         AS new_now,
   count(*) FILTER (WHERE c.status = 'in_progress') AS in_progress_now
   ```
   Диалог со статусом «Ждёт клиента» или «Отложен» не попадёт **ни в одну** карточку группы «Прямо сейчас». Руководитель увидит, что открытых диалогов стало меньше, хотя их столько же. Это самая дорогая поломка: по этой цифре решают, звать ли смену.
2. **`app/services/stats.py:1131`, виджет «моя статистика за сегодня»** — `WHERE c.assignee_id = :user_id AND c.status = 'in_progress'`. Из «Мои активные» и «Ждут моего ответа» пропадут отложенные и ждущие клиента диалоги оператора. При этом именно у оператора их будет больше всего — он их сам и наставил.
3. **`app/services/distribution.py:70`, `OPEN_STATUSES = ("new", "in_progress")`** — нагрузка для автораспределения. Оператор с двадцатью отложенными диалогами будет считаться незанятым, и система выдаст ему ещё. Комментарий рядом («закрытый не занимает внимания оператора») после правки станет неверным, если его не переписать.
4. **`app/services/stats.py:1464` и `:1505`** — лист «Диалоги» печатает `status` как есть. Сегодня в отчёте владельца стоит `in_progress`; после правки встанут `waiting_client` и `snoozed`. Дефект уже описан как STATS-09 в `docs/29-AUDIT-STEP1-SCREENS.md:466`, но новые значения делают его заметнее, поэтому чинится в этой же задаче.
5. **`app/services/conversations.py:358-369`, вкладки списка.** `all` = `status != "closed"`, `new` = `status == "new"`. Новые значения молча попадут во «Все» и не попадут ни в один именованный срез. Само по себе это верно, но фильтр «Статус» их не покажет, пока не расширен `STATUS_OPTIONS`.
6. **`app/api/routes/conversations.py:188`** — регулярка фильтра отвергнет новые значения с 400 до того, как их кто-то успеет выбрать.
7. **`app/bots/runtime.py:137`** — `if conv.status != "new": return False`. Бот входит только в свежий диалог. Новые значения этого не меняют, но правило надо перечитать осознанно: бот НЕ должен просыпаться в отложенном диалоге.

Отдельно: **отдельного отчёта по статусам сегодня нет ни на одном экране.** Ни `GET /stats/summary`, ни экспорт не дают разбивки «сколько сейчас в каком статусе»; есть только две карточки из пункта 1.

### 9.6 Что есть в WebSocket и как фронт это принимает

Сервер публикует ровно один тип кадра про изменение диалога — `conversation:updated`, состав `{conversation_id, patch}`. Публикуют его девять мест: `app/api/routes/conversations.py:173` (общий `_publish_change`), `:529`, `:560`, `:639`, `:755`; `app/api/routes/inbox.py:199`, `:274`, `:327`, `:401`; `app/services/messages.py:725`; `app/services/client_enrich.py:144`; `app/scheduler/jobs/reclaim.py:102,281`; `app/bots/engine.py:555,566,693`; `app/bots/handoff.py:297`.

Состав патча при смене статуса — три поля, `app/api/routes/conversations.py:100-118`:

```python
return {"status": detail["status"], "assignee": detail["assignee"], "in_inbox": detail["in_inbox"]}
```

Фронт принимает это в `frontend/src/shared/realtime/applyWsEvent.ts:580-582` → `applyConversationPatch` (`:168-186`), который:
* патчит деталь диалога (`qk.conversations.detail`) через `mergeConversationPatch` (`:59-73`) — плоские ключи копируются как есть, поэтому **новые поля патча доедут без единой правки клиента**;
* патчит строку во всех закэшированных вариантах списка (`:173`);
* кладёт статус в стор непрочитанных (`:177-180`);
* при изменении `status` или `assignee` инвалидирует корень `qk.conversations` (`:183-185`) — то есть вкладки пересчитываются сервером.

**Вывод по WS: канал и клиентская сторона готовы.** Новых типов событий не нужно; нужно расширить состав патча и добавить один тост на проигрыш гонки.

Гонка «двое взяли одновременно» **уже решена** для пути очереди — `app/services/inbox.py:653-698`: один `UPDATE … WHERE claimed_by_id IS NULL AND assignee_id IS NULL AND status <> 'closed'` с проверкой `rowcount`, один повтор при освобождении между попытками, и разбор отказа в `_raise_not_claimable` (`:559-593`) — проигравший получает **409 `already_claimed` с именем победителя**. Важное свойство, записанное в докстринге `claim` (`:631-636`) и подтверждённое кодом: `offered_at IS NOT NULL` в условие захвата **не входит**, то есть ручка работает и для диалога, который в очереди никогда не стоял.

А вот путь `PATCH /conversations/{id}/status` гонку решает хуже: `get_conversation_for_update` берёт строчный лок (`app/services/conversations.py:623-636`), второй запрос дождётся коммита первого, увидит уже `in_progress` и получит **422 «Диалог уже в этом статусе»** — сообщение верное по букве и бесполезное по смыслу: оператор не узнает, что диалог забрал коллега.

### 9.7 Механизма отложенного возврата НЕТ

Проверено грепом по `app/` и `frontend/src`: ни `snooze`, ни `postpone`, ни `remind_at`, ни колонки под срок — ничего. Единственные вхождения слова «отложенн» относятся к таймаутам бота и к баннеру обновления десктопа.

**Что есть и годится в фундамент:**

* **ARQ с задержкой умеет** — `_defer_by` используется ровно в одном месте, `app/bots/runtime.py:230-236` (дедлайны шагов `ask`/`menu`). Значит инфраструктура проверена боем.
* **Ежеминутный сторож на APScheduler — тоже есть, и их два:** `app/scheduler/jobs/awaiting.py:279-281` (`IntervalTrigger(minutes=1)`) и `app/scheduler/jobs/reclaim.py:296,300-301`. Оба зарегистрированы в `app/scheduler/main.py:158-168`.
* Адресные уведомления оператору уже устроены — вид `conversation.awaiting_you` в каталоге `app/services/notifications.py:266-272` (`audience=None`, получатель — ответственный).

**Какой путь выбрать — важно и не очевидно.** ARQ `_defer_by` для срока «до завтра 10:00» не годится: задача с отложенным запуском живёт в Redis, и перезапуск Redis без persistence её теряет; кроме того, отменить отложенное («снять отложку») в ARQ можно только зная `job_id`, а срок можно менять. Сторож раз в минуту по индексированной колонке `snoozed_until` переживает перезапуск чего угодно, потому что правда лежит в базе. Берём сторож — по образцу `awaiting.py`, который уже решает ровно эту задачу «раз в минуту посмотреть на колонку с датой».

Поэтому «Отложен» вынесен **отдельной задачей** с отдельной оценкой (§7), как и просил заказчик.

### §0. Главный принцип

**Словарь статусов становится ОДНИМ объектом в двух файлах — по одному на сторону, — и все девять нынешних копий его импортируют.** Ни в одном другом месте продукта не должно остаться литерала `"in_progress"` и подписи «В работе». ### §2. Схема БД — миграция `0026_conversation_status_model`

```sql
-- 1. Ограничение на словарь. Сегодня его нет вовсе: в колонку писали
--    тринадцать мест, и ни одно не проверялось базой.
ALTER TABLE conversations
    ADD CONSTRAINT ck_conversations_status
    CHECK (status IN ('new','in_progress','waiting_client','snoozed','closed'));

-- 2. Когда диалог вошёл в НЫНЕШНИЙ статус. Нужно строке контекста
--    «В работе у Иванова · 12 мин».
ALTER TABLE conversations ADD COLUMN status_since timestamptz;

-- 3. Отложка (задача §7; колонки заводятся сразу, чтобы не делать вторую
--    миграцию через неделю — ALTER на этой таблице стоит дороже колонки).
ALTER TABLE conversations
    ADD COLUMN snoozed_until  timestamptz,
    ADD COLUMN snoozed_by_id  uuid REFERENCES users(id),
    ADD COLUMN snooze_reason  text;

-- Сторож §7 бежит раз в минуту по этому индексу и должен читать сотни строк,
-- а не всю таблицу.
CREATE INDEX ix_conversations_snoozed_until
    ON conversations (snoozed_until) WHERE snoozed_until IS NOT NULL;
```

**`status_since` — обязательная колонка, и вот почему её нельзя заменить `updated_at`.** В шапке модели написано прямо (`app/models/conversation.py:56`): «Any row change (ORM onupdate)». `updated_at` двигает любое сообщение, любая заметка, любое обогащение карточки клиента. Строка «В работе у Иванова · 12 мин», построенная на нём, показывала бы время с последнего сообщения — то есть совсем другую величину, и показывала бы правдоподобно. Это ровно та ошибка, которой в этом проекте уже шесть штук за два дня.

**Заполнение при миграции:** `UPDATE conversations SET status_since = COALESCE(last_message_at, updated_at) WHERE status_since IS NULL` — одним запросом, внутри миграции, потому что он не ходит в сеть, детерминирован и на нынешнем объёме (десятки тысяч строк) занимает доли секунды. Это заведомо приблизительно, и так и написано в шапке миграции: точное время входа в статус за прошлое не восстановимо ниоткуда, журнал `audit_log` хранит смены (`conversation.status_changed`), но не для всех строк — автопереходы до 7 августа в нём есть не всегда. Приблизительное значение честнее NULL: интерфейс не должен показывать прочерк там, где у 100 % диалогов будет число через сутки работы.

**Именование.** В проекте жёсткий `naming_convention` (`app/models/base.py`): `ck_%(table_name)s_%(constraint_name)s`, `ix_%(column_0_label)s`, `fk_…`. Все имена в миграции выписываются явно, иначе метаданные моделей разъедутся с базой.

**Портируемость на SQLite.** Юнит-тесты строят схему из моделей (`tests/unit/conftest.py:35` — `Base.metadata.create_all`, движок `sqlite+aiosqlite://`). Значит `CheckConstraint` объявляется В МОДЕЛИ — прецедент уже есть и работает: `app/models/user.py:16`, `CheckConstraint("role IN ('admin','head','manager','observer')", name="users_role")`. Частичный индекс — через `postgresql_where`.

**Порядок и риск.** `ADD CONSTRAINT … CHECK` без `NOT VALID` сканирует таблицу под `ACCESS EXCLUSIVE`, а в `conversations` непрерывно пишет inbound-конвейер. На нынешнем объёме это доли секунды — так и написать в шапке, вместе с указанием: **если запрос из unknown №4 покажет сотни тысяч строк, разбить на `ADD CONSTRAINT … NOT VALID` + `VALIDATE CONSTRAINT` двумя транзакциями.** И обязательно — сначала запрос из unknown №5: `CHECK` упадёт на первом же неизвестном значении.

**Downgrade** полный: `DROP CONSTRAINT`, четыре `DROP COLUMN`, `DROP INDEX`. Обратим **до первого перевода диалога в новый статус**; после отката такие строки останутся со значением, которого код уже не знает. Поэтому downgrade обязан сначала выполнить `UPDATE conversations SET status='in_progress' WHERE status IN ('waiting_client','snoozed')` — и это написано в шапке миграции прямым текстом, а не подразумевается.

**Тест обратимости обязателен:** `upgrade → downgrade → upgrade` для 0026 на настоящем PostgreSQL. Сегодня интеграционные тесты гоняют только `alembic upgrade head` (`tests/integration/conftest.py:61-77`), то есть ни один downgrade в проекте не проверен ни разу.

### §3. Матрица переходов

Объектом, а не двумя `if`-ами. `app/services/conversation_status.py`:

```
TRANSITIONS = {
  'new':            {'in_progress', 'closed'},
  'in_progress':    {'new', 'waiting_client', 'snoozed', 'closed'},
  'waiting_client': {'in_progress', 'snoozed', 'closed'},
  'snoozed':        {'in_progress', 'waiting_client', 'closed'},
  'closed':         {'in_progress'},          # 'new' — только системой
}
```

Запреты и их причины — каждый со своим `reason`, потому что «нельзя» без объяснения оператор читает как поломку:

| Переход | Ответ | Почему |
|---|---|---|
| `new → waiting_client` | 422 `no_reply_yet` | Клиенту ещё никто не ответил — ждать ему нечего. Проверяется не только статусом: диалог обязан иметь хотя бы одно исходящее оператора (тот же предикат, что в витрине, `has_operator_reply`). |
| `new → snoozed` | 422 `snooze_requires_owner`, если `is_waiting(conv)` | Отложить диалог, стоящий в очереди, значит спрятать его от всех тринадцати. Отложить можно только то, что взял. |
| `closed → new` вручную | 422 `manual_reopen_forbidden` | Уже есть, `app/services/conversations.py:821-830`. Оставляем как есть. |
| `closed → waiting_client`, `closed → snoozed` | 422 `reopen_to_progress_only` | Закрытый возвращают в работу и решают дальше. Иначе «вернул и сразу отложил» прячет диалог мимо чьих-либо глаз. |
| `X → X` | 422 `same_status` | Уже есть, `:815-820`. |

**Автопереходы — где именно править:**

```
ФУНКЦИЯ ensure_in_progress(conv, actor, *, source)   # новая, app/services/conversations.py
  # Один вход для всех автоматических «взялись за диалог». Сегодня это
  # четыре копии одного if-а: messages.py:313, inbox.py:271, inbox.py:665,
  # transfer.py:138 — и каждая знает свой набор исходных статусов.
  если conv.status в ('new', 'snoozed'):

      записать_переход(conv, 'in_progress', by=source)
```

* **`app/services/messages.py:313-327` — первый ответ оператора.** Сегодня `if conv.status == "new"`. Становится `ensure_in_progress(...)`, то есть добавляется пробуждение из «Отложен»: оператор вернулся к диалогу и написал — отложка кончилась. **`waiting_client` НАМЕРЕННО НЕ СБРАСЫВАЕТСЯ:** если мы ждём клиента и написали ему ещё раз («напоминаю про завтра»), ход по-прежнему за клиентом. Иначе любое напоминание возвращало бы диалог в «В работе», и значение обесценилось бы за день. Отдельный тест.
* **`app/services/inbound.py:289-296` — клиент написал.** Сегодня обрабатывается только `closed → new`. Добавляется: `waiting_client → in_progress` и `snoozed → in_progress` (со снятием отложки), обоим — запись в журнал с `"by": "system"`, как у существующего reopen. Причина: клиент ответил — ждать больше нечего, и держать диалог отложенным до завтрашнего утра означало бы молчать в ответ на живое сообщение.
* **`app/services/inbox.py:665-670` (`claim`)** — атомарный `UPDATE` уже ставит `status=IN_PROGRESS` безусловно. Условие `status <> 'closed'` в `WHERE` **расширяется** до `status NOT IN ('closed')` — оставляем как есть: отложенный диалог в очереди лежать не может по построению (у него есть владелец), а если по какой-то причине окажется — взять его должно быть можно.
* **`app/services/inbox.py:299-341` (`return_to_queue`)** — `if conv.status != CLOSED: conv.status = NEW`. Добавляется снятие отложки: возврат в очередь обнуляет `snoozed_until/…_by_id/…_reason`. Без этого диалог вернётся в очередь и через час «проснётся» второй раз, уже ничей.
* **`app/services/conversations.py:1014`** — `conv.status = "in_progress" if new_id else "new"`. Остаётся, но снятие ответственного дополнительно снимает отложку (через `return_to_queue`, который уже вызывается на `:1026`).
* **`app/bots/handoff.py:256` и `app/services/avito_accounts.py:653`** — ставят `new`; трогать не надо, но отложку снять обязаны, иначе передача от бота оставит `snoozed_until` на диалоге со статусом `new`.

**`status_since` пишется в ОДНОМ месте** — во внутренней `_set_status(conv, value)`, которую зовут все тринадцать точек. Присваивание `conv.status = …` напрямую после этой задачи считается ошибкой и ловится грепом в code review.

### §4. Согласование `awaiting`, `unread_count` и счётчика «ждёт N мин»

Правила, обязательные к реализации (первое и второе — это дефект №3 из `docs/33`, теперь на пять значений):

1. `closed` и `snoozed` **гасят ожидание**: `clear_awaiting(conv)` вызывается для обоих. Для `closed` уже так (`app/services/conversations.py:877-880`), для `snoozed` — добавить.
2. `closed` **обнуляет `unread_count`**. Сегодня не обнуляет, и из-за этого закрытый диалог с непрочитанным показывает чип ожидания в списке (`ConversationListItem.tsx:94` → `waiting.ts:67-72`). Обнулять именно на сервере, а не прятать чип на клиенте: чип — не единственный потребитель счётчика, его же читает бейдж в трее десктопа.
3. Фронт перестаёт считать ожидание в обход статуса: `ChatThreadPane.tsx:159` получает первой строкой `if (conv && !STATUS_SHOWS_WAIT.has(conv.status)) return null;` и `conv.status` в зависимости мемо; `waiting.ts:67` принимает `status` и возвращает `null` для `closed` и `snoozed`. `STATUS_SHOWS_WAIT = {new, in_progress, waiting_client}`.
4. Нижняя панель `Composer.tsx:266-289` перестаёт быть привязанной к одному значению: у `closed` — «Диалог закрыт» + «Вернуть в работу» (как сейчас), у `snoozed` — «Отложен до 14 авг, 10:00» + «Вернуть в работу сейчас», у остальных — обычное поле ввода. **Поле ввода при `waiting_client` и `snoozed` НЕ блокируется**: написать клиенту, не меняя решения, — законное действие (см. §3, «напоминаю про завтра»).

### §5. Интерфейс — макеты текстом

**Строка контекста** — по образцу подписи «(из диалога)» у телефона, то есть мелким приглушённым текстом сразу под контролом. Состав по статусам:

| Статус | Строка | Источник |
|---|---|---|
| `new` | «Ничей · в очереди 4 мин» / «Ничей» | `offered_at`, формат `inbox.format_wait` |
| `in_progress` | «В работе у Иванова · 12 мин» / «В работе у вас · 12 мин» | `assignee`, `status_since` |
| `waiting_client` | «Ждём ответа клиента · 2 ч» | `status_since` |

Формат длительности берётся у существующего `format_wait` (`app/services/inbox.py:152-163`) — он уже даёт «12 мин», «3 ч 20 мин», «2 дн 4 ч»; заводить второй формат нельзя, иначе «12 мин» в одном месте и «12 минут» в другом.

**Кнопки — только те, которые сейчас недостижимы.**

* **«Взять в работу»** — показывается при `assignee === null` и праве `messages:send`. Дёргает **существующую** ручку `POST /conversations/{id}/claim` (`app/api/routes/inbox.py:152`). Новой ручки не надо: её `UPDATE` не требует `offered_at` (докстринг `app/services/inbox.py:631-636`), то есть она работает и для диалога, которого в очереди не было.
* **«Отложить до…»** — при `assignee === me` и статусе из `{in_progress, waiting_client}`. Открывает окно §7.
* **«Вернуть в очередь» В КАРТОЧКЕ НЕ ДОБАВЛЯЕТСЯ.** Она уже есть в шапке ленты (`ThreadActions.tsx:84-96`) с теми же условиями и тем же сервером. Вместо третьей копии — **вынести «Передать» и «Позвать» из карточки**, оставив их только в шапке: тогда докстринг `ThreadActions.tsx:23-26` перестанет врать, ряд в карточке станет коротким и понятным («Взять в работу» / «Отложить до…»), а места хватит без переносов. Это решение требует явного согласия владельца — оно меняет привычный экран, и в оценку заложен час на разговор, а не на догадку.

**Ширина ряда.** `.card-actions` — `flex-wrap: wrap`, дети `flex: 1 1 auto; min-width: 8ch` (`client-card.css:432-446`). Содержимое секции 348 px (380 − 2×16). Две кнопки укладываются в строку без переноса; четыре — переносятся по две, что допустимо. Пять (если «Передать»/«Позвать» останутся) дадут три ряда — ещё одна причина их вынести.

**Бейдж в списке чатов.** `ConversationListItem.tsx` уже проставляет `data-status` на `.conv-card` (`:127`), но CSS его не использует. Бейдж ставится в правый верхний угол карточки, рядом с временем, тем же чипом, что и в `/dialogs` (общий класс `.lc-status-chip`, выносится в `frontend/src/app/lc-base.css` и переиспользуется тремя экранами). **Для `new` и `in_progress` бейдж НЕ рисуется** — это 95 % строк, и чип на каждой превратится в шум; рисуются только `waiting_client`, `snoozed`, `closed`, то есть ровно то, что объясняет, почему строка выглядит непривычно.

**`/dialogs`.** Колонка «Статус» уже есть (`TablePage.tsx:193-198`), меняется только словарь и число веток CSS. Фильтр (`:341-346`) собирается из `Object.entries(STATUS_LABEL)` — правится сам, как только словарь станет общим.

**§6.1. Статистика.** `_SNAPSHOT_SQL` (`app/services/stats.py:411-417`) переписывается на группировку, а не на два `FILTER`:

```sql
SELECT c.status, count(*) AS n
FROM conversations c
WHERE true {_F_CONV}
GROUP BY c.status
```

Ответ `GET /stats/summary` получает `cards.by_status = {new: N, in_progress: N, waiting_client: N, snoozed: N, closed_now: N}` **вместе с сохранением старых ключей** `in_progress_now` и `waiting_now` — их читает нынешний фронт (`SummaryCards.tsx:64,71`) и лист «Сводка» выгрузки (`stats.py:1436-1437`), и ломать контракт в одном релизе с миграцией незачем. Старые ключи помечаются в докстринге как устаревшие с датой удаления.

**Карточка «Ждут ответа» чинится здесь же** — это STATS-01 из `docs/29:447`, критический: подпись обещает одно, число показывает другое. С появлением словаря выбор становится очевидным: карточка называется «**В очереди**» и считает `new`; рядом встают «В работе» (`in_progress`), «Ждут клиента» (`waiting_client`), «Отложено» (`snoozed`). Пять чисел группы «Прямо сейчас» в сумме дают все открытые диалоги — сегодня два числа не дают ничего, и проверить их нечем.

**Лист «Диалоги» выгрузки** (`stats.py:1505`) прогоняется через общий `LABELS`, как это уже сделано для исходов строкой ниже (`:1518` — `convs.OUTCOME_LABELS.get(...)`). Это STATS-09 из `docs/29:466`.

**Нагрузка автораздачи** (`app/services/distribution.py:70`) переходит на `ACTIVE_STATUSES = ("new", "in_progress")` — то есть отложенный и ждущий клиента диалоги **не считаются нагрузкой**. Это осознанное решение, и оно ровно противоположно «взять всё открытое»: отложенный диалог не занимает внимания оператора прямо сейчас, а по смыслу поля (`«Диалоги, которые считаются нагрузкой»`, комментарий на `:69`) считается именно внимание. Комментарий переписывается вместе с константой — иначе он соврёт на следующий же день.

**Виджет «моя статистика»** (`app/services/stats.py:1131`): `c.status = 'in_progress'` → `c.status IN ('in_progress','waiting_client')`. Отложенные в «активные сейчас» не идут — их считает отдельное число «Отложено: N» в том же виджете, и это то, что оператор хочет видеть перед концом смены.

### §7. ОТДЕЛЬНАЯ ЗАДАЧА: «Отложен» с возвратом по времени — 16 часов

Механизма нет (§9.6). Ниже — задание на него; оно отделимо и может ехать вторым релизом. Без него значение `snoozed` заводить **нельзя**: статус «Отложен», который никогда сам не возвращается, — это ловушка, а не функция.

**Хранение** — колонки из §2 (`snoozed_until`, `snoozed_by_id`, `snooze_reason`).

**Ручка `POST /conversations/{id}/snooze`**, тело `{until: ISO8601, reason?: str(≤200)}`. Проверки:
* право `messages:send` и `assignee_id == actor.id` (либо роль `admin`) — иначе 403 `not_holder`, тем же текстом, что уже даёт `release` (`app/services/inbox.py:1043-1055`);
* статус в `{in_progress, waiting_client}` — иначе 422 из матрицы §3;
* `until` строго в будущем и не дальше 30 суток — иначе 400. Верхняя граница нужна: «отложить до 2031 года» — это скрытое удаление диалога, и оно должно называться закрытием.

**Пресеты в окне** (кнопками, чтобы не заставлять выбирать дату на каждый диалог): «Через 1 час», «Через 3 часа», «Завтра в 10:00», «В понедельник в 10:00», «Свой срок…». Пресеты считаются в **московском времени** — том же `ZoneInfo("Europe/Moscow")`, что уже используется отчётностью (`app/services/conversation_table.py:233`). Это заявлено явно подписью в окне «время московское», потому что настройки часового пояса у пользователя нет (unknown №3), и молчаливое предположение здесь стоило бы пропущенного звонка.

**Сторож** — новый `app/scheduler/jobs/snooze.py`, `IntervalTrigger(minutes=1)`, регистрация в `app/scheduler/main.py` рядом с `awaiting_jobs.register(scheduler)` (`:168`). Устройство — по образцу `awaiting.py`, который уже решает задачу «раз в минуту посмотреть на колонку с датой»:

```
ЗАДАЧА wake_snoozed():
  now = utcnow()
  выбрать id диалогов: status='snoozed' AND snoozed_until <= now
       (частичный индекс ix_conversations_snoozed_until)
  для каждого, ОТДЕЛЬНОЙ транзакцией:
      conv = SELECT ... FOR UPDATE
      если conv.status != 'snoozed': пропустить   # проснулся сам, клиент написал
      снять_отложку(conv)                          # три поля в NULL
      если conv.assignee_id есть:
          _set_status(conv, 'in_progress', by='system')
          enter_queue НЕ вызывается: у диалога есть хозяин
      иначе:
          _set_status(conv, 'new', by='system')
          inbox.enter_queue(conv, now=now)         # вернулся во «Входящие»
      add_system_message(db, conv, f"Отложенный диалог вернулся: {срок}")
      write_audit(action='conversation.status_changed', by='system')
      notify(kind='conversation.snooze_due', recipient=прежний владелец)
      commit
      публикация ПОСЛЕ commit: conversation:updated + (если в очередь) inbox:new
```

**Отдельной транзакцией на диалог, а не пачкой** — по тому же доводу, что в `reclaim.py`: одна упавшая строка не должна отменять остальные девятнадцать.

**Куда возвращается диалог.** Заказчик пишет «возвращает во „Входящие“». Буквально это верно только для диалога без ответственного. Если владелец есть — возвращать диалог в общую очередь значит отбирать его у человека, который сам же его и отложил; это прямо противоречит доводу, записанному в `app/scheduler/jobs/awaiting.py:34-41` («не отбираем у того, кто в сети»). Поэтому: **есть владелец — статус «В работе» и уведомление ему; владельца нет — во «Входящие» и звук у всех.** Если владелец в этот момент не в сети — за него уже отвечает существующий сторож `awaiting.py`, второй писать не надо.

**Уведомление** — новый вид в каталоге `app/services/notifications.py` (`KINDS`, рядом с `conversation.awaiting_you`, `:266-272`):

```python
"conversation.snooze_due": KindSpec(
    severity="warning", audience=None,        # адресное: прежний владелец
    title="Отложенный диалог вернулся",
    dedup="entity", entity_type="conversation",
)
```

**`DELETE /conversations/{id}/snooze`** — «вернуть сейчас», то же самое без ожидания срока. Нужна кнопкой в нижней панели (§4 п. 4).

**Что должно упасть, если сделано неправильно:**
1. Диалог с `snoozed_until` в прошлом и статусом `in_progress` (проснулся от клиента) сторож **не трогает** — иначе второй раз всплывёт уже разобранный диалог.
2. Клиент написал в отложенный диалог → статус `in_progress`, `snoozed_until` пуст, уведомление владельцу ушло.
3. Перезапуск планировщика между постановкой и сроком: диалог всё равно возвращается (правда лежит в базе, а не в очереди задач).
4. `snoozed_until` в прошлом на момент запроса → 400, а не молчаливое «уже пора».
5. «Завтра в 10:00», заданное в 23:50 МСК, даёт следующий календарный день по Москве, а не через 10 часов 10 минут.
6. Отложка гасит `awaiting_since` → янтарная полоса срочности и янтарный чип «Отложен» на одной карточке невозможны (охрана цветового решения §1).

### §8. Разрешение конфликта «двое взяли одновременно»

Механизм уже есть и переиспользуется целиком: атомарный `UPDATE … WHERE claimed_by_id IS NULL AND assignee_id IS NULL AND status <> 'closed'` + проверка `rowcount` + один повтор (`app/services/inbox.py:653-698`). Проигравший получает **409 `already_claimed`** с телом `{reason, claimed_by:{id, full_name}, mine}` (`:581-593`).

Что добавляется:

1. **Фронт показывает имя.** Обработчик ошибки кнопки «Взять в работу» разбирает `details.claimed_by.full_name` и показывает тост «Диалог уже взял Пётр Иванов», а не «Не получилось». Приём в продукте уже есть у кнопки «Принять» в очереди — переиспользуется тот же код.
2. **Кадр `conversation:updated` уходит всем** (это уже так — `app/api/routes/inbox.py:199` у принятия, `:401` у возврата в очередь), и у проигравшего поле «Статус» и «Ответственный» перерисовываются сами, без перезагрузки: `applyConversationPatch` патчит и деталь, и все варианты списка (`applyWsEvent.ts:168-186`).
3. **Смена статуса через `PATCH` перестаёт врать в гонке.** Сегодня второй получает 422 `same_status` («Диалог уже в этом статусе»). После правки `change_status` при переходе в `in_progress` сравнивает `conv.assignee_id` с актором и, если ответственный уже другой, отвечает тем же **409 `already_claimed`** с именем — один код ошибки на оба пути, один текст в интерфейсе.
4. **Состав патча расширяется** до `{status, status_since, assignee, in_inbox, snoozed_until}` — `app/api/routes/conversations.py:100-118`. Клиентская сторона правки не требует: `mergeConversationPatch` копирует незнакомые плоские ключи как есть (`applyWsEvent.ts:59-73`).

## Миграция и порядок выката

**Шаг 0 — до единой строки кода (0.5 ч).** На проде:

```sql
SELECT status, count(*) FROM conversations GROUP BY status ORDER BY 2 DESC;
SELECT count(*) FROM conversations;
```

Первый запрос закрывает unknown №5 (есть ли значения вне трёх) и №4 (объём). Если во второй строке больше 200 000 — `CHECK` ставится через `NOT VALID` + `VALIDATE`, а индекс — `CONCURRENTLY`. Решение принимается по цифре.

**Шаг 1 — общий словарь, без новых значений (релиз №1).** `app/services/conversation_status.py` и `frontend/src/shared/lib/conversationStatus.ts` содержат **прежние три значения**; все девять копий переведены на них; охранный тест «сервер = фронт» зелёный; лист «Диалоги» выгрузки начинает переводить статус (STATS-09 закрыт). **Поведение продукта не меняется ничем.** Этот релиз можно выкатить и жить с ним неделю — он полезен сам по себе.

**Шаг 2 — миграция 0026.** Схема, `CHECK` на **пять** значений, три колонки, индекс, заполнение `status_since`. Данных с новыми статусами ещё нет.

**Шаг 3 — фронт (релиз №2).** Пять значений в словарях, поле «Статус» в карточке, строка контекста, бейдж в списке, колонка и фильтр. **Фронт выкатывается РАНЬШЕ бэкенда** — иначе в окне выката старый клиент получит незнакомый код статуса и покажет `waiting_client` латиницей (см. крайние случаи). Новые значения фронт умеет отображать, но сервер их ещё не отдаёт и не принимает — это безопасно.

**Шаг 4 — бэкенд (релиз №3).** Матрица переходов, автопереходы, `ensure_in_progress`, статистика на пять чисел, `distribution.ACTIVE_STATUSES`, согласование `awaiting`/`unread_count`.

**Проверка после шага 4, до объявления готовности.** На боевом канале: написать с телефона, ответить, поставить «Ждёт клиента», написать с телефона снова — убедиться, что статус сам вернулся в «В работе», а в ленте появилась системная запись. **Настоящий канал, а не имитатор.**

**Шаг 5 — «Отложен» (релиз №4, задача §7).** Ручки, окно, сторож, уведомление. Включается **после** того, как шаг 4 отработал сутки: пока не видно, что автопереходы ведут себя правильно, добавлять к ним ещё и возврат по времени — значит разбирать два источника странностей сразу.

**Откат.** Шаги 1 и 3 откатываются сборкой. Шаг 4 — откатом релиза; в базе останутся диалоги со статусами `waiting_client`/`snoozed`, которые старый код покажет латиницей и не даст сменить. Поэтому в `docs/RUNBOOK-DEPLOY.md` рядом с задачей кладётся запрос отката данных:

```sql
UPDATE conversations
   SET status = 'in_progress', snoozed_until = NULL,
       snoozed_by_id = NULL, snooze_reason = NULL
 WHERE status IN ('waiting_client', 'snoozed');
```

`WHERE` обязателен: без него это переписывание всей таблицы и потеря закрытых.

**Что должно упасть, если задача сделана неправильно (охранные тесты).**

1. Серверный `STATUSES` и фронтовый `STATUS_ORDER` разошлись → тест красный.
2. Грeп по `app/` и `frontend/src` находит литерал `"in_progress"` вне двух файлов словаря → тест красный (проверка по списку разрешённых файлов, как уже сделано для `SORTABLE`).
3. `new → waiting_client` даёт 422 `no_reply_yet`, а не 200.
4. Первый ответ оператора в диалоге `snoozed` снимает отложку; в диалоге `waiting_client` — **не** меняет статус.
5. Входящее от клиента в `waiting_client` и в `snoozed` даёт `in_progress` и два события журнала.
6. Закрытие обнуляет `unread_count`; закрытый диалог с непрочитанным не показывает чип ожидания ни в списке, ни в шапке.
7. Сумма пяти чисел группы «Прямо сейчас» равна `count(*)` по `conversations` с теми же фильтрами.
8. `alembic upgrade → downgrade → upgrade` для 0026 на настоящем PostgreSQL.
9. Диалог в статусе `snoozed` не считается нагрузкой в `distribution.candidates`.

По правилу из `HANDOFF-2026-08-09`: каждый тест написан, потом **код намеренно сломан**, и проверено, что тест краснеет. Тест, который зеленеет на сломанном коде, в этом проекте уже случался трижды за два дня.
