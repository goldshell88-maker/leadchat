# 09 — План реализации веб-кабинета и десктопа (UX-first)

> Главный документ реализации. Отвечает на бриф заказчика из 9 разделов и связывает
> пакет docs/01–08 в исполняемый план. Правило документа: **только дельта** —
> конкретика реализации, приоритеты и риски поверх уже зафиксированных контрактов;
> сами контракты не пересказываются, на них даются точные ссылки.
> Источник истины по архитектуре и ролям — [DESIGN.md](../DESIGN.md) (§1–9),
> по фронту — [docs/03](03-FRONTEND.md). Дизайн-система — docs/10-UX-DESIGN-SYSTEM.md,
> макеты экранов — docs/11-SCREENS.md (пишутся параллельно; ссылки на их разделы
> ниже — по согласованной структуре), кликабельный прототип — `prototype/index.html`.
>
> Фокус пакета: опыт сотрудника. Три сквозных UX-инварианта, которые проверяются
> в definition of done каждого спринта:
> 1. **Ответ клиенту — меньше 3 кликов** от появления диалога в списке
>    (клик по строке → «⚡»/хоткей шаблона → Enter).
> 2. **Хоткеи работают** (каталог — §1.1 ниже; полный реестр — docs/10 §«Хоткеи»).
> 3. **Ни одного «белого» состояния**: у каждого экрана есть скелетон, пустое
>    состояние и состояние ошибки (библиотека `shared/ui`, docs/10 §«Состояния»).

## 1. Общий план реализации: этапы DESIGN §7 → 2-недельные спринты

Этапы 0–6 (суммарно ~12.5 недель) укладываются в **7 спринтов по 2 недели**
(14 недель = 12.5 плана + ~1.5 недели буфера, распределённого по спринтам 4 и 7).
Команда: **FS-A** (fullstack, ведёт бэкенд) и **FS-B** (fullstack, ведёт фронт/UX).
При 1 разработчике — см. §1.3.

### 1.0. Каталог хоткеев (фиксируется здесь, реализуется по спринтам)

| Хоткей | Действие | Спринт |
|---|---|---|
| `Enter` / `Shift+Enter` | отправить / перенос строки (03 §1.2 Composer) | 3 |
| `/` в пустом поле ввода | открыть «⚡ быстрые ответы» с фокусом в поиске | 4 |
| `Ctrl+K` | фокус в поиск по диалогам | 3 |
| `J`/`K` или `↓`/`↑` | следующий/предыдущий диалог в списке | 4 |
| `Alt+↓` / `Alt+↑` | следующий/предыдущий диалог с непрочитанным | 4 |
| `Alt+1..4` | вкладки Мои / Все / Новые / Закрытые | 4 |
| `Ctrl+Shift+N` | режим заметки 🗒 в композере | 4 |
| `Esc` | «луковица» слоёв: поповер → модалка → режим заметки → поиск | 3 |

### 1.1. Спринты

**Спринт 1 (нед. 1–2) — «Фундамент + лицо продукта»** = этап 0 + старт этапа 1.

- Экраны/состояния: `/login` (все состояния: ошибка пароля, блокировка после 10
  попыток, invite-установка пароля — 01 §2.4) — docs/11 §Login; каркас `AppLayout`
  (сайдбар, индикатор соединения, юзер-меню) — docs/11 §Shell; библиотека
  скелетонов/пустых состояний в `shared/ui`; тема Lead Partner в коде
  (см. правку §2.5 — светлая тема основная, палитра от `#3cc13b`).
- Параллельно (FS-B): **дизайн-токены docs/10 финализируются + `prototype/index.html`
  кликабельный прототип трёх главных экранов** — стейкхолдер подписывает до того,
  как свёрстан первый боевой экран. Это дешёвая страховка от переделок.
- FS-A: repo, Docker Compose dev, CI, скелет FastAPI, схема БД + миграции,
  auth JWT+refresh (08 §1, DESIGN §9); **день 1 — заявка на Messenger API Авито
  и запуск fake-avito в dev-композе** (§6).
- DoD: логин работает с холодного старта; тихий refresh по cookie (03 §6);
  прототип подписан; CI гоняет unit-тесты (§8); скелетон `/login` и layout — без FOUC.

**Спринт 2 (нед. 3–4) — «Ядро Авито + первый живой список»** = этап 1 + начало этапа 2.

- FS-A: OAuth-подключение, шифрование/refresh токенов, webhook gateway → Redis
  Streams → воркер, backfill, reconciliation (§6; 08 §2, §4).
- FS-B, параллельно на fake-avito: `/settings/accounts` (docs/11 §Accounts; все
  состояния карточки аккаунта: 🟢 active / 🔴 needs_reauth / disabled, кнопка
  «Проверить webhook» 01 §4.7) и **левая колонка `/chats`**: виртуализированный
  список, вкладки, поиск, скелетон и пустые состояния («Нет диалогов — подключите
  аккаунт Авито» со ссылкой для админа) — docs/11 §Chats-List.
- DoD: сообщение из fake-avito появляется в списке по WS < 1 с без перезагрузки;
  скролл списка на 5 000 сидированных диалогов — 60 fps; смена вкладки — мгновенно
  (кэш по ключу фильтра, 03 §2.1) и без «вспышки пустоты» (§2.4).

**Спринт 3 (нед. 5–6) — «Рабочее место» + минимальный прод** = ядро этапа 2.

- Экраны: центр (лента, пузыри, статусы доставки ⏳/✓/✗+«повторить», заметки) и
  композер — docs/11 §Chats-Thread; правая карточка (клиент, объявление, статус,
  передача) — docs/11 §Chats-Card; deep-link `/chats/:id` (03 §6).
- Отправка: оптимистичный путь temp→pending→delivered/failed (03 §3.4).
- **Деплой минимального прода** (§9) и подключение реального аккаунта Авито.
- DoD (UX-критерии — обязательные): **ответ на новый диалог ≤ 3 кликов**; хоткеи
  спринта 3 (§1.0) работают; обрыв сети 2 мин → реконнект+догон без потерь
  (чеклист 03 «DoD этапа 2»); скелетоны ленты и карточки; первый byte→FCP < 1.5 с
  на проде (§7.2). Обязательные тесты §8.2 — зелёные.
- Конец спринта 3 = **команда начинает реально работать в вебе** (план DESIGN §7
  обещает 6-ю неделю — совпадает).

**Спринт 4 (нед. 7–8) — «Комфорт + роли»** = хвост этапа 2 + этап 3.

- Экраны: «⚡ шаблоны» (поповер с поиском/папками/переменными — docs/11
  §Templates-Picker), `/settings/templates`, `/settings/profile` (личные шаблоны,
  тема, звук, уведомления браузера), передача коллеге с комментарием, история
  клиента; полный RBAC в UI (03 §5, режимы head/observer — docs/11 §RolesView),
  `/settings/team` + invite-флоу, журнал аудита (01 §9.7).
- `/stats` (карточки, график, тепловая карта, таблица менеджеров, экспорт —
  06 §4–5, docs/11 §Stats) — «догоняет» в конце спринта, это не критический путь.
- Сюда же — недельный буфер: обратная связь первых пользователей из спринта 3
  разбирается с приоритетом выше плановых задач (правило: багфикс UX < 1 дня).
- DoD: хоткеи `/` и `Alt+↑/↓`; вставка шаблона ≤ 2 действий; head видит плашку
  режима просмотра и переназначает; observer — только чтение; прямые URL
  редиректят по правам (03 §6); все экраны статистики со скелетонами и empty.

**Спринт 5 (нед. 9–10) — «Десктоп»** = этап 4 (последовательность — §4).

- Инсталлятор NSIS на `/download`, трей+бейдж, тосты с «Ответить», автозапуск,
  глобальный хоткей, автообновление, офлайн-кэш+outbox (04 §3–6).
- FS-A параллельно начинает движок ботов (runtime, §5) — десктоп почти не трогает
  бэкенд (04 §9).
- DoD: полный чеклист 04 §10; «закрыл ноутбук в метро → открыл → набранное ушло».

**Спринт 6 (нед. 11–12) — «Боты: runtime + редактор»** = этап 5 без AI.

- Runtime всех детерминированных шагов, расписания, «оператор написал → бот
  замолк», защита от зацикливания (02 §2); редактор-список + валидация +
  песочница (02 §5, 01 §8.6) — docs/11 §Bots.
- DoD: сценарий «Первичный приём» (без `ai_answer`, ветка через `condition`)
  проходит в песочнице и на fake-avito e2e; менеджер видит переменные бота
  в карточке; 🤖-бейджи в списке и ленте.

**Спринт 7 (нед. 13–14) — «AI + полировка → релиз 1.0»** = хвост этапа 5 + этап 6.

- `ai_answer` + классификатор негатива + извлечение телефона (02 §3), деградация
  «AI недоступен → handoff» (02 §3.3).
- Нагрузочный прогон k6 (07 §3 — gate релиза), UAT-сценарии (07 §5), чек-лист
  безопасности (07 §4 целиком), онбординг-инструкция для сотрудников, приёмка.
- DoD: k6-критерии пройдены; UAT подписан; бэкап восстановлен на чистой машине
  (07 §4.8); Sentry без незакрытых ошибок уровня error за последние 3 дня.

### 1.2. Критический путь и параллелизация

```
Критический путь: Спринт1(auth+фундамент) → Спринт2(Avito inbound) →
                  Спринт3(рабочее место+прод) → Спринт4(RBAC)
Вне критического пути (можно сдвигать/параллелить):
  дизайн-система+прототип (спринт 1, FS-B) · /stats (спринт 4) ·
  десктоп (спринт 5) · боты (спринты 6–7) · экспорт XLSX · аудит-UI
```

Правило параллелизации: FS-A всегда на один спринт «впереди по бэкенду»
(контракты 01 фиксированы — фронт работает на fake-avito и моках OpenAPI-типов,
не ожидая живого бэкенда).

### 1.3. Если разработчик один

- Порядок строго последовательный по критическому пути; из параллельного
  выживает только прототип (1–2 дня, он экономит больше, чем стоит).
- Команда начинает работать на **8-й неделе** (спринт 3 растягивается на 4-й).
- Сдвигается «вправо»: `/stats` → после десктопа; **десктоп → после ботов-runtime**
  (боту нужнее быть раньше: он снимает ночную нагрузку), либо наоборот по решению
  заказчика — но не оба сразу; `ai_answer` и экспорт XLSX — кандидаты в фазу 2.0.
- Итого при 1 разработчике: релиз 1.0 ≈ 17–18 недель; веб-ядро — 8 недель.

### 1.4. Риски плана

| Риск | Митигация |
|---|---|
| Доступ к Messenger API дают дольше 2 недель | заявка в день 1; вся разработка до спринта 3 идёт на fake-avito (07 §2) — блокируется только прод-подключение |
| docs/10/11 отстают от спринтов | прототип спринта 1 — обязательный gate; экраны без макета не верстаются «из головы», а ждут макет (или макет рисуется прямо в PR) |
| Обратная связь спринта 3 ломает план 4 | буфер в спринте 4 предусмотрен именно под это |

## 2. Архитектура фронтенда — дельта к docs/03

Архитектура (каталоги, стейт, realtime, виртуализация, роли, роутинг) целиком —
docs/03 §1–6. Здесь — решения уровня «в каком порядке и с какими бюджетами».

### 2.1. Порядок создания фич (и почему такой)

1. `shared/api` (http, queryKeys, типы из OpenAPI) + `app/theme.ts` — фундамент,
   без него любой экран — переделка.
2. `features/auth` + guard'ы роутера (03 §6) — открывает все остальные экраны.
3. `shared/ui`: `Skeleton*`, `EmptyState`, `ErrorState`, `ConfirmModal` — **до**
   первого доменного экрана, чтобы состояния были у всех экранов с рождения,
   а не «потом допилим».
4. `shared/realtime` (WsClient + applyWsEvent, 03 §3) — до ленты сообщений:
   список чатов уже живой на спринте 2.
5. `features/chats`: list → thread → composer/отправка → client-card
   (в порядке ценности для менеджера).
6. `features/templates-picker` → `features/settings/*` → `features/stats`.
7. `platform/` (мост Tauri, 03 §7) — последним, интеграционных точек ровно четыре.

### 2.2. Паттерн подключения WS к кэшу

Контракт и код — 03 §3.1–3.3. Дельта-правила реализации:

- **Единственная точка входа**: WsClient создаётся один раз в `providers.tsx`
  после логина; все события идут только через `applyWsEvent` → `setQueryData`.
  Компонентам запрещено подписываться на сокет напрямую (ревью-чеклист).
- `message:new` — никогда `invalidateQueries` (03 §2.3, при 10 000 сообщений/сутки
  это DDoS собственного API); бюджет применения одного события — < 8 мс (§2.4).
- Порядок реализации: сначала «догон» (03 §3.2) и дедупликация по `message.id`,
  потом звук/бейджи. Догон — это и есть первый коннект (код общий), поэтому
  отдельного «initial sync» не существует — меньше путей, меньше багов.

### 2.3. Code-splitting по роутам

- В главном бандле — только `/chats` со всеми тремя колонками (основной сценарий;
  ленивая загрузка здесь ухудшила бы главный экран ради второстепенных).
- `React.lazy` + `Suspense`-скелетон страницы: `/stats` (тянет чарты),
  каждый раздел `/settings/*` отдельно, **редактор ботов — самый тяжёлый чанк**
  (валидация JSON Schema, песочница) — грузится только у админа.
- `/login` — отдельный чанк (не тащит Query/WS-слой).
- Tauri-модули не попадают в веб-бандл динамическим импортом (03 §7) — проверять
  в CI отчётом бандла (см. §2.4).

### 2.4. Бюджет производительности и как держим

| Метрика | Бюджет | Как мерим |
|---|---|---|
| FCP `/chats` (холодный, прод) | < 1.5 с | Lighthouse CI в GH Actions на собранном бандле, budgets.json; на проде — web-vitals → Sentry |
| Интеракция списка (скролл/hover/выбор) | < 16 мс/кадр | React DevTools Profiler на сиде 5 000 диалогов / 10 000 сообщений (скрипт сида в fake-avito) |
| Применение WS-события к кэшу | < 8 мс | `performance.mark` вокруг `applyWsEvent` в dev-сборке |
| Открытие диалога из списка | < 150 мс из кэша; < 500 мс холодное | Profiler + network throttling |
| Initial JS (gzip) главного бандла | ≤ 250 КБ | `rollup-plugin-visualizer`, порог в CI |
| Переключение вкладок списка | 0 «вспышек пустоты» | `placeholderData: keepPreviousData` на `conversations.list` — вкладка меняется поверх старых данных с фоновым refetch |

Дешёвые обязательные приёмы под FCP: preload woff2-сабсета Inter (кириллица+латиница),
`font-display: swap`, брутли-сжатие в nginx (05 §3), скелетон трёх колонок рисуется
до ответа API.

### 2.5. Ловушки виртуализации (дельта к 03 §4)

1. **Замена temp→server id ломает `getItemKey`**: пузырь ремоунтится, `measureElement`
   перемеряет, скролл дёргается. Решение: ключ виртуализатора — `client_message_id`
   (он стабилен через все три фазы 03 §3.4), а не `id`.
2. **Картинки в `AttachmentPreview` дозагружаются после measure** → лента «прыгает».
   Контракт 01 §6.5 отдаёт у вложения только `media_id/kind/url/name/size` (пиксельных
   размеров изображения в API нет — aspect ratio вычислить не из чего), поэтому
   резервировать фиксированную высоту превью (240px по длинной стороне, 10 §4.7):
   контейнер фиксированного размера, изображение вписывается `object-fit`;
   onload не меняет высоту контейнера.
3. **`scrollTop`-компенсация при prepend** (03 §4.2) обязана идти в том же кадре
   после перемера (`requestAnimationFrame`) — иначе мигание; не вызывать
   `scrollToIndex` во время компенсации.
4. Смена фильтра = новый query key = новый массив rows → виртуализатор надо
   сбрасывать (`scrollToOffset(0)`), иначе остаётся глубокий скролл старой вкладки.
5. `estimateSize` ленты (64px) сильно врёт на длинных сообщениях → скроллбар
   «дышит». Это норм-поведение TanStack Virtual; не пытаться «чинить» пересчётом
   всех высот — дороже. В списке диалогов высота фиксированная (76px) — там
   measure выключен (03 §4.1), не включать его «для красоты».
6. Звук/unread считать в `applyWsEvent`, а не в компонентах строк: строка может
   быть не смонтирована (за пределами overscan).

### 2.6. Правка несоответствия в docs/03 §8.1 (важно)

docs/03 §8.1 писался до фиксации палитры и говорит «тёмная тема — основная»
с палитрой-плейсхолдером. **Норма — DESIGN §3.2/§6 и бренд-токены docs/10:
светлая тема основная**, `defaultColorScheme="light"`, primary-шкала генерится
от `#3cc13b` (hover `#2ea32d`, subtle `#d8f3d8`, focus ring `rgba(60,193,59,.25)`),
шрифтовой стек `"Proxima Nova", Roboto, Inter, -apple-system, "Segoe UI", sans-serif`.
Структура темы (Mantine-токены, chat-vars.css, переключатель в профиле) из 03 §8.1
сохраняется как есть; тёмная тема остаётся опцией. В docs/03 внести правку
при первом же PR темы.

5. **Автообновление + CI**: minisign-подпись, `latest.json`, workflow сборки

**Первый инсталлятор (конец спринта 5) включает**: пп. 1–5 целиком, автозапуск,
глобальный хоткей Ctrl+Shift+L. Если спринт трещит — жертвуем в порядке:
MSI-вариант (NSIS достаточно, MSI — для GPO позже) → шифрование кэша DPAPI
(кэш можно временно не писать вовсе — но outbox-путь отправки не режется,
он единственный) → интерактивный «Ответить» из тоста (тост без кнопки остаётся).

**Чем веб-режим отличается в первом релизе** (по 03 §7, это осознанные отличия,
а не долги): нет офлайн-очереди (при `offline` композер показывает «нет
соединения»); уведомления — только Notification API при скрытой вкладке и выданном
разрешении; бейдж — только `(N)` в title; нет трея, автозапуска, глобального
хоткея; обновления — просто перезагрузка страницы. Функционально чаты/роли/боты
идентичны — различие только в «нативном слое».

Риск: WebView2 на старых Windows-сборках сотрудников — проверить на 2–3 реальных
машинах компании в начале спринта 5, а не в конце (fallback-план Electron —
DESIGN §2, но решение принимаем по факту теста).

## 5. Боты: порядок реализации поверх docs/02

Формат сценария, runtime, AI-подсистема, редактор — docs/02 целиком. Порядок:

1. **Runtime + 3 шага: `send`, `ask`, `handoff`** (02 §1.3, §2.1–2.3) + два
   железных правила с первого дня: «оператор написал → бот замолкает навсегда»
   (02 §2.6) и защита от зацикливания (02 §2.7). Уже этого достаточно для
   сценария «представиться, задать вопрос, позвать человека» — он включается
   на ночные часы у одного аккаунта как пилот.
2. Остальные детерминированные шаги: `menu`, `condition`, `tag`/`note`, `close`,
   таймауты `ask`/`menu` (02 §2.4), расписания (02 §2.5).
3. **Редактор (MVP-список)** + валидация при сохранении + песочница
   (02 §5, API 01 §8.6). Редактор — после runtime: пока сценарий один,
   его правит разработчик JSON'ом, ценность редактора — когда шагов уже 8 видов.
4. **`ai_answer`** (02 §3.1–3.3) + классификатор негатива и извлечение телефона
   (02 §3.4–3.5) — спринт 7, последним: вся деградация уже готова
   (`ai_answer` недоступен → `handoff`, 02 §3.3).

**Как тестировать сценарии до подключения AI:**

- Unit: движок гоняется на JSON-сценариях без сети (07 §1.1,
  `test_bot_engine.py`) — каждая ветка «Первичного приёма» = отдельный кейс.
- Песочница `/bots/sandbox/*` (01 §8.6, 02 §5.3): админ играет клиента в
  чате-эмуляторе — основной ручной инструмент, работает без Авито вообще.
- E2E: fake-avito (07 §2) шлёт скриптованного «клиента» вебхуками — проверяем
  сквозной путь webhook → runtime → отправка → карточка с переменными.
- AI-заглушка: env `AI_FAKE=1` — провайдер возвращает фиксированные
  `{reply, confidence, needs_operator}` из фикстуры; ей же тестируем пороги
  confidence и таймаут 10 с → handoff, не тратя токены и не флапая CI.

UX-дельта: собранные ботом переменные (`bot_vars`) показываются в карточке
клиента отдельным блоком «🤖 Бот собрал» (docs/11 §Chats-Card) — менеджер после
handoff не перечитывает всю переписку. Это критерий приёмки спринта 6.

## 9. Деплой: минимальный прод на спринте 3

Вся инфраструктура — docs/05. Решение: **staging = prod** — для внутреннего
инструмента на ~50 человек отдельный staging не окупается; его роль выполняют
dev-компоуз с fake-avito и деплой-smoke (07 §6).

Минимальный прод (конец спринта 3), по чек-листу 05 «Приложение Б»:

1. VPS: firewall, fail2ban, deploy-пользователь (05 §1); DNS
   `chat.partner-lead-centre.ru`, bootstrap-сертификат (05 §1).
2. `docker compose` полного состава (05 §2.2) — сразу все сервисы (api, worker,
   scheduler, postgres, redis, nginx), даже пока боты пустые: состав прода
   не должен меняться между спринтами.
3. CI/CD: деплой по тегу через `deploy.sh` (05 §5) — руками не выкатываем
   вообще, с первого раза.
4. Бэкапы: cron `backup.sh` + офсайт + restore-тест (05 §6, Приложение А).

**Порядок включения мониторинга** (05 §7):

| Когда | Что |
|---|---|
| Спринт 1 (dev) | Sentry (backend+frontend DSN) — с первой строки кода, дешевле всего |
| Спринт 3 (прод) | Uptime-Kuma: HTTPS-чек, `/api/v1/health`, cert-expiry; JSON-логи структурно; Telegram-алерты скриптов (05 §4) |
| После реального Авито (спринт 3–4) | Канарейка вебхуков: push-монитор «нет входящих N минут при рабочем дне» (05 §7.2) — единственный сигнал молчаливой смерти вебхука |
| Спринт 5 | Монитор `latest.json`/`/download` (канал автообновлений) |
| Спринт 7 | Ревизия алертов по итогам месяца эксплуатации: убрать шумные, добавить пропущенные; runbook сверен с реальностью (05 §8) |

Риск: единственный VPS — единая точка отказа. Принято осознанно (DESIGN
допущение §3); компенсация — офсайт-бэкапы + проверенный restore + runbook
(05 §6, §8): цель не «не падать никогда», а «подняться за час».
