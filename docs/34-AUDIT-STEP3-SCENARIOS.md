# Шаг 3 аудита: сквозные сценарии

Семь сценариев из брифа пройдены целиком по коду — маршруты, компоненты, ручки
API — с подсчётом кликов и фиксацией мест, где человек запнётся. Живого входа
в интерфейс нет (учётной записи не выдано), поэтому все выводы опираются на
исходники; там, где это меняет достоверность, сказано отдельно.

**Главное из этого шага — сценарий 6, истёкший токен.** Постоянного уведомления
о том, что канал отвалился, в системе не существует: вид уведомления объявлен
и покрыт двадцатью тестами, но ни одна строка боевого кода его не создаёт.
Хуже: любая сетевая ошибка при обновлении токена переводит канал в состояние
«требует переподключения», а из этого состояния система не выходит сама —
и все три сторожа, следящие за каналами, перебирают только активные.
Оба боевых аккаунта подключены своими ключами, то есть идут ровно по этому пути.

## Сквозные сценарии, часть 1

Три пути пройдены по коду от первого экрана до последнего действия: маршруты, компоненты, ручки сервера. Считались клики мышью и нажатия клавиш; набор текста за нажатия не считался.

Условия, одинаковые для всех трёх сценариев:

* роль `manager` — права `conversations:read, messages:send, conversations:manage, notes:read, notes:write, templates:own, stats:own` (`app/core/rbac.py:48-58`);
* `handles_conversations = true` (`app/models/user.py:55`), то есть человек участвует в раздаче;
* автораспределение выключено — это значение по умолчанию (`app/services/app_settings.py:95`: `bool(getattr(settings, "distribution_enabled", False))`), поэтому каждое обращение встаёт в очередь и ждёт, пока его возьмут руками (`app/services/inbound.py:349-355`);
* экран ≥1360px, если не сказано иначе (порог трёх колонок — `frontend/src/shared/lib/breakpoints.ts:25`).

Уже описанные дефекты не переписываю: где находка совпадает с разобранной ранее, стоит ссылка на её номер из `docs/29-AUDIT-STEP1-SCREENS.md` или на пункт `docs/28-AUDIT-STEP0-INVENTORY.md`.

### Точки трения

**1. Ни один клик из трёх нельзя заменить клавиатурой — у вкладки «Входящие» нет сочетания.**
Каталог сочетаний обещает «Alt + 1…4 — Срезы списка: Мои, Все, Новые, Закрытые» (`frontend/src/features/hotkeys/catalog.ts:31`), и обработчик действительно знает ровно эти четыре (`frontend/src/features/hotkeys/useChatHotkeys.ts:40-45, 79-83`). Очереди — вкладки, с которой начинается смена, — в списке нет вовсе. Первым пунктом справки при этом стоит «Ctrl + R — Принять диалог» (`catalog.ts:23`), то есть человека учат ускорять действие, до которого он не может дойти без мыши.

**2. Пустое состояние «Моих» уводит мимо очереди.**
Кнопка «Посмотреть новые» ставит `tab: "all", status: "new"` (`frontend/src/features/chats/components/list/ChatListPane.tsx:614`), а `setFilters` попутно закрывает очередь (`chatUiStore.ts:91`). Получившийся список — не очередь, и отличается тремя вещами:

* он не сужен по каналам оператора. Очередь сужается `visible_queue_condition` (`app/services/inbox.py:104-127`), обычный список — нет: у вкладки `all` условие `Conversation.status != "closed"` и всё (`app/services/conversations.py:368`). Новичок видит обращения всех девяти каналов;
* в нём остаются диалоги, от которых он уже отказался: очередь их прячет (`inbox.py:126`, `_declined_by`), список — нет;
* порядок другой: очередь строго `offered_at ASC` (`inbox.py:451`), список сортирует сначала по закреплённым и непрочитанным (`conversations.py:486-500`).

Взять чужой канал при этом получится: `claim` проверяет только право `messages:send` и не смотрит на принадлежность канала (`app/services/inbox.py:512-527` — весь текст проверки).

**3. Пустая очередь у неназначенного оператора выглядит как выполненная работа.**
Пустое состояние очереди — «Очередь пуста / Новые обращения появятся здесь — их будет видно и слышно» (`ChatListPane.tsx:88-96`). Если админ не добавил человека ни на один канал и все девять каналов кому-то назначены, обращения не появятся никогда: правило видимости — «мой канал ИЛИ канал, на который не назначен никто живой» (`app/services/account_operators.py:124-140`). Система знает эту разницу и умеет её объяснить — блок «Мои каналы» показывает жёлтое «Каналы не назначены. Новые обращения во «Входящие» к вам не попадут» (`frontend/src/features/settings/profile/MyChannelsBlock.tsx:58-65`). Но блок лежит в Настройки → Профиль → вкладка «Учётная запись», ниже формы обращения к администратору (`frontend/src/features/settings/profile/ProfilePage.tsx:95`), и с экрана чатов на него нет ни ссылки, ни намёка.

**4. При каждом входе менеджер тянет список диалогов дважды.**
`ChatListPane` монтируется вместе с `AppLayout`, эффекты потомка выполняются раньше эффекта родителя, а `filters` в сторе на этот момент — `DEFAULT_FILTERS = { tab: "all" }` (`chatUiStore.ts:65`, `:82`). Запрос уходит с `tab=all` (`frontend/src/features/chats/api.ts:29`), затем `useRoleUiSync` ставит `tab: "mine"` (`useRoleUiSync.ts:34` → `chatUiStore.ts:127`), меняется ключ кэша (`ChatListPane.tsx:195`) и уходит второй запрос. Ролей `admin/head/observer` это не касается: у них умолчание совпадает.

**5. Пять действий над диалогом в шапке ленты — только иконки.**
`ThreadActions` рисует булавку, «вернуть в очередь», «позвать коллегу», «передать», «пометить нежелательным» без подписей; подписи возвращаются подсказкой при наведении с задержкой 400 мс (`frontend/src/features/chats/components/thread/ThreadActions.tsx:59-148`). Для первого дня это ряд из пяти неизвестных значков рядом с единственной подписанной кнопкой «Закрыть».

### Где человек встанет без подсказки коллеги

* **Шаг 5 → 6.** Ничто на экране не говорит, что работа начинается с «Входящих». Счётчик у вкладки появляется только при непустой очереди (`ChatListPane.tsx:472-476`), а единственная кнопка ведёт в другой список.
* **Шаг 6 при пустой очереди.** Отличить «всё разобрано» от «вам ничего не приходит» по экрану нельзя, а проверить самому негде: `/settings/accounts` закрыт правом `accounts:read`, которого у менеджера нет (`app/core/rbac.py:48-58`, маршрут — `frontend/src/app/router.tsx:143`).
* **Шаг 5, если человек пошёл «Посмотреть новые».** Почему в списке чужие каналы и уже отклонённые им обращения — из интерфейса не следует ничем.

Действующие лица: оператор А (принимает и отвечает) и оператор Б (получает передачу).

### Карта шагов

| Шаг | Кто | Что делает | Что видит и сколько ждёт | Кликов | Трение |
|---|---|---|---|---|---|

### Точки трения

**1. Тост о передаче утверждает то, чего не произошло, и называет не того человека.**
Передача другому сотруднику — это предложение: ответственный не меняется, пока получатель не согласится (`app/services/conversations.py:987` внутри `assign_conversation`, механизм — `app/services/transfer.py:82-106`). Ручка возвращает свежую деталь диалога, где `assignee` — по-прежнему передающий (`app/api/routes/conversations.py:790`). Фронт берёт это поле и печатает «Ответственный: …»:

```
frontend/src/features/chats/hooks/useConversationActions.ts:143-149
  title: "Диалог передан",
  message: res.conversation.assignee
    ? `Ответственный: ${res.conversation.assignee.full_name}`
```

Оператор А видит «Диалог передан. Ответственный: Александр Иванов», где Александр Иванов — он сам, и одновременно полосу «Ждёт подтверждения: Борис» в двухстах пикселях ниже.

**2. Получателю сообщают о свершившейся передаче и подставляют его ответственным до согласия.**
Кадр `conversation:assigned` несёт `assignee` = тот, КОМУ предложили (`app/api/routes/conversations.py:740-757`), а обработчик записывает это значение прямо в строку списка и показывает тост «Диалог передан вам»:

```
frontend/src/shared/realtime/applyWsEvent.ts:589-598
  patchRowEverywhere(..., { transferred_to_me: true, assignee: e.data.assignee })
  showToast({ title: "Диалог передан вам", ... })
```

То есть у Б в списке диалог числится за ним ещё до того, как он нажал «Принять», а текст не оставляет ему понимания, что от него чего-то ждут. Зелёный тон тоста у события, которое успехом не является, — уже описан как NOTIF-03 в `docs/29-AUDIT-STEP1-SCREENS.md:652`.

**3. Истечение предложения не видит никто.**
Через 15 минут `expire_transfers` снимает предложение и публикует `conversation:updated` с `patch.transfer = null` (`app/scheduler/jobs/reclaim.py:262-274`). Фронт применяет патч молча (`frontend/src/shared/realtime/applyWsEvent.ts:580-582`): полоса «Ждёт подтверждения» просто исчезает у А, и он остаётся с диалогом, который считал отданным. У Б, если он в это время не смотрел на экран, не остаётся ничего, кроме прочитанного уведомления, ведущего в диалог без кнопок.

**4. Закрытие диалога не снимает висящее предложение передачи.**
`change_status` трогает `outcome`, `status`, автораздачу и «ждёт ответа», но `transfer_svc.clear(conv)` не вызывает (`app/services/conversations.py:789-891`; ближайшая ветка закрытия — `:876-877`, `clear_awaiting(conv)`). `accept_transfer` статуса тоже не проверяет (`app/api/routes/conversations.py:503-530`), а `transfer.accept` меняет `new → in_progress` и только (`app/services/transfer.py:133-141`). Итог: А передал, потом закрыл диалог сам — Б до 15 минут видит на **закрытом** диалоге полосу «А передаёт вам диалог» с рабочей кнопкой «Принять», а нажав её, становится ответственным за закрытое обращение. Внизу при этом стоит «Диалог закрыт. Вернуть в работу» (`frontend/src/features/chats/components/composer/Composer.tsx:273-289`) — полоса и подвал говорят разное.

**5. В окне «Чем закончилось обращение?» порядок чтения обратен порядку действий.**
Пять кнопок результата стоят сверху, поле «Сумма заказа, ₽» — под ними (`OutcomeModal.tsx:41-86`). Клик по «Выезд назначен» немедленно отправляет форму с тем, что уже введено в поле (`OutcomeModal.tsx:49-51`), и окно закрывается (`frontend/src/features/chats/components/thread/ChatThreadPane.tsx:515-518`). Кто прочитал окно сверху вниз и нажал результат первым, теряет возможность указать сумму: вернуться в это окно можно только через повторное открытие, а диалог уже закрыт. Речь о единственной денежной величине в системе. Смежные дефекты этого окна — CHATS-10 и M9 в `docs/29-AUDIT-STEP1-SCREENS.md:16` и `:227`.

### Где человек встанет без подсказки коллеги

* **Шаг 8.** После «Передать» А получает три разных ответа на вопрос «отдал или нет»: тост говорит «передан», полоса — «ждёт подтверждения», лента — «предложен». Какой из них правда, из интерфейса не выводится.
* **Шаг 9 → 10.** Диалог, который Б «передали», не лежит ни в «Моих», ни во «Входящих». Если тост пропущен, единственный путь — колокольчик, и об этом нигде не написано.

## Сценарий 3. Клиент вернулся через неделю

Возврат бывает двух видов, и они ведут себя по-разному.

**Вид А — тот же чат Авито (клиент пишет по тому же объявлению).** Диалог был закрыт, входящее переоткрывает его: `status → new`, `assignee_id → None`, диалог заново встаёт в очередь со свежим `offered_at`, прошлые отказы обнуляются (`app/services/inbound.py:289-312`).

### Точки трения

**1. Два готовых признака повторности посчитаны сервером и не выведены никуда.**
`GET /conversations/{id}` отдаёт `client_conversations_count` (число диалогов этого клиента) и `first_client_at` (когда клиент написал впервые) — `app/services/conversations.py:672-690`. Оба поля объявлены во фронтовом типе (`frontend/src/shared/api/types.ts:212-213`) и не используются ни в одном компоненте: `grep` по `frontend/src`, кроме тестов, даёт ровно эти две строки объявления. Ровно на них строится ответ «повторный ли клиент», и ровно их на экране нет. Дублирование имён при доработке уже отмечено в `docs/30-TZ-CROSS-CLIENT.md:729` (пункт D4) — заводить второе поле не нужно, достаточно вывести существующее.

**2. Уведомление «Клиент вернулся в закрытый диалог» объявлено и не порождается.**
Описано в `docs/28-AUDIT-STEP0-INVENTORY.md:2407`. Подтверждаю по коду: `KindSpec` есть (`app/services/notifications.py:326-332`), значок и подпись есть (`frontend/src/features/notifications/catalog.ts:95`), а `notify(kind="conversation.reopened")` не вызывается нигде — все совпадения строки в `app/` относятся к одноимённому действию журнала аудита.

**3. Диалоги, приехавшие импортом истории, в очередь не встают, хотя комментарий обещает обратное.**
При подключении аккаунта Авито чаты заводятся со статусом `closed` (`app/services/avito_accounts.py:594-614`, строка 608: `status="closed",  # решение №3: история — в архив`), а чат с непрочитанным поднимается из архива:

```
app/services/avito_accounts.py:775-778
  if chat.has_unread and conv.status == "closed":
      # в чате реально ждут ответа — поднять из архива в очередь (решение №3)
      await _reopen_conversation(db, conv, client_row)
```

`_reopen_conversation` (`app/services/avito_accounts.py:651-670`) ставит `status="new"` и `assignee_id=None`, но `inbox.enter_queue` не зовёт и `offered_at` не трогает — во всём файле нет ни одного упоминания `enter_queue` или `offered_at`. Предикат очереди требует `offered_at IS NOT NULL` (`app/services/inbox.py:131-142`), поэтому такой диалог не попадает ни во «Входящие», ни в чьи-либо «Мои»: он виден только на вкладке «Все». Ни звука, ни бейджа. Комментарий «поднять из архива в очередь» описывает поведение, которого у кода нет. Путь сверки (`reconcile_account`) этим не задет — он идёт через `apply_inbound_event`, где `enter_queue` вызывается (`app/workers/reconciliation.py:186`, `app/services/inbound.py:296`).

**4. Признак «диалог ждёт принятия» приходит в детали, а два комментария в коде утверждают, что не приходит.**
`in_inbox`, `offered_at` и `escalated` кладутся в **каждый** диалог, включая деталь: `conversation_out` (`app/services/conversations.py:253-255`) — база и для строки списка, и для `conversation_detail` (`conversations.py:638`, строка 656: `out = conversation_out(...)`). При этом:

* `frontend/src/features/chats/inbox/useIsQueued.ts:16-18` — «`GET /conversations/{id}` полей очереди не отдаёт вовсе — на детали `in_inbox` просто нет»;
* `frontend/src/shared/api/types.ts:151-155` — «обычный список и деталь их не несут вовсе».

Работать это не мешает (запасной путь через стор даёт тот же ответ), но следующий, кто будет чинить очередь, начнёт с ложной картины. Отдельно: соседний комментарий в `frontend/src/features/chats/inbox/InboxDecisionBar.tsx:19` называет клавиши «Ctrl+Enter и Ctrl+Backspace», тогда как основным сочетанием принятия давно является Ctrl+R (`useChatHotkeys.ts:167-171`, `catalog.ts:23`), а Ctrl+Enter оставлен синонимом (`useChatHotkeys.ts:202-206`).

**5. Сквозной клиент между каналами держится на одном допущении, которое в репозитории не подтверждено.**
Сегодня клиент — это строка `clients` с уникальностью `(channel, external_id)`, где `external_id = str(event.author_id)` (`app/services/inbound.py:114-123`). Если Авито отдаёт один и тот же `author_id` при обращении к разным нашим аккаунтам, повторный клиент опознаётся между каналами сам собой; если нет — «История клиента» будет молчать даже там, где человек уже обращался. Проверить это по репозиторию нельзя, и то же зафиксировано во встречной критике ТЗ: `docs/30-TZ-CROSS-CLIENT.md:576-589` (пункт B1).

   расхождение «Новые диалоги» против «Принято» уже разобрано — п. 9
   `docs/33-AUDIT-STEP2-DEFECTS.md`.

3. **Кнопка «Диалоги ↗» ведёт туда, где вчерашнего не видно.**
   `StatsPage.tsx:114-117` кладёт `{tab: "all", assigneeId}` и уходит на `/chats`.
   Вкладка «Все» по умолчанию режет закрытые: `app/services/conversations.py:369` —
   `Conversation.status != "closed"`. Вчерашние разобранные диалоги закрыты, значит
   руководитель увидит пустоту или чужой текущий поток. Дата в фильтры не попадает
   физически: в типе `ConversationFilters` (`frontend/src/shared/api/queryKeys.ts:21-28`)
   полей периода нет. Родственная беда «пришёл по ссылке — слева пусто» разобрана в
   п. 2 `docs/33-AUDIT-STEP2-DEFECTS.md`.

4. **Тот, кто не ответил вообще, в рейтинге «кто тормозил» стоит внизу.**
   `app/services/stats.py:991` — `ORDER BY {sort} {order} NULLS LAST`. Медиана первого
   ответа у менеджера без единого ответа — `NULL`, при сортировке «по убыванию» он
   уезжает в конец списка, туда же, где самые быстрые. В ячейке при этом прочерк
   (`frontend/src/features/stats/lib/format.ts:16`), но позиция в таблице говорит
   обратное. Число «без ответа» в системе есть — и показано только в тексте всплывающей
   подсказки одной общей карточки (`SummaryCards.tsx:96`), не по людям.

5. **Метка свежести молчит именно тогда, когда важна.**
   `formatRefreshedAt` печатает только часы и минуты, без даты и без «сколько назад»
   (`frontend/src/features/stats/lib/format.ts:47-59`), а сама строка рисуется только
   если метка есть (`StatsFilters.tsx:133-141`). Метку пишет ежечасный job
   (`app/scheduler/jobs/stats.py:62-67`, расписание `CronTrigger(minute=5)` — там же :100).
   Отсюда два исхода. Планировщик стоит с ночи — метка застыла на «Данные на 03:05», и
   в три часа дня она выглядит как обычная строка, отличить её от свежей можно только
   сверив с часами на стене. Redis почистили — `refreshed_at` приходит `null`
   (`app/services/stats.py:602-609`), и строка исчезает совсем; экран при этом
   продолжает показывать цифры.

6. **Пояснение «обновляется раз в час» спрятано в тултипе** (`StatsFilters.tsx:134`) —
   то есть доступно наведением мышью и недоступно с клавиатуры и скринридера.

|---|---|
| Пресеты «Вчера»/«Сегодня» в `/dialogs` и единое определение периода с `/stats` (календарные сутки МСК в обоих) | 3 |
| Серверная сортировка по времени первого ответа: вынести `first_response_sec` в витрину/колонку с индексом либо ввести фильтр «первый ответ дольше N минут», считаемый по всей выборке | 5 |

| Метка свежести: дата + «N мин назад», предупреждение при возрасте больше 90 минут | 2 |

### Точки трения

1. **Подписка Jivo заменяется молча и без спроса.** Авито держит на аккаунт ровно одну

2. **Посмотреть, кто подписан сейчас, из интерфейса нельзя, а докстринг обещает

   ПОДКЛЮЧЕНИЯ… здесь же аккаунт трогать не нужно: достаточно ключей приложения»

   расшифровывает его токен (`:186-193`). Значит спросить «кто подписан» можно только
   после подключения, то есть после того, как чужая подписка уже сброшена. Комментарий
   описывает свойство, которого у кода нет.

3. **Провал регистрации вебхука не отменяет зелёный тост.** Исключение внутри
   `register_webhook` проглатывается целиком (`avito_connect.py:476-478`), ответ всё

   объявлениям пойдут в «Чаты»» (`ConnectChannelWizard.tsx:138-142`). Настоящее
   состояние (`Webhook: ✗ сбой`) появится только на карточке после обновления списка
   (`AccountsPage.tsx:54-90`). Про два противоречащих значка в этой же строке — п. 11
   `docs/33-AUDIT-STEP2-DEFECTS.md`.

4. **Обещание «Загружаем историю чатов…» не выполняется никогда.** Функция постановки
   задачи `enqueue_backfill` объявлена (`app/services/avito_accounts.py:526-543`) и не
   вызывается ни из одного места приложения (grep по `app/` даёт только само

   знает: тост после возврата с Авито по-прежнему говорит «Загружаем историю чатов…»

5. **Из трёх заготовленных вспомогательных ручек не выведена ни одна.** «Проверить
   связь» `POST /avito/app/check` (`avito_connect.py:321`), «ссылка владельцу аккаунта»

   переподключение идёт через `POST /avito-accounts/{id}/reconnect` (`:167-170`). Ещё

## Сценарий 6. Истёк токен Авито

> **Уточнение владельца от 11 августа.** `client_id` и `client_secret` Авито
> выдаёт один раз и не меняет. Следовательно, состояние «требует
> переподключения» для аккаунта на ключах недостижимо по смыслу: переподключать
> нечем и незачем. Всё, что реально приводит канал в это состояние, —
> временная недоступность Авито, то есть ложный диагноз. Вывод раздела от этого
> усиливается: ветку нужно не уточнять, а убирать для аккаунтов на ключах.



### Как устроено на самом деле

Токен живёт сутки, планировщик обновляет его за два часа до конца, проверяя каждые
30 минут (`app/scheduler/main.py:137`, `app/services/avito_accounts.py:490-520`).
Статус `needs_reauth` ставится **только** в момент неудачной попытки обновления
(`avito_accounts.py:435` для аккаунтов со своими ключами, `:471` для подключённых
через согласие). Все аккаунты, заведённые нынешним мастером, — со своими ключами
(`connect_with_keys`, `:305-308`), значит рабочая ветка — первая.

### Карта шагов

| Шаг | Что происходит | Что видит человек | Клики | Трение |
|---|---|---|---|---|
| 1 | Планировщик не смог обновить токен | ничего | 0 | — |
| 2 | Ставится `needs_reauth`, публикуется WS-кадр | Красный тост **только у тех администраторов, кто прямо сейчас в системе** | 0 | Кадр без `id` → в колокольчик не попадает |
| 3 | Оператор отвечает клиенту | 409 и красная плашка «Аккаунт Авито отключён — отправка невозможна» | 1 (после набора текста) | Узнаёт после того, как написал; ссылки «сообщить админу» нет |
| 4 | Администратор открывает `/settings/accounts` | Карточка красная, «Требует переподключения» | 2 | — |
| 5 | Жмёт «🔄 Переподключить» | Уход на avito.ru, вход под учёткой канала, возврат | 1 + вход | **Для аккаунта со своими ключами это лечит на один день** |

**Итого: 3 клика администратора от входа до кнопки — если он вообще узнал, что чинить.**

### Точки трения

1. **Уведомление о протухшем токене не сохраняется нигде.** В каталоге центра вид
   объявлен: `app/services/notifications.py:185-192` — `account.needs_reauth`,
   важность «критично», кнопка «Переподключить». Производителя у него нет: поиск по
   `app/` даёт только это объявление, подпись фронта
   (`frontend/src/features/notifications/catalog.ts:76`) и обработчик кнопки
   (`app/services/avito_accounts.py:1038-1081`). Оба места, где статус реально
   меняется, публикуют эфемерный WS-кадр: `avito_accounts.py:466-480` (тип `notify`,
   без `id`) и `:474-478` / `app/workers/deliver.py:256-266` (тип
   `account:needs_reauth`). Кадр без `id` показывается тостом и исчезает
   (`frontend/src/features/notifications/wsNotify.ts:26`), второй — тоже тост
   (`frontend/src/shared/realtime/applyWsEvent.ts:605-613`). Ночью, в выходной или
   просто при закрытой вкладке об этом не узнаёт никто, а утром в журнале
   `/notifications` нет ни строки.

2. **Обрыв связи с Авито останавливает канал так же, как отзыв доступа.**
   `avito_accounts.py:431-435`: `except (AvitoApiError, OSError)` → `status =
   "needs_reauth"`. `AvitoUnavailable` (сеть, DNS, таймаут) — наследник `AvitoApiError`
   (`app/integrations/avito/errors.py:44-66`), то есть тридцатисекундная недоступность
   Авито даёт тот же результат, что и отозванные ключи, с текстом «ключи приложения
   больше не принимаются» (`avito_accounts.py:448`). Сравните с веткой для аккаунтов
   на согласии — там отзыв опознаётся отдельным типом `TokenRevokedError` и только он
   ведёт к `needs_reauth` (`:459-478`).

3. **Из `needs_reauth` система сама не выходит никогда.** Планировщик перебирает
   только активные: `avito_accounts.py:501-505` — `where(AvitoAccount.status ==
   "active")`. Сверка пропущенных пропускает такой аккаунт
   (`app/workers/reconciliation.py:110`), отправка отбивается сразу
   (`app/services/messages.py:236-240`). Значит ложное срабатывание из пункта 2
   останавливает боевой канал до тех пор, пока человек не нажмёт кнопку.

4. **Кнопка на карточке лечит не ту болезнь.** У статуса `needs_reauth` показывается
   единственное действие — «🔄 Переподключить» (`AccountsPage.tsx:429-448`), оно ведёт
   в OAuth. Возврат с Авито ставит новые токены и статус `active`
   (`avito_connect.py:571-577` → `avito_accounts.py:250-266`), но **не трогает
   `client_id`/`client_secret_enc`**. При следующем плановом обновлении
   `refresh_tokens` снова видит ключи (`avito_accounts.py:427-429`) и снова идёт с
   ними — то есть канал вернётся в `needs_reauth` в течение суток. Настоящее лечение —
   ввести новые ключи в том же мастере подключения, но карточка этого не предлагает,
   а мастер на такой ввод отвечает жёлтым «Это тот же аккаунт, что уже подключён»
   (`ConnectChannelWizard.tsx:127-137`) — текст, который читается как отказ, хотя это
   и есть успешная починка.

5. **Оператор узнаёт последним и не может ничего сообщить.** Плашка в композере
   считается из ошибки уже отправленного запроса
   (`frontend/src/features/chats/components/composer/Composer.tsx:270` и `:295-304`),
   то есть появляется после того, как ответ набран. Ссылка «Переподключить» в ней
   показана только при праве `accounts:manage` (`:298-302`) — у тринадцати диспетчеров его
   нет. Про то, что набранный текст при провале отправки затирается, — находка M2 в
   `docs/29-AUDIT-STEP1-SCREENS.md`.

### Если планировщик не работает

Проверено по коду, что именно перестаёт происходить:

* обновление токена не запускается вовсе (`app/scheduler/main.py:137`), срок молча
  уходит в прошлое, статус остаётся `active` — карточка продолжает утверждать «Токен:
  активен» (разбор строки и формата даты — п. 11 `docs/33-AUDIT-STEP2-DEFECTS.md`);
* первым признаком становится отказ отправки у оператора: `assert_sendable`

  поэтому сообщение создаётся и падает уже в Авито

* сторож «приём остановился» тоже живёт внутри планировщика
  (`app/scheduler/jobs/watchdog.py:663-670`, запуск `:734`) — значит не сработает;
* самопроверка живости честно называет себя ограниченной: «сам себя планировщик
  проверить не может» (`watchdog.py:436-441`);

### Что предлагаю

| Работа | Часы |

## Сценарий 7. Два оператора в одном диалоге

Сначала честный ответ на главный вопрос: **механизма «диалог занят» в системе нет.**
Ни блокировки, ни признака «его уже кто-то открыл», ни индикатора «коллега печатает».
Есть три частных механизма, и работают они по-разному.

### Карта шагов

| Шаг | Что делает | Что видит A (ответственный) | Что видит B | Клики | Трение |
|---|---|---|---|---|---|
| 1 | Оба открыли `/chats/<id>` | Обычная лента | Обычная лента | по 1 | Ни один не знает о другом |
| 2 | B смотрит шапку | — | «Парт-7 · +7… · **Иванов И.**» | 0 | Имя ответственного стоит третьим в ряду метаданных без подписи (`ChatThreadPane.tsx:322`) |
| 3 | Оба пишут ответ | Своё сообщение, затем чужое | То же зеркально | по 1 | Клиент получает два ответа; предупреждения нет |
| 4 | B нажимает «Взять» — если диалог в очереди | Строка исчезла из очереди | «Диалог уже занят · Диалог принял Иванов И.» | 1 | **Обработано правильно** |
| 5 | B нажимает «Взять» — если диалог уже за A | Такой кнопки нет | Такой кнопки нет | — | Менеджер не может забрать чужой диалог вовсе; администратор — может, молча |
| 6 | Оба закрывают | Окно результата, диалог закрыт | 422 и тост «Статус не изменился · Этот статус уже стоит» | по 2 | Выбранный B результат обращения теряется, кто закрыл — не сказано |

### Что действительно работает

* **Принятие из очереди атомарно.** Один `UPDATE … WHERE claimed_by_id IS NULL AND
  assignee_id IS NULL AND status <> 'closed'` с проверкой числа затронутых строк
  (`app/services/inbox.py:653-670`), проигравший получает `409` с именем победителя, и
  интерфейс показывает «Диалог принял N» и переводит к следующему
  (`frontend/src/features/chats/inbox/useInbox.ts:68-73`, `:122-128`). Оптимистичного
  захвата намеренно нет (`:84-85`).
* **Все меняющие статус и назначение ручки берут строчную блокировку**
  (`app/services/conversations.py:623-635`, вызовы — `app/api/routes/conversations.py:658`
  и `:685`), отправка тоже (`app/services/messages.py:389`). Потерянных обновлений в
  базе не будет.
* **Живая синхронизация есть.** Сообщение коллеги, смена статуса и ответственного
  прилетают по WebSocket и применяются к открытой ленте
  (`frontend/src/shared/realtime/applyWsEvent.ts:567-583`). То есть двое видят действия
  друг друга — но задним числом, уже как факт.
* **Счётчик непрочитанного персональный**: маркер `read:{user_id}` в Redis,
  `conversations.unread_count` не трогается, кадр уходит только своим вкладкам
  (`app/api/routes/conversations.py:623-643`). Руководитель, заглянувший в чужую
  переписку, не гасит бейдж оператору.

### Чего нет

1. **Никто не видит, что диалог открыт вторым человеком.** Кадр `subscribe`, который
   привязывает сессию к диалогу, и кадр `typing` сервер принимает
   (`app/ws/hub.py:236-254`), но клиент не отправляет ни одного из них: единственная
   исходящая строка в `WsClient` — это `ping`
   (`frontend/src/shared/realtime/WsClient.ts:90`). Отсюда следует и второе:
   `session.conversation_id` навсегда остаётся `None`, поэтому фильтр доставки
   `d.get("conversation_id") == cid` (`hub.py:192-194`) не пропустил бы кадр `typing`
   даже если бы его кто-то послал. На фронте `typing` числится в объединении типов
   (`frontend/src/shared/realtime/wsEvents.ts:80`) и попадает в `default`-ветку
   разбора, то есть игнорируется (`applyWsEvent.ts:621-623`).

2. **Ответ в чужой диалог разрешён и ничем не помечен.** `ThreadFooter` показывает
   полный композер всякому, у кого есть `messages:send`, если диалог не стоит в очереди
   (`frontend/src/features/chats/components/composer/ThreadFooter.tsx:44-61`). Сервер
   переназначения не делает: `_auto_assign` трогает `assignee_id` только когда он пуст
   (`app/services/messages.py:287-288`). Значит второй оператор пишет клиенту от своего
   имени, а диалог, статистика первого ответа и «Мои» остаются за первым.

3. **«Забрать себе» у администратора проходит молча.** В `assign_conversation`
   двухфазная передача включается только когда получатель не равен инициатору
   (`app/services/conversations.py:984-987`); выбор себя в селекте «Ответственный»
   (`ClientCardPane.tsx:371-381`) идёт мимо неё и меняет ответственного немедленно.
   Прежний ответственный узнаёт об этом системной строкой в ленте — если смотрит на неё.

4. **Одновременное закрытие теряет работу второго.** Второй получает `422 same_status`
   (`app/services/conversations.py:814-820`), интерфейс откатывает оптимистичное
   изменение и показывает «Статус не изменился · Этот статус уже стоит»
   (`useConversationActions.ts:79-88`). Проблема не в отказе, а в том, что к этому
   моменту человек уже выбрал результат обращения и, возможно, ввёл сумму заказа
   (`OutcomeModal.tsx:41-53`, `:77-84`) — всё это отбрасывается, а в тосте не сказано ни
   кто закрыл, ни с каким результатом. Само окно результата при чужом закрытии не
   закрывается: `setOutcomeOpen(false)` вызывается только по подтверждению
   (`ChatThreadPane.tsx:512-517`).

5. **Присутствие людей есть, но не в диалоге.** `PUT /presence` работает
   (`app/api/routes/presence.py:50`, вызов —
   `frontend/src/features/presence/usePresence.ts:42`), однако показывается только в
   списке сотрудников `/settings/team`
   (`frontend/src/features/settings/team/TeamMembersTab.tsx:50-63`), доступном админу и
   руководителю. Рядом — ещё один комментарий, описывающий несуществующее свойство:
   «Серверного `PUT /api/v1/presence` в API нет»
   (`frontend/src/platform/index.ts:121`).

### Что предлагаю

| Работа | Часы |
|---|---|
| Включить уже написанный протокол: клиент шлёт `subscribe` при открытии диалога и `typing` при наборе; в шапке — «здесь же: Пётр С.» и «Пётр печатает…». Серверная часть готова (`app/ws/hub.py:236-254`), нужен клиент и отображение | 8 |
| Композер не-ответственного: строка «Диалог ведёт Иванов И.» над полем + кнопка «Забрать себе», отправка без неё требует подтверждения | 4 |
| Конфликт закрытия: в ответе `422` возвращать, кто и когда закрыл и с каким результатом, показывать это в тосте; окно результата закрывать по WS-кадру о смене статуса | 3 |

## Чего проверить не смог

* Живого входа в интерфейс нет — числа кликов посчитаны по обработчикам, а не сняты с
  экрана. Расхождение возможно на выпадающих списках Mantine с поиском (`searchable`),
  где выбор может стоить лишнего клика или ввода.
* Не проверял на боевом Авито, что `POST /messenger/v3/webhook` возвращает при уже
  существующей чужой подписке: код разбирает только HTTP-статус
  (`app/services/avito_accounts.py:149-167`), тела ответа не читает.
* Не измерял длительность `REFRESH MATERIALIZED VIEW` на боевых объёмах — порог
  деградации в 2–3 минуты объявлен (`app/scheduler/jobs/stats.py:21-22`), фактических
  замеров в репозитории нет.
* Не могу подтвердить, что крон внешнего наблюдателя на <IP наблюдателя> установлен и
  работает: скрипт `deploy/watchdog-offsite.sh` в репозитории есть, факт установки из
  репозитория не виден. От этого зависит, узнает ли кто-нибудь об остановке
  планировщика.
* Гонку двух операторов вживую не воспроизводил (нужны две учётные записи) — выводы
  сделаны по коду блокировок, обработчиков и WS-кадров.
* Не проверял, доходит ли WS-тост о `needs_reauth` до десктоп-клиента иначе, чем до
  браузера: путь `toastForNotification` работает только для строк центра
  (`frontend/src/features/notifications/wsNotify.ts:63-66`), а кадр без `id` до него не
  доходит; поведение самого клиента Tauri не проверял.
* Число строк и диалогов на проде не измерял: оценки «страница 50 строк» взяты из кода
  (`frontend/src/features/table/TablePage.tsx:35`), не из данных.
