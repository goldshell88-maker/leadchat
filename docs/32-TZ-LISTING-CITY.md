### Дефект 1. Адаптер читает форму, которой на боевом Авито, судя по нашему же имитатору, нет

`app/integrations/avito/adapter.py:156-171` — `_extract_item(value)` пробует ровно две формы:
1. `value["item"]` — вложенный объект;
2. `value["context"]` при `context["type"] == "item"` → `context["value"]`.

`item_id` скаляром **не читается вовсе**. А в докстринге нашего имитатора, `fake_avito/main.py:29-32`, написано:

```
"item_id": 1234567890,         // только у чатов с объявлением
"item": {"id": …, "title": …,  // расширение мока: реальный Авито шлёт
         "price_string": …,    // только item_id — адаптер обязан уметь

```

и `fake_avito/main.py:319-321` действительно кладёт в вебхук **и** `item_id`, **и** полный `item`. Адаптер написан под расширение мока, а не под то, что мок сам объявляет боевым форматом. Это третье повторение ловушки из `docs/26`: имитатор, написанный по нашим догадкам, подтвердил наши догадки.

Оговариваю честно: утверждение «боевой шлёт только item_id» — тоже наше, из нашего же файла. Проверяется за минуту, см. unknowns №1.

## Чего мы не знаем

* ЧТО РЕАЛЬНО ЛЕЖИТ В БОЕВОМ ВЕБХУКЕ. Есть ли в `payload.value` ключ `item_id`, ключ `item`, ключ `context` — по коду не выводится. Наш имитатор шлёт и `item_id`, и `item`, а его собственный докстринг (fake_avito/main.py:29-32) утверждает, что боевой шлёт только `item_id`, — это наше предположение, записанное как факт. Проверяется одним запросом к проду, данные есть с 8 августа: SELECT count(*) FILTER (WHERE payload->'payload'->'value' ? 'item_id') AS с_item_id, count(*) FILTER (WHERE payload->'payload'->'value' ? 'item') AS с_item, count(*) FILTER (WHERE payload->'payload'->'value' ? 'context') AS с_context, count(*) FILTER (WHERE payload->'payload'->'value'->>'chat_type'='u2i') AS u2i FROM webhook_raw_log WHERE payload->'payload'->>'type'='message'; плюс SELECT jsonb_pretty(payload) ... ORDER BY received_at DESC LIMIT 3. Это ПЕРВОЕ, что надо сделать: от ответа зависит, нужна ли дозагрузка карточки вообще или хватит синхронного пути.
* ФОРМА `context` В ОТВЕТЕ GET /messenger/v2/accounts/{uid}/chats НА БОЕВОМ. Наш код (adapter.py:156-171) берёт из `context.value` ключи `title`, `url`, `price_string`/`price`. Проверяется одним запросом с боевым токеном.
* ЕСТЬ ЛИ КАРТИНКА ОБЪЯВЛЕНИЯ В ОТВЕТЕ ЧАТА И В КАКОМ ПОЛЕ. Миниатюра требуется в 10.4. По коду и каталогу неизвестно ничего. Если её нет — блок рисуется без миниатюры, макет это переживает; выдумывать имя поля нельзя.
* РАБОТАЕТ ЛИ НА БОЕВОМ ОДИНОЧНЫЙ GET /messenger/v2/accounts/{uid}/chats/{chat_id}. В каталоге он есть (docs/26, строка 68), но у нашего имитатора его НЕТ, и client_enrich.py:69-79 уже ходит по нему вслепую с запасным путём через список чатов. * ЧТО ПРИХОДИТ ПО СНЯТОМУ ОБЪЯВЛЕНИЮ. Остаётся ли `item_id`, приходит ли заголовок, не превращается ли чат в `u2u`. От этого зависит, отличим ли мы «снято» от «объявления не было» — а на этом стоит весь пункт 10.3 «удалённое не терять».

Это меняет архитектуру шага, поэтому проверять надо ДО начала работ.
* ФОРМАТ ПУБЛИЧНОЙ ССЫЛКИ НА ПРОФИЛЬ КЛИЕНТА (пункт 10.6). См. подробный разбор в proposal §7: по коду мы располагаем только числовым `author_id`, а публичного маршрута, который из него собирается, ни в каталоге, ни в коде нет. Спросить у владельца; до ответа справочник наполняется по факту встреченных слагов, а незнакомые пишутся в лог.

## §1. СХЕМА БД — миграция `0024_listings_and_city`

```sql
-- ============================================================ listings
-- ТЕКУЩЕЕ состояние объявления. Обновляется; снимок для истории живёт
-- в conversations (см. ниже) и не переписывается никогда.
CREATE TABLE listings (
    item_id           bigint       PRIMARY KEY,
    -- Аккаунт, на котором объявление увидели ВПЕРВЫЕ. Не единственный:
    -- все пары «объявление × аккаунт» лежат в listing_accounts.
    avito_account_id  uuid         NOT NULL REFERENCES avito_accounts(id) ON DELETE CASCADE,

    title             text,
    -- Категория и город — НОРМАЛИЗОВАННЫМИ полями, а не разбором на чтении.
    category_slug     text,
    category_name     text,
    city_slug         text,
    city_name         text,
    region            text,

    url               text,
    price             text,        -- строкой: Авито отдаёт «от 1 500 ₽», а не число
    image_url         text,

    -- Откуда взялся заголовок. 'url' рисует в интерфейсе пометку
    -- «восстановлен из ссылки» (требование 10.2).
    title_source      text         NOT NULL DEFAULT 'api'
                                   CHECK (title_source IN ('api', 'url')),

    first_seen_at     timestamptz  NOT NULL DEFAULT now(),
    last_seen_at      timestamptz  NOT NULL DEFAULT now(),

    -- Снятое объявление НЕ УДАЛЯЕМ (10.3): строка остаётся, гаснет флаг.
    is_active         boolean      NOT NULL DEFAULT true,
    inactive_since    timestamptz,

    -- Сырьё ровно в том виде, в каком его дал Авито. Когда форма чужого
    -- API прояснится (unknowns 1-5), перечитаем ЭТО, а не полезем в сеть
    -- за тем, что уже получали.
    raw_payload       jsonb        NOT NULL DEFAULT '{}'::jsonb
);

CREATE INDEX ix_listings_city     ON listings (city_slug) WHERE city_slug IS NOT NULL;
CREATE INDEX ix_listings_account  ON listings (avito_account_id);
CREATE INDEX ix_listings_active   ON listings (is_active, last_seen_at DESC);
-- Подсказки в фильтре «Объявление ▾» ищутся по началу слова, регистр не важен.
CREATE INDEX ix_listings_title_trgm ON listings USING gin (lower(title) gin_trgm_ops);
-- ^ требует CREATE EXTENSION IF NOT EXISTS pg_trgm; если расширение недоступно,
--   индекс не создаётся и фильтр падает на ILIKE-префикс по ix_listings_city.

-- =================================================== listing_accounts
-- Одно объявление, увиденное на двух наших аккаунтах (случай 10.8).
-- Без этой таблицы второй аккаунт молча перетирал бы первый в listings.
CREATE TABLE listing_accounts (
    item_id           bigint       NOT NULL REFERENCES listings(item_id) ON DELETE CASCADE,
    avito_account_id  uuid         NOT NULL REFERENCES avito_accounts(id) ON DELETE CASCADE,
    first_seen_at     timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (item_id, avito_account_id)
);

-- ====================================================== conversations
-- СНИМОК на момент обращения. Пишется один раз, при первом сообщении
-- диалога, и не переписывается никогда — иначе переименование объявления
-- задним числом перепишет отчёт за прошлый квартал (10.8).
ALTER TABLE conversations
    ADD COLUMN item_id            bigint,
    ADD COLUMN item_city_slug     text,
    ADD COLUMN item_city_name     text,
    ADD COLUMN item_category_name text;

-- FK на listings НАМЕРЕННО НЕТ: диалог может знать item_id раньше, чем мы
-- успели завести карточку объявления, и вебхук не должен ждать похода в
-- чужой API. Ссылочную целостность держит задача дозагрузки, а не база.
CREATE INDEX ix_conversations_item_id
    ON conversations (item_id) WHERE item_id IS NOT NULL;
-- Фильтр «Город» в /chats и /dialogs идёт вместе с сортировкой по свежести.
CREATE INDEX ix_conversations_city_last
    ON conversations (item_city_slug, last_message_at DESC) WHERE item_city_slug IS NOT NULL;
```

**Почему снимок дублирует listings.** Две причины, и вторая важнее первой. (1) `/dialogs` и статистика фильтруют и группируют по городу на 454 тысячах строк — JOIN на каждую строку списка мы уже однажды отвергли (шапка `conversation_table.py`). (2) Требование 10.8 прямое: перенос объявления в другой город не должен переписывать прошлое. Одна таблица не может одновременно быть «текущим состоянием» и «неизменным снимком».

**Почему `item_id bigint`, а не text.** В примере из задания `8213779975` — 10 знаков, в мока́х встречаются 10-значные. `int4` кончается на 2 147 483 647, то есть уже мал. `bigint` берётся с запасом; парсер отвергает всё, что не влезло, и пишет в лог, а не роняет диалог.

**Downgrade.** `0024` роняет две таблицы и четыре колонки. Обратима полностью до первого прогона наполнения; после — теряет снимки, поэтому в шапке миграции это написано прямым текстом.

## §3. РАЗБОР ССЫЛКИ (10.2) — `app/integrations/avito/listing_url.py`

Чистая функция, ни сети, ни базы, ни исключений наружу.

```
СТРУКТУРА ListingUrlParts:
    item_id: int | None
    city_slug / city_name / region: str | None
    category_slug / category_name: str | None
    title_slug: str | None
    kind: 'item' | 'brand' | 'user' | 'short' | 'foreign' | 'garbage'
    ok: bool

ФУНКЦИЯ parse_listing_url(raw: str | None) -> ListingUrlParts
  ПУСТО = ListingUrlParts(всё None, kind='garbage', ok=False)
  если raw пусто или len(raw) > 2048 -> вернуть ПУСТО
  s = raw.strip()
  если не начинается с 'http://' и не с 'https://' -> s = 'https://' + s
  попробовать u = urlsplit(s); при ValueError -> вернуть ПУСТО
  если u.hostname пуст -> вернуть ПУСТО

  host = u.hostname.lower()
  host = снять_префикс(host, 'www.'); host = снять_префикс(host, 'm.')
  если host не в ДОМЕНЫ_АВИТО -> вернуть ПУСТО с kind='foreign'
      # ДОМЕНЫ_АВИТО = {'avito.ru', 'avito.st', 'ru.avito.ru'}
      # Проверка по РАЗОБРАННОМУ hostname, а не подстрокой: 'avito.ru.evil.com'
      # содержит 'avito.ru' и должен отвергаться.

  # Query и якорь отбрасываются целиком: там ходят метки рекламы, и ничему
  # оттуда доверять нельзя.
  сегменты = [x for x in unquote(u.path).split('/') if x]
  если сегменты пусты -> вернуть ПУСТО

  # --- item_id: ПОСЛЕДНЯЯ группа цифр в ПОСЛЕДНЕМ сегменте, регуляркой.
  # Не по позиции сегмента: у /kerch/predlozheniya_uslug/slug_8213779975 он
  # третий, у /items/3060161080 — второй, у короткой ссылки — первый.
  m = ПОСЛЕДНИЕ_ЦИФРЫ.search(сегменты[-1])      # r'(\d{6,})(?!.*\d)'
  item_id = int(m.group(1)) если m иначе None
  если item_id и item_id > 9_223_372_036_854_775_807 -> item_id = None  # не влез в bigint

  # --- особые маршруты
  если сегменты[0] == 'brands'  -> kind='brand'
  иначе если сегменты[0] == 'user' -> kind='user';  item_id = None   # это профиль, не объявление
  иначе если сегменты[0] in ('company', 'agencies') -> kind='user'; item_id = None
  иначе если len(сегменты) == 1 и сегменты[0] — только цифры -> kind='short'
  иначе если item_id -> kind='item'
  иначе -> kind='garbage'

  # --- город: ТОЛЬКО по справочнику, никакой транслитерации
  если kind in ('item','brand') и len(сегменты) >= 2:
      cand = сегменты[0]
      если cand в СЛУЖЕБНЫЕ_ПЕРВЫЕ_СЕГМЕНТЫ ('items','catalog','web','api','brands','user'):
          city_slug = None
      иначе:
          city_slug = cand
          город = ГОРОДА.get(cand)
          если город: city_name, region = город.name, город.region
          иначе: city_name = None
                 log.info('listing.unknown_city_slug', slug=cand, url=raw)   # справочник растёт по факту

  # --- категория: второй сегмент, тем же правилом
  если city_slug и len(сегменты) >= 3:
      category_slug = сегменты[1]
      category_name = КАТЕГОРИИ.get(category_slug)      # нет — оставляем None, слаг храним
      если category_name is None: log.info('listing.unknown_category_slug', slug=category_slug)

  # --- заголовок из слага: ТОЛЬКО когда API не дал title (решает вызывающий)
  если kind == 'item' и len(сегменты) >= 1:
      title_slug = сегменты[-1] без хвоста '_<item_id>'

  вернуть ListingUrlParts(..., ok = item_id is not None)
```

**Справочник** — `app/integrations/avito/geo.py`: `ГОРОДА: dict[str, City]`, `City(name, region)`. Стартовый набор — слаги из задания и все, что встретятся на проде: `kerch → Керчь / Республика Крым`, `moskva → Москва`, `moskva_i_mo → Москва и МО`, `sankt-peterburg → Санкт-Петербург`, `rostov-na-donu → Ростов-на-Дону`, `nizhniy_novgorod → Нижний Новгород`, `ekaterinburg`, `novosibirsk`, `kazan`, `simferopol`, `sevastopol`, `krasnodar`, `sochi`. **Транслитерация запрещена явно, тестом:** `rostov-na-donu` обратной транслитерацией даёт «Ростов На Дону», `moskva_i_mo` — «Москва И Мо», и человек видит мусор в отчёте.

**Восстановление заголовка из слага.** `remont_televizorov_i_nastroyka_kanalov_s_vyezdom` → подчёркивания в пробелы, первая буква заглавная. Это **латиница**, читаемая, но не русская: показывать её как настоящее название нельзя. Поэтому `title_source='url'` и в интерфейсе рядом стоит серым «восстановлен из ссылки».

**Тесты парсера — минимум 20 кейсов, каждый называет, что проверяет:**
1. канонический пример из задания → item_id=8213779975, city='kerch'/'Керчь', category='predlozheniya_uslug';
2. `m.avito.ru/...` — мобильный хост;
3. `http://` без TLS;
4. без `www.`;
5. `?utm_source=...&context=H4sI...` — query отброшен, id тот же;
6. `#comments` — якорь отброшен;
7. `avito.ru/3060161080` — короткая ссылка: id есть, города нет, kind='short';
8. `avito.ru/items/3060161080` — форма без слага (встречается в наших же моках);
9. `/brands/xxx/remont_8213779975` — kind='brand', id извлечён;
10. `/user/a7f3.../profile` — kind='user', **item_id обязан быть None**, иначе профиль попадёт в объявления;
11. слаг с цифрами в середине: `remont_iphone_13_pro_max_8213779975` → берётся ПОСЛЕДНЯЯ группа, не «13»;
12. неизвестный слаг города `zazerkalye` → city_slug сохранён, city_name=None, запись в лог;
13. `rostov-na-donu` → «Ростов-на-Дону» (проверка, что не транслитерация);
14. `moskva_i_mo` → «Москва и МО»;
15. `https://avito.ru.evil.com/kerch/x_1` → kind='foreign', ничего не извлечено;
16. `https://ozon.ru/...` → kind='foreign';
17. `None` и `''` → ПУСТО, без исключения;
18. строка 5000 символов → ПУСТО, без исключения;
19. `https://` без хоста, `avito.ru` без пути, `://///` → ПУСТО;
20. кириллица в пути в percent-encoding → разбирается после unquote;
21. `..._99999999999999999999999` (не влезает в bigint) → item_id=None, kind='garbage', в лог;
22. property-тест: 500 случайных строк из ASCII+кириллицы — функция **ни разу не бросает**.

**`GET /stats/cities` — тело ответа и честный знаменатель:**

```json
{"period": {...},
 "rows": [{"city_slug":"kerch","city_name":"Керчь","region":"Республика Крым",
           "conversations":48,"answered":45,"unanswered":3,
           "frt_median_sec":214,"frt_median_biz_sec":190,
           "outcomes_set":31,"outcome_visit":19,"outcome_declined":8,
           "conversion_pct":61.3}],
```

Два решения, которые обязаны быть в задании явно:
* **`conversion_pct` считается от `outcomes_set`, а не от `conversations`.** Исход проставляется руками при закрытии; считай мы от всех — город, где диспетчер аккуратен, выглядел бы хуже города, где исходы не ставят вовсе. Поэтому `outcomes_set` едет в ответе рядом и **показывается в таблице отдельной колонкой**: цифра, у которой не видно знаменателя, врёт.
* **`no_city` — строка «Город не определён»** внизу таблицы, а не тихо выброшенные диалоги. Пока unknowns не закрыты, таких будет много, и прятать их — значит рисовать красивый отчёт по половине данных.

SQL опирается на `mv_conversation_stats` (`s`) с `JOIN conversations c ON c.id = s.conversation_id`, группировка по `c.item_city_slug`, `LEFT JOIN` не нужен. Витрину **не перестраиваем**: тот же приём уже применён в экспорте (`stats.py:1456-1470`) ради названия объявления, и мотив там записан.

## §6. МАКЕТЫ ТЕКСТОМ (10.4)

**Шапка диалога** — новая третья строка, кликабельная, `target="_blank" rel="noopener noreferrer"`:

```
[←] Иван Петров                          [Передать] [Закрыть] [⋯]
    +7 900 111-22-41 · ждёт 4 мин
    Керчь · Ремонт телевизоров и настройка каналов ↗
```

Правила: город впереди названия — оператор сначала решает «мой ли это город», потом «что за услуга». Строка обрезается многоточием, полное название — в `title`. Нет объявления — строки нет вовсе (пустой слот хуже отсутствия). В Tauri ссылка перехватывается тем же `bridge.openExternal`, что и в правой карточке (`ClientCardPane.tsx:83-102`) — компонент `ExternalLink` выносится в `shared/ui/`.

**Правая карточка**, блок «Объявление» вместо нынешних двух строк:

```
┌ Объявление ─────────────────────────────────┐
│ ┌──────┐  Ремонт телевизоров и настройка    │
│ │ фото │  каналов с выездом, замена…        │
│ │64×64 │  от 1 500 ₽                        │
│ └──────┘  Керчь · Предложения услуг         │
│           Открыть на Авито →                │
└─────────────────────────────────────────────┘
```

Состояния блока:
* *миниатюры нет* — плитка-заглушка с иконкой, ширина не скачет;
* *заголовок восстановлен из ссылки* — под названием серым 11px: «восстановлен из ссылки»;
* *объявление снято* — жёлтая плашка внизу: «Объявление снято 3 августа», ссылка остаётся (она ведёт на страницу «объявление снято», и это честнее битой кнопки);
* *объявление изменилось* — серым: «На момент обращения: Симферополь · Ремонт телевизоров»;
* *грузится* — скелетон в три полосы, не спиннер;
* *не загрузилось* — «Не удалось загрузить объявление» + «Повторить»; **уже известные из снимка название и город показываются, а не прячутся**.

**Строка списка чатов.** Сейчас `{канал} · {объявление} · {ответственный}` (`ConversationListItem.tsx:200-202`). Город приклеивается к объявлению **одним полем**, слотов по-прежнему три:

```
Сергей · Керчь · Ремонт телевизоров · Пётр И.
            └──── одно поле, заменяет «без объявления» ────┘
```

Нет города — «Ремонт телевизоров». Нет ничего — «без объявления», как сейчас.

**`/dialogs`.** Колонка «Город» встаёт **между** «Канал» и «Объявление» — читается слева направо как «откуда пришло → где → про что». ## §7. ПРОФИЛЬ КЛИЕНТА (10.6) — ФИЧА В ЗАДУМАННОМ ВИДЕ НЕВОЗМОЖНА

**Что приходит.** Единственный идентификатор клиента — `payload.value.author_id`, целое число (`adapter.py:372`), которое ложится в `clients.external_id` строкой (`inbound.py:114`, `models/client.py:19`). В ответе чата — `users[].id` и `users[].name` (`adapter.py:394-404`); больше из `users[]` не читается **ничего**, и схемы этого массива в каталоге `docs/26` нет — там только пути и права.

**Почему ссылку нельзя собрать.** `author_id` — внутренний идентификатор мессенджера. Публичной страницы вида `avito.ru/<число>` у продавца/покупателя нет; публичный профиль живёт по маршруту с непрозрачным ключом, а сопоставления «число → ключ» нет ни в каталоге, ни в коде, ни в наших сырых payload'ах. **Собрав ссылку по догадке, мы дадим оператору кнопку, ведущую в 404 — ровно тот сценарий, который в этом проекте уже случался дважды.** Формат не изобретаем.

**Что честно предложить вместо.**

1. **Блок «Клиент на Авито» в правой карточке — без ссылки:**
```
┌ Клиент на Авито ──────────────────────────┐
│ Иван Петров                               │
│ ID 923456789                       [копия]│
│ 4 обращения по 2 каналам с 12 июля        │
│ Показать все →                            │
└───────────────────────────────────────────┘
```
Число обращений и переход — на уже существующем `GET /conversations/{id}/client-history` (`conversations.py:742`), сегодня спрятанном в подвале карточки. Ценность та же, что задумывалась («кто это и что у нас с ним было»), и она достижима без чужого API.

2. **Заготовка на будущее — одна функция.** `app/integrations/avito/profile.py::client_profile_url(client, account) -> str | None`, сегодня **всегда возвращает None**. Интерфейс рисует ссылку только при непустом ответе. Подтвердится формат (unknowns №7) — правка одной функции, фронт и API уже готовы. Заведомо возвращающая None функция с тестом «сегодня None и это осознанно» честнее закомментированного кода.

3. **Проверка, которая закрывает вопрос за час** — на боевом аккаунте: `GET /messenger/v2/accounts/{uid}/chats/{chat_id}` и глазами посмотреть, что лежит в `users[]`. Если там окажется готовое поле со ссылкой или хешем — фича делается за 2 часа, и они не входят в оценку ниже.

**Уточнение по 10.8 «клиент без профиля»:** клиента, у которого нет имени, мы уже показываем как «Клиент» (`ChatThreadPane.tsx:303`). Блок «Клиент на Авито» в этом случае показывает только ID и историю — и это не пустое состояние, а нормальное.

Появление второй пары пишет `log.warning('listing.seen_on_second_account')` — по коду мы не знаем, законно ли это (unknown №9), и молчать о нём нельзя. В /dialogs фильтр по каналу и фильтр по объявлению независимы, так что «это объявление, но только по каналу Олег» выражается. Удаление одного из каналов уносит по `ON DELETE CASCADE` строку связи, а карточка живёт, пока жив первый аккаунт; если удаляют именно его — карточка уходит вместе с ним, и это приемлемо, потому что переписка по решению от 8 августа стирается тем же действием. |
| Заголовок 90+ символов (пример из задания — 96) | Обрезается ТОЛЬКО при показе, в базе лежит целиком. Шапка диалога — одна строка с многоточием и полным текстом в `title`. Правая карточка — до двух строк (`-webkit-line-clamp:2`), дальше многоточие; полный текст в `title`. Строка списка — общий `lc-truncate` на всю вторую строку, объявление обрезается после канала и города, то есть первым исчезает наименее важное. /dialogs — существующий класс `dt__ell--wide` + `title`. CSV — полностью, без обрезки: файл открывают в Excel и там читают. Тест: заголовок в 300 символов не ломает вёрстку ни на 390px, ни на 1920px. |
| Клиент без профиля / без имени | Имя и так может отсутствовать (вебхук его не несёт — это записано в `types.ts:74`), фолбэк «Клиент» уже есть. Новый блок «Клиент на Авито» показывает ID и историю обращений; ссылки нет ни у кого (см. §7), поэтому «клиент без профиля» ничем не отличается от остальных и отдельного пустого состояния не требует. |
| Нет сети при подгрузке карточки объявления | Три уровня, ни один не даёт пустоты. (1) Снимок (`item_title`, `item_url`, `item_city_name`) лежит в самом диалоге и приходит вместе с ним — он показывается всегда, даже когда Авито недоступен. (2) Задача `enrich_conversation` при `AvitoApiError`/таймауте пишет warning и завершается успешно — она идемпотентна, следующее сообщение в этом чате поставит её снова; ARQ-ретраев не заводим, чтобы не долбить чужой API. (3) Фронт: пока карточка не пришла — скелетон; если запрос упал — «Не удалось загрузить объявление» + «Повторить», при этом снимок остаётся на экране. Категорически не допускается: спиннер вместо уже известного названия и исчезновение блока при ошибке. |
| Ссылка битая, чужая или отсутствует | `parse_listing_url` возвращает `ok=False` и НИКОГДА не бросает (property-тест на 500 случайных строк). Чужой домен — `kind='foreign'`, город и категория не заполняются, ссылка в интерфейс не выводится вовсе: кнопка «Открыть на Авито», ведущая на ozon.ru, хуже её отсутствия. `item_id` без ссылки — карточка живёт, город пуст, диалог попадает в строку «Город не определён». |
| Незнакомый слаг города или категории | `city_slug` сохраняется как есть, `city_name` остаётся NULL, пишется `log.info('listing.unknown_city_slug', slug=…, url=…)`. В интерфейсе показывается сам слаг моноширинно (`kerch-2`) — это читаемо и сразу видно, что справочник надо пополнить. Раз в неделю логи просматриваются и справочник растёт по ФАКТИЧЕСКИМ данным, а не по нашим представлениям о географии заказчика. |
| Пришёл только item_id, ничего больше | Наиболее вероятный боевой случай (unknown №1). `conversations.item_id` заполняется синхронно, ставится задача `enrich_conversation`; до её выполнения строка списка показывает «без объявления» — как сейчас, то есть хуже не становится. После выполнения — всё на месте. Если чат Авито не отдаёт вовсе, в `listings` заводится строка-заглушка `title=NULL, title_source='api'`, а интерфейс показывает «Объявление №8213779975» со ссылкой, собранной... — НЕТ: ссылку из голого id не собираем (тот же запрет, что в §7). Показывается «Объявление №8213779975» без ссылки. |
| Чат без объявления (u2u) | `extract_item_ref` возвращает None молча, без предупреждения: это законное состояние, а не сбой. Диалог живёт с `item_id IS NULL`, в списке — «без объявления», в срезе — строка «Город не определён». Предупреждение пишется только для `chat_type='u2i'` без единого признака объявления — вот это уже подозрительно и должно быть видно в логе. |
| Цена приходит числом, строкой или не приходит | Хранится строкой (`price text`), как и сейчас: Авито отдаёт «от 1 500 ₽», и превращать это в число значит терять «от». Число приводится к строке (`_price_str` уже так делает, `adapter.py:150-153`). Пусто — строка цены в карточке не рисуется, а не рисуется как «0 ₽» или «—». |
| Два вебхука по одному чату подряд — гонка задач обогащения | Дедуп ARQ по `_job_id=f"enrich:{conversation_id}"` — приём уже применён в `client_enrich.py:48`. Внутри задачи фаза 1 выходит немедленно, если и имя, и объявление уже известны. `upsert_listing` берёт `SELECT … FOR UPDATE` по `item_id`, вставка в `listing_accounts` — `ON CONFLICT DO NOTHING`. Повторный запуск ничего не портит и не дублирует. |
| Обращение из города, где компания не работает | В этой задаче — НИЧЕГО, кроме того, что город виден. Предупреждение «город вне зоны» и распределение по городу вынесены отдельными задачами по требованию 10.5 и в оценку не входят. Важное следствие для схемы: справочник «наши города» — это НЕ `listings.city_slug`, и заводить его сейчас нельзя, потому что списка городов у нас нет (unknown №8). |
| Отключение канала (стирание переписки) | `ON DELETE CASCADE` уносит `listings` и `listing_accounts` вместе с аккаунтом — согласовано с решением от 8 августа («отключаем — стираем историю»). Проверить и вписать в тест: удаление аккаунта не должно падать на внешнем ключе и не должно задевать объявления соседнего канала — их держит собственная строка в `listing_accounts` и собственный `avito_account_id`, если он на них указывает. Если первый аккаунт удаляют, а второй остаётся — карточка уходит; это осознанная потеря справочных данных, переписка по ней всё равно стёрта. |
| Город или название с разделителем CSV | Пишем через `csv.writer` с `delimiter=';'` — экранирование уже его забота (`conversation_table.py:263`). Отдельно проверить тестом название с `;`, кавычкой и переводом строки: «Ремонт ТВ; выезд» не должен разъезжаться на две колонки. |
| Диалог создан до выкатки — снимка нет | Ремонтный прогон `backfill-listings` заполняет, что может: по `item_url` из снимка — без сети вообще; по `item_id` или chat_id — одним запросом с соблюдением лимитера. Чего не смог — остаётся с прочерком, и это честно: чат месячной давности Авито может уже не отдать. Прогон резюмируем (прогресс в Redis, как у прежнего backfill), падение на середине не требует начинать заново. |

## Порядок, обратимость, dry-run

### Шаг 0 — ДО единой строки кода: проверить формат на боевом (0.5 ч)

Сырьё уже есть на проде, `webhook_raw_log` держит 30 дней, с 8 августа прошло 33 входящих:

```sql
SELECT count(*) AS всего,
       count(*) FILTER (WHERE payload->'payload'->'value' ? 'item_id') AS с_item_id,
       count(*) FILTER (WHERE payload->'payload'->'value' ? 'item')    AS с_item,
       count(*) FILTER (WHERE payload->'payload'->'value' ? 'context') AS с_context,
       count(*) FILTER (WHERE payload->'payload'->'value'->>'chat_type' = 'u2i') AS u2i
FROM webhook_raw_log
WHERE payload->'payload'->>'type' = 'message';

SELECT jsonb_pretty(payload) FROM webhook_raw_log
WHERE payload->'payload'->>'type' = 'message'
ORDER BY received_at DESC LIMIT 3;
```

Плюс один запрос с боевым токеном к `GET /messenger/v2/accounts/{uid}/chats?limit=1` — посмотреть настоящую форму `context`.

**Результат вписывается в `docs/26-AVITO-API-CATALOG.md` до начала работ.** Если окажется, что боевой вебхук несёт полный `item`, ярус 2 из горячего пути превращается в редкий запасной, и часть оценки высвобождается. Если окажется, что не несёт даже `item_id`, — единственным ключом становится `chat_id`, и ярус 2 становится обязательным для каждого нового диалога. Оба исхода схему не меняют, меняют только частоту походов в Авито. Ради этого схема и построена так.

### Шаг 1 — миграция `0024_listings_and_city`: ТОЛЬКО схема

Две новые таблицы, четыре колонки в `conversations`, четыре индекса. **Ни одной строки данных не пишет и не читает.** На боевом объёме (`conversations` — десятки тысяч строк, `454 000` ожидаются позже) `ALTER TABLE … ADD COLUMN` с NULL-умолчанием — операция на метаданных, доли секунды, без переписывания таблицы. Индексы создавать `CONCURRENTLY` **не нужно** на нынешнем объёме; в шапке миграции записать, что при возврате к этой правке на четырёхсоттысячной базе — нужно.

`downgrade` полный: `DROP TABLE listing_accounts, listings` + `ALTER TABLE conversations DROP COLUMN …`. Обратимость честная **до первого прогона наполнения**; после отката теряются снимки города и категории, а `item_title/url/price` не трогаются — они были и до нас. Это написано в шапке миграции прямым текстом, чтобы никто не откатил «безопасно» вторым заходом.

### Шаг 2 — код бэкенда: пишет новое, читает по-старому

Выкатывается отдельно от фронта. Новые поля заполняются, API их уже отдаёт, но старый фронт их игнорирует — совместимость сохраняется, потому что `item` в ответе только **дополняется** ключами, а `title/url/price` остаются на месте.

Проверка после выкатки, до фронта: написать в боевой канал с телефона по объявлению → убедиться, что `SELECT item_id, item_city_name FROM conversations ORDER BY id DESC LIMIT 1` непусто. **Настоящий канал, настоящее объявление, а не имитатор.** Имитатор в этой задаче доказательством не является — он ровно тот, кто дважды подтвердил наши ошибки.

### Шаг 3 — наполнение: ОТДЕЛЬНАЯ КОМАНДА, НЕ МИГРАЦИЯ

```
python -m app.cli backfill-listings [--dry-run] [--account <uuid>] [--since YYYY-MM-DD] [--limit N]
```

Почему не в миграции: наполнение ходит в чужой API, ограничено лимитером, длится минуты и может упасть на середине. Миграция обязана быть быстрой, детерминированной и не зависеть от чужой доступности. Ровно эта ошибка уже стоила проекту семисуточного «Загружаем историю…» (шапка `backfill_account`).

**`--dry-run` (по умолчанию — да; писать заставляет явный `--apply`)** печатает и НИЧЕГО не меняет:
```
Диалогов без item_id ................. 87
  из них есть item_url ............... 12   → разберутся без сети
  из них можно спросить у Авито ...... 75   → 75 запросов
  из них чат старше 30 дней .......... 41   → Авито может не отдать
Оценка: 75 запросов, ~4 мин при текущем лимите bulk-контура
Будет заведено объявлений (оценка) ... до 63
Изменений НЕ внесено (--dry-run)
```

Прогон резюмируем: прогресс в Redis `backfill_listings:{account_id}`, повтор дублей не создаёт (все записи — upsert), падение продолжается с последнего диалога. Идти по одному аккаунту: сначала «Сергей», проверить глазами десяток строк, потом «Олег».

### Откат наполнения — один запрос, без миграции

```sql
BEGIN;
UPDATE conversations
   SET item_id = NULL, item_city_slug = NULL,
       item_city_name = NULL, item_category_name = NULL;
TRUNCATE listing_accounts, listings;
COMMIT;
```
`item_title/item_url/item_price` **не трогаются**: они существовали до этой задачи, и стереть их значило бы откатить чужую работу. Записать этот запрос в `docs/RUNBOOK-DEPLOY.md` рядом с задачей.

### Шаг 4 — фронт

Шапка, карточка, строка списка, две колонки и два фильтра в /dialogs, фильтр «Город» в /chats, две таблицы в статистике. Выкатывается последним: до него данные уже правильные, и любая беда на этом шаге откатывается сборкой фронта, не трогая базу.

### Шаг 5 — сторож «снято»

Суточная задача `refresh_listings` включается **через неделю после наполнения**, не раньше: пока справочник наполняется, «объявление не отдалось» слишком часто означает нашу собственную недоделку, а не снятие с публикации. Раньше срока она наставит ложных «снято».

### Что должно упасть, если задача сделана неправильно (охранные тесты)

1. `parse_webhook` на payload'е **без** `item`, но **с** `item_id` → `item_id` извлечён. Сломай `extract_item_ref` — тест обязан покраснеть.
2. Второе сообщение в диалоге, у которого `item_title IS NULL`, а событие несёт название → название дописалось (проверка ремонта дефекта 2).
3. Второе сообщение с **другим** названием при уже заполненном → название **не** изменилось (проверка неизменности снимка).
4. Смена города в `listings` → цифра `GET /stats/cities` за прошлый период не сдвинулась.
5. Список слагов в `SORTABLE`/фильтрах фронта совпадает с серверным — тем же приёмом, что уже охраняет `SORTABLE` в `frontend/src/features/table/api.ts`.
6. Property-тест: `parse_listing_url` на 500 случайных строк не бросает ни разу.

По правилу из `HANDOFF-2026-08-09`: каждый из шести написан, потом **код намеренно сломан**, и проверено, что тест краснеет. Тест, который зеленеет на сломанном коде, в этом проекте уже случался трижды за два дня.

## ПЕРЕДЕЛАТЬ (по убыванию опасности)

### 1. Второй угаданный контракт: грамматика ссылки Авито. В unknowns его нет

Весь §3 стоит на утверждении «первый сегмент пути — город, второй — категория, id — последняя группа цифр последнего сегмента». Этого нет ни в `docs/26`, ни в коде, ни в наших данных — и, в отличие от вебхука, **проверить это по своей базе нельзя**: `item_url` пуст ровно потому, что фича сломана. Задание само требует такое писать в unknowns прямым текстом, и само же этого не сделало.

Хуже того, задание пускает непроверенную догадку **до глаз оператора и в группировку статистики**: неизвестный слаг сохраняется в `city_slug`, показывается моноширинно и попадает в срез «Обращения по городам». Это ровно та ловушка, что дважды стоила проекту 4xx, только результат тише: не ошибка, а красивый отчёт по выдуманной географии.

**Как переделать.**
* Добавить unknown: «Грамматика публичной ссылки Авито: правда ли первый сегмент — город, а второй — категория; бывают ли региональные и общероссийские слаги (`/rossiya/`, `/all/`). Проверяется глазами по 10 живым `item_url` после того, как ярус 1 их наполнит».
* Разделить парсер на две очереди доверия: **`item_id` из ссылки — можно сейчас** (по нему нечему разъехаться); **город и категория — только после проверки**.
* Неизвестный слаг **не становится `city_slug`**: пишется в `city_slug_raw` (или только в лог), `city_slug` остаётся NULL, диалог честно уходит в «Город не определён». Слаг попадает в справочник и в `city_slug` **после того, как человек его подтвердил**, а не потому, что он стоял первым в пути.
* Пока доля «города нет + слаг неизвестен» выше, скажем, 20 %, у таблицы «Обращения по городам» стоит подпись «данные неполные: N обращений без города».

### 2. Ярус 1 нереализуем как написан

```
services/inbound.apply_inbound_event:
    ref = extract_item_ref(сырое_событие)        # уже разобрано адаптером
```

Сырого события там нет и быть не может: `apply_inbound_event(db, redis, account, event: InboundEventLike)` (`inbound.py:241-249`), а протокол `InboundEventLike` (`inbound.py:53-65`) — это четыре атрибута и два свойства, никакого `raw`. Сырьё живёт только в воркере (`workers/inbound.py:216-231`). Комментарий «# уже разобрано адаптером» и вызов `extract_item_ref` в одной строке противоречат друг другу.

**Как переделать.** Правильный вариант — тот, что уже описан в §2: `extract_item_ref` вызывается **в адаптере**, а `InboundEvent` получает поле `item_id: int | None`. Тогда `_touch_item(conv, event)` работает с нормализованным событием и не знает о чужом формате ничего. В §4 переписать соответственно.

**И два забытых места, которые придётся править вместе с `InboundEvent`:**
* `FallbackInboundEvent` (`workers/inbound.py:48-63`) и `_fallback_parse_webhook` (`:74-100`) — резервный разбор на случай отсутствия адаптера; там своя копия `item_*` и своё чтение `value["item"]`. Не тронешь — резервный путь молча теряет объявление, то есть у нас снова два разных контракта в двух файлах.
* `InboundEvent.item_info` (`adapter.py:85,92-96`) — мёртвое поле, не читается нигде. Раз уж лезем — убрать, а не дописывать в него `item_id`.

### 3. `_touch_item` встанет после проверки дубля — и сверка ничего не починит

`apply_inbound_event` выходит на `if msg is None: return False` (`inbound.py:268-269`) **до** любых правок полей диалога. Если ремонт полей поставить туда, куда его кладёт §4 (после `_upsert_conversation`, но в общем потоке), надо помнить: **все повторы — ретрай вебхука и сверка — уходят раньше**. А сверка (`workers/reconciliation.py:176-187`) гоняет ровно повторы: для старого диалога, где новых сообщений нет, она не починит ничего.

**Как переделать.** `_touch_item` вызывать **сразу после `_upsert_conversation`, до `_insert_message_idempotent`**. Тогда сверка становится вторым бесплатным путём ремонта — и половина ремонтного прогона делается сама. В тестах-охранниках это надо закрепить отдельным кейсом: «повторная доставка того же сообщения с объявлением дописывает пустое поле».

### 4. `_job_id` столкнётся с существующей задачей — и обогащение молча не поставится

Задание пишет: «Дедуп ARQ по `_job_id=f"enrich:{conversation_id}"` — приём уже применён в `client_enrich.py:48`». Он не «применён» — **он занят**: `enqueue_enrich_client` ставит job с ровно этим id (`client_enrich.py:44`). ARQ дедуплицирует **по job_id, а не по имени функции**. Плюс `WorkerSettings` (`app/workers/main.py:61-85`) не задаёт `keep_result`, то есть действует умолчание ARQ — час: **в течение часа после отработавшего `enrich_client` любая постановка с тем же id отбрасывается без единой записи в лог**.

Итог по типовому сценарию: первое сообщение → задача тянет имя → отработала; второе сообщение через 10 минут → ставим «обогащение объявления» с тем же id → **тишина**, ничего не выполнится, и снаружи это неотличимо от «Авито не дал объявление».

**Как переделать.** Не заводить `enrich_conversation`. §4 сам говорит «это расширение существующей client_enrich» — так и сделать: одна задача `enrich_client` тянет за один запрос имя **и** объявление, фаза 1 выходит, только если известно и то, и другое. Один job_id, одна функция, ноль новых запросов к Авито. Заодно минус регистрация задачи в воркере и минус целый блок часов.

Если всё же нужны две задачи — id обязан быть разным (`enrich_item:{id}`), и это надо написать явно, потому что молчаливый дедуп через час — то, что ищут в три часа ночи дольше всего.

### 5. `SELECT … FOR UPDATE` не спасает от гонки вставки

```
row = SELECT ... FROM listings WHERE item_id = ref.item_id FOR UPDATE
если row нет: INSERT ...
```

`FOR UPDATE` по строке, которой нет, **не блокирует ничего**. Два диалога по одному новому объявлению → две задачи → обе видят пусто → обе INSERT → вторая получает нарушение уникальности, транзакция задачи падает. На SQLite юнит-тестов это не воспроизведётся никогда.

**Как переделать.** `INSERT … ON CONFLICT (item_id) DO UPDATE SET …` через существующий `_dialect_insert` (`inbound.py:95-103`) — тот же приём, что уже держит `_upsert_client` и `_insert_message_idempotent`. Кейс в интеграционных тестах на настоящем PG.

### 6. DDL не в стиле проекта и не поднимется в юнит-тестах

* **Имена ограничений.** В проекте жёсткий `naming_convention` (`app/models/base.py`): `pk_%(table_name)s`, `fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s`, `ix_%(column_0_label)s`, `ck_…`. Голый DDL задания (`item_id bigint PRIMARY KEY`, инлайновые `REFERENCES`, `CHECK (…)`) даст автоимена PostgreSQL (`listings_pkey`, `listings_avito_account_id_fkey`) — и метаданные моделей навсегда разойдутся с базой. В миграции все имена выписать явно.
* **Юнит-тесты строят схему из моделей на SQLite** (`tests/unit/conftest.py:35` — `Base.metadata.create_all`, `tests/conftest.py:12` — `sqlite+aiosqlite://`). Значит: `raw_payload` — через `app/models/types.JSONB`, а не `postgresql.JSONB`; частичные индексы — через `postgresql_where`; **а индекс `gin (lower(title) gin_trgm_ops)` в модели уронит `create_all` на SQLite** (класс операторов SQLite не знает). Его надо либо объявлять только в миграции, либо — см. «выбросить».
* **`pg_trgm` в проекте нет** — в 0001 создаётся только `citext`. «Если расширение недоступно, индекс не создаётся» — это недетерминированная миграция; такого в схеме быть не должно. И утешение «фильтр падает на ILIKE-префикс по `ix_listings_city`» бессмысленно: индекс по городу поиску по названию не помогает ничем.
* **Ремарка про `ALTER TABLE … ADD COLUMN`** верна, а вот «индексы CONCURRENTLY не нужны» стоит уточнить: `CREATE INDEX` берёт блокировку, запрещающую запись, а пишет в `conversations` inbound-конвейер непрерывно. На нынешнем объёме это доли секунды — так и написать, вместо «операция на метаданных».
* **Downgrade нигде не проверяется.** Интеграционные тесты гоняют только `alembic upgrade head` (`tests/integration/conftest.py:61-77`). Раз задание обещает обратимость — добавить в охранные тесты `upgrade → downgrade → upgrade` для 0024. Иначе обещание ничем не подкреплено.

### 7. Каскад при отключении канала описан неверно

Задание: «`ON DELETE CASCADE` уносит `listings` и `listing_accounts` вместе с аккаунтом — согласовано с решением от 8 августа». Решение от 8 августа реализовано **не удалением аккаунта**: «Отключить» вызывает `purge_history` (`avito_connect.py:673`), которая стирает сообщения и диалоги, **а строку аккаунта не трогает** (`avito_accounts.py:170-210`). Каскад сработает только на настоящем удалении канала (`avito_connect.py:811-812`).

Следствие: после отключения канала переписка стёрта, а `listings` этого канала остались — и торчат в подсказках фильтра «Объявление ▾» и в срезе по городам вечно, без единого диалога за ними.

Отдельно замечу: докстринг `purge_history` — это разбор ровно такой же ошибки, сделанной в этом же файле («Каскада нет: у `conversation_participants` и `conversation_pins` он есть, а у `messages` — `NO ACTION`. На проде отключение канала падало с „Внутренняя ошибка сервера“»). Повторять её в задании нельзя.

**Как переделать.** В `purge_history` явно удалять `listings`, у которых после чистки не осталось ни одного диалога (или просто по `avito_account_id`), с тем же комментарием и **интеграционным тестом на PG** — на SQLite внешние ключи не проверяются вовсе, там это не видно.

### 8. `is_active` в строке списка противоречит собственному доводу

§1 обосновывает снимок тем, что JOIN на каждую строку списка мы уже однажды отвергли. §5 кладёт в строку `GET /conversations` поле `is_active` — а оно живёт только в `listings`, то есть требует того самого JOIN. **Убрать из списка**: в строке достаточно снимка (`item_id`, `city_name`, `title`). Признак «снято» нужен в карточке и, может быть, в `/dialogs` — там JOIN оправдан, он уже есть.

### 9. Обратимость теряется на шаге 2, а не на шаге 3

«Обратима полностью до первого прогона наполнения» — неверно: как только выкачен бэкенд (шаг 2), снимки начинают копиться с боевых вебхуков. Откат после шага 2 уже теряет данные.

И «откат наполнения одним запросом» — это `UPDATE conversations SET item_id = NULL …` **по всей таблице**, то есть переписывание каждой строки и раздувание, причём стирает не только результат бэкфилла, но и всё, что приехало живыми вебхуками. Как минимум `WHERE item_id IS NOT NULL`, и в RUNBOOK назвать это честно: «откат всего наполнения», а не «откат прогона».

### 10. Цена ремонтного прогона посчитана в предположении, которое сами же записали в unknowns

Dry-run печатает «75 запросов, ~4 мин» — это верно, **только если работает одиночный `GET …/chats/{chat_id}`** (unknown №4, никогда не проверенный на боевом). Если там 404, включается запасной путь `client_enrich`: **две страницы списка чатов на КАЖДЫЙ диалог** (`client_enrich.py:82-95`) — 87 диалогов × 2 страницы = 174 запроса по 100 чатов, и это уже не «4 минуты».

**Как переделать.** Для бэкфилла запасной путь должен быть другим по устройству: **один проход по списку чатов на аккаунт** (страницами до конца), сопоставление всех нужных `chat_id` за проход. Это O(всего чатов / 100) запросов вместо O(диалогов). И в `--dry-run` печатать обе оценки — «если одиночный чат работает» и «если нет».

### 11. Мелкое, но чинится одной строкой

* **CSV.** Вставка «Города» в середину меняет порядок колонок (`CSV_HEADER`, `conversation_table.py:218-230`) и ломает чужие формулы. Добавить **в конец** — стоит столько же, не ломает ничего, и не нужно предупреждать владельца.
* **Фильтр «Город».** У диалогов до выкатки `item_city_slug IS NULL`; при выбранном городе они исчезнут молча. В выпадашке нужен явный пункт «Город не определён» — не только в статистике.
* **Один город под двумя слагами** (`moskva` и `moskva_i_mo`) раздвоит строку в отчёте. Справочник должен уметь склеивать слаг → канонический город, а группировка идти по каноническому ключу, а не по слагу.
* **`avito.st` в списке доменов Авито** — это статика/CDN, объявлений там не бывает. Убрать: лишний домен в белом списке — это лишняя дверь.
* **`(\d{6,})` как признак id** — тоже допущение (id короче шести знаков отбрасывается молча). Надёжнее правило по форме: «хвост `_<цифры>` последнего сегмента» или «последний сегмент целиком из цифр». И честно назвать это допущением, а не порогом.
* **`rel="noreferrer"`** — в проекте уже так (`ClientCardPane.tsx:88`), задание пишет `noopener noreferrer`; мелочь, но при выносе `ExternalLink` в `shared/ui/` пусть будет одинаково.

## ВЫБРОСИТЬ

1. **Таблица `listing_accounts`.** Пара «объявление × аккаунт» уже выводится из `conversations (item_id, account_id)` — под неё в задании и так создаётся индекс. Аккаунтов девять, случай «одно объявление на двух» — гипотеза, которую сами же записали в unknown №9. Уходит: таблица, каскадные тонкости, тесты, целый абзац edge-case. Предупреждение `listing.seen_on_second_account` оставить — оно стоит один `SELECT DISTINCT`.
2. **`gin (lower(title) gin_trgm_ops)` и `CREATE EXTENSION pg_trgm`.** В `listings` будет от силы несколько сотен строк — по числу объявлений заказчика. `ILIKE '%q%'` последовательным чтением уложится в миллисекунды. Уходит: расширение, недетерминированная миграция, поломка `create_all` на SQLite.
3. **`ix_listings_active (is_active, last_seen_at DESC)`.** Его единственный потребитель — сторож, который я предлагаю выбросить следующим пунктом.
4. **Суточный сторож `refresh_listings`.** Он ежедневно жжёт квоту Авито ради признака, поведение которого мы **не знаем** (unknown №5: что приходит по снятому объявлению). Строить сторожа на неизвестном сигнале — это гарантированные ложные «снято». И задание само предлагает включить его только через неделю. Признак «снято» отлично добывается лениво: следующий поход за карточкой всё равно случится. Отдельной задачей — после того, как unknown №5 закроется.
5. **`GET /stats/listings` ИЛИ `conversations_count` в `GET /listings` — одно из двух.** Сейчас это один и тот же расчёт в двух ручках с разными правами. Выпадашке фильтра счётчик не нужен вовсе (она нужна, чтобы выбрать объявление); срез «Топ объявлений» пусть живёт в статистике. Так `/listings` остаётся дешёвым поиском по названию.
6. **`region` в `listings` и в ответе `/stats/cities`.** Ни в одном макете он не показывается. Появится нужда — добавится колонкой.
7. **`app/integrations/avito/profile.py::client_profile_url`, всегда возвращающая None**, вместе с готовой веткой отрисовки на фронте. Если решено ссылку не собирать (а решено правильно), то и розетку под неё заводить не наду: это мёртвый код с тестом, утверждающим, что он мёртв. Заготовку заменяет одна строка в unknowns. Блок «Клиент на Авито» из §7 п.1 — оставить, он полезен сам по себе.
8. **Третья строка в шапке диалога.** Её убрал UX-аудит осознанно (`ChatThreadPane.tsx:304-314`), и задание об этом не знает. Либо выносить отдельным вопросом владельцу («вернуть объявление в шапку — да/нет»), либо не трогать. Город в шапке — идея хорошая, но она отменяет чужое решение и потому не может ехать прицепом к почин­ке данных.
9. **`item_category_name` в снимке** — под вопросом: он нужен ровно для строки «На момент обращения: Симферополь · Ремонт телевизоров». Города для неё достаточно. Колонка дешёвая, но раз в задании требуют резать лишнее — это первый кандидат после перечисленных.

## Пропущенные крайние случаи

1. **Повторная доставка того же сообщения** (ретрай вебхука, сверка): выход по `msg is None` до правки полей — см. пункт 3 «переделать». В edge-cases этого нет, а это самый частый путь в системе.
2. **Эхо собственного исходящего** отбрасывается первым же условием (`inbound.py:252-253`), до всякой записи. Если окажется, что объявление приходит только в эхо-событии (а мы не знаем, приходит ли оно вообще) — ярус 1 не сработает никогда. Стоит одной строки в задании.
3. **Отключённый канал**: `listings` остаются сиротами (пункт 7 «переделать»).
4. **Гонка первой вставки `listings`** (пункт 5 «переделать»).
5. **Дедуп ARQ съедает задачу** (пункт 4 «переделать»).
6. **Диалог с `item_id`, но без ссылки и без карточки**: показываем «Объявление №8213779975». Что делает по нему фильтр «Объявление ▾» и как эта строка выглядит в срезе по городам — не сказано. Ответ должен быть: попадает в «Город не определён», в выпадашке показывается номером.
7. **Один город под двумя слагами** — раздвоение строки в отчёте (см. «мелкое»).
8. **Клиент пишет по объявлению, снятому ДО первого обращения** (объявление снято, а старый чат ожил): `is_active=false` уже при заведении карточки. Ветки «завели сразу неактивным» в `upsert_listing` нет — там `is_active = true` безусловно.
9. **`--dry-run` при пустом `--account`** и повторный запуск после падения на середине: прогресс в Redis есть, а вот что делать, если между прогонами диалог удалили (канал отключили) — не сказано. Ответ простой: пропускать молча.

**После предложенных сокращений** (нет `listing_accounts`, нет trgm, нет сторожа, нет дубля в `/stats/listings`, нет строки в шапке, нет заготовки профиля) реалистично **44–50 часов**, и к ним **отдельной строкой 8–10 часов резерва на ветвление unknowns**: если `items:info` окажется доступен (unknown №6), разбор ссылки перестаёт быть основным путём и §3 переписывается; если одиночный `GET` чата отдаёт 404 (unknown №4), переписывается бэкфилл. Резерв надо назвать резервом, а не спрятать в 58: смета, в которой неизвестное посчитано как известное, — это тот же угаданный контракт, только в часах.
